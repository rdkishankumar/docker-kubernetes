## Question 1: Explain why a bind mount to `/app` overwrites the container's `node_modules` folder, even though `npm install` ran during image build.

### Answer

When you bind mount a host folder to `/app` in the container, the bind mount **completely replaces** what the container sees at that path. Here's the sequence:

**During Image Build:**
1. `COPY package.json .` → Copies package.json to `/app`
2. `RUN npm install` → Creates `/app/node_modules` with all dependencies
3. `COPY . .` → Copies remaining source code to `/app`
4. Image is complete with `/app/node_modules` populated

**At Container Runtime (with bind mount):**
1. Container starts from image (which has `/app/node_modules`)
2. Bind mount activates: `-v $(pwd):/app`
3. **The host folder REPLACES the entire `/app` directory**
4. Host folder has no `node_modules` → Container now has no `node_modules`
5. Node.js fails: "Cannot find module 'express'"

**Key Insight:**
Docker does not merge the bind mount with existing container contents. The bind mount completely shadows/hides whatever was in the container at that path. All the work done by `npm install` during build becomes invisible.

### Practical Guide

```bash
# ============================================
# DEMONSTRATE THE OVERWRITE PROBLEM
# ============================================

docker build -t feedback-node .

# Check what exists in the IMAGE (without bind mount)
echo "=== Contents of /app in IMAGE ==="
docker run --rm feedback-node ls -la /app
# drwxr-xr-x node_modules    ← EXISTS in image
# -rw-r--r-- package.json
# -rw-r--r-- server.js
# ... etc

# Check what exists in your HOST folder
echo "=== Contents of host project folder ==="
ls -la
# -rw-r--r-- package.json
# -rw-r--r-- server.js
# ... NO node_modules!

# Run WITH bind mount - see what container actually gets
echo "=== Contents of /app WITH bind mount ==="
docker run --rm -v "$(pwd):/app" feedback-node ls -la /app
# -rw-r--r-- package.json
# -rw-r--r-- server.js
# ... NO node_modules!  ← Image's node_modules is HIDDEN

# Try to run the app - it crashes
docker run -d -p 3000:80 \
  -v "$(pwd):/app" \
  --name crash-demo feedback-node

# Check the error
docker logs crash-demo
# Error: Cannot find module 'express'

docker rm -f crash-demo
```

## Question 2: How does Docker behave when there's a conflict between container files and bind mount files?

### Answer

Docker follows specific rules when containers interact with volumes and bind mounts:

**Scenario 1: Volume is empty, container has files**
- Container's files are copied INTO the volume
- Volume now contains what the container had
- This is useful for initializing volumes with application data

**Scenario 2: Volume has files, container path is empty**
- Volume's files are used IN the container
- Container sees the volume's contents at the mount point
- This is what makes data persistence work

**Scenario 3: BOTH have files (the clash)**
- For **bind mounts**: Host files OVERRIDE container files
- For **named volumes**: If volume is empty, container files win; if volume has data, volume wins
- Docker does NOT merge the contents
- Docker does NOT overwrite your host machine files (that would be dangerous)

**Critical Point:**
Docker protects your host machine. It will never automatically delete or overwrite files on your host filesystem. Instead, the bind mount makes the host folder the "source of truth" — the container sees only what's on the host.

### Practical Guide

```bash
docker build -t feedback-node .

# ============================================
# SCENARIO 1: Empty volume, container has files
# ============================================

# Create empty named volume
docker volume create test-data

# Container has /app/feedback folder (from image)
# Volume is empty → Container's files populate the volume
docker run --rm \
  -v test-data:/app/feedback \
  feedback-node ls /app/feedback
# (shows contents from image if any exist)

# Check what's in the volume now
docker run --rm -v test-data:/data alpine ls /data
# (same contents - container populated the volume)

docker volume rm test-data

# ============================================
# SCENARIO 2: Volume has files, container path is empty
# ============================================

docker volume create test-data

# Pre-populate the volume
docker run --rm -v test-data:/data alpine sh -c 'echo "from volume" > /data/file.txt'

# Container's /app/feedback is empty/default
# Volume has files → Volume files appear in container
docker run --rm \
  -v test-data:/app/feedback \
  feedback-node cat /app/feedback/file.txt
# Output: from volume

docker volume rm test-data

# ============================================
# SCENARIO 3: BOTH have files (THE CLASH)
# ============================================

# Host folder has files (your source code)
ls -la  # package.json, server.js, etc.

# Container /app has files (from image build including node_modules)

# With bind mount: HOST WINS, container files are hidden
docker run --rm -v "$(pwd):/app" feedback-node ls /app
# Shows YOUR host files, not the image's /app contents

# Critically: node_modules is in image but NOT on host
# So container sees NO node_modules

# Verify Docker does NOT modify your host folder
ls -la  # Still the same - Docker didn't add node_modules here
```

## Question 3: How does Docker's "longer path wins" rule work, and how does it solve the node_modules problem?

### Answer

**The Rule:**
When multiple volumes/mounts are attached to a container, Docker evaluates all mount points. If there are overlapping paths, the **more specific (longer) path takes precedence** over less specific paths.

**Application to Our Problem:**

We have two mounts:
1. `-v $(pwd):/app` — Bind mount for the entire `/app` directory
2. `-v /app/node_modules` — Anonymous volume for `/app/node_modules` specifically

Since `/app/node_modules` is a longer, more specific path than `/app`, Docker handles them as:
- Everything in `/app` comes from the bind mount (host folder)
- EXCEPT `/app/node_modules`, which comes from the anonymous volume

**Why the Anonymous Volume Contains node_modules:**
When the container starts, Docker sees an anonymous volume mounted at `/app/node_modules`. The volume is initially empty. Following Scenario 1 rules (empty volume + container has files), the container's `node_modules` (from `npm install` during build) populates the anonymous volume. This happens BEFORE the bind mount "clash" is evaluated for that specific path.

The result: `node_modules` survives because it's protected by its own volume mount.

### Practical Guide

```bash
docker build -t feedback-node .

# ============================================
# THE SOLUTION: ANONYMOUS VOLUME FOR NODE_MODULES
# ============================================

docker run -d -p 3000:80 \
  -v "$(pwd):/app" \
  -v /app/node_modules \
  --rm \
  --name feedback-app feedback-node

# Container starts successfully!
docker ps --filter name=feedback-app
# STATUS: Up ✓

# ============================================
# VERIFY THE PATH PRECEDENCE
# ============================================

# /app comes from bind mount (host folder)
docker exec feedback-app ls /app
# Dockerfile, package.json, server.js, etc. ← From HOST
# node_modules ← From ANONYMOUS VOLUME (protected!)

# Confirm node_modules has the actual dependencies
docker exec feedback-app ls /app/node_modules | head -5
# accepts
# array-flatten
# body-parser
# ... etc. ← Dependencies from npm install ✓

# Confirm the app works
curl http://localhost:3000
# Success! ✓

# ============================================
# VERIFY BIND MOUNT STILL WORKS (live editing)
# ============================================

# Make a change on host
echo "<!-- Modified -->" >> feedback.html

# Change is immediately visible in container
docker exec feedback-app grep "Modified" /app/feedback.html
# <!-- Modified --> ✓

# Revert the change
git checkout feedback.html 2>/dev/null || sed -i '' '/Modified/d' feedback.html

docker stop feedback-app
```

## Question 4: What are the two ways to add an anonymous volume, and when would you use each approach?

### Answer

**Method 1: In the Dockerfile (VOLUME instruction)**
```dockerfile
VOLUME ["/app/node_modules"]
```
- Volume is created automatically when any container starts from this image
- Baked into the image definition
- Good for paths that ALWAYS need to be volumes
- Cannot be named (always anonymous)

**Method 2: At runtime with docker run (-v flag)**
```bash
docker run -v /app/node_modules image
```
- Volume is created for this specific container instance
- More flexible — can be added/removed without rebuilding image
- Useful for development scenarios
- Can also be easily changed to a named volume

**Key Difference:**
Both methods create anonymous volumes. The runtime method (`-v /app/node_modules`) is preferred when:
- You want flexibility in different environments
- You're experimenting during development
- You want to avoid rebuilding the image

The Dockerfile method is useful when:
- The path should ALWAYS be a volume
- You want to document volume requirements in the image
- You're creating a base image for others to use

### Practical Guide

```bash
# ============================================
# METHOD 1: VOLUME instruction in Dockerfile
# ============================================

cat <<'EOF' > Dockerfile.with-volume
FROM node:14
WORKDIR /app
COPY package.json .
RUN npm install
COPY . .
VOLUME ["/app/node_modules"]
EXPOSE 80
CMD ["node", "server.js"]
EOF

docker build -t feedback-node:vol-instruction -f Dockerfile.with-volume .

# Run with just the bind mount - node_modules is auto-protected
docker run -d -p 3000:80 \
  -v "$(pwd):/app" \
  --name method1-demo feedback-node:vol-instruction

# Works because VOLUME instruction created anonymous volume
docker exec method1-demo ls /app/node_modules | head -3
# Dependencies present ✓

docker stop method1-demo && docker rm method1-demo

# ============================================
# METHOD 2: Runtime -v flag (preferred for flexibility)
# ============================================

# Use original Dockerfile without VOLUME instruction
docker build -t feedback-node .

# Add anonymous volume at runtime
docker run -d -p 3000:80 \
  -v "$(pwd):/app" \
  -v /app/node_modules \
  --name method2-demo feedback-node

# Same result
docker exec method2-demo ls /app/node_modules | head -3
# Dependencies present ✓

docker stop method2-demo && docker rm method2-demo

# ============================================
# COMPARING THE APPROACHES
# ============================================

# Method 1: Image defines the volume
# Pros: Self-documenting, consistent across all containers
# Cons: Requires image rebuild to change, always anonymous

# Method 2: Runtime defines the volume
# Pros: Flexible, no rebuild needed, can switch to named volume
# Cons: Must remember to add -v flag each time

# RECOMMENDED: Use runtime method for development
# It's explicit and doesn't require rebuilding when experimenting

# Clean up
rm Dockerfile.with-volume 2>/dev/null
```

## Question 5: Walk through the complete solution for a development setup with bind mounts, explaining each volume's purpose.

### Answer

A complete development setup requires three volumes working together:

1. **Bind Mount (`-v $(pwd):/app`)**: Enables live source code editing
2. **Anonymous Volume (`-v /app/node_modules`)**: Protects dependencies from being overwritten
3. **Named Volume (`-v feedback-data:/app/feedback`)**: Persists application data across container restarts

**How They Work Together:**

```
Container /app/ directory:
├── server.js           ← Bind mount (live editing from host)
├── feedback.html       ← Bind mount (live editing from host)  
├── package.json        ← Bind mount (from host)
├── node_modules/       ← Anonymous volume (protected, from npm install)
│   ├── express/
│   └── body-parser/
└── feedback/           ← Named volume (persisted data)
    └── awesome.txt
```

### Practical Guide

```bash
# ============================================
# COMPLETE DEVELOPMENT SETUP
# ============================================

docker build -t feedback-node .

# The full command with all three volume types
docker run -d -p 3000:80 \
  -v "$(pwd):/app" \
  -v /app/node_modules \
  -v feedback-data:/app/feedback \
  --rm \
  --name feedback-app feedback-node

# Verify everything is working
echo "=== Container Status ==="
docker ps --filter name=feedback-app --format "table {{.Status}}\t{{.Ports}}"
# Up    0.0.0.0:3000->80/tcp

# ============================================
# VERIFY EACH VOLUME'S FUNCTION
# ============================================

# 1. BIND MOUNT: Live code editing
echo "=== Testing Bind Mount (live editing) ==="
# Original content
docker exec feedback-app grep -c "Your Feedback" /app/feedback.html

# Make a change on host
sed -i.bak 's/Your Feedback/Your Feedback Please/' feedback.html

# Change is immediately visible in container
docker exec feedback-app grep "Your Feedback Please" /app/feedback.html
# Your Feedback Please ✓

# Restore original
mv feedback.html.bak feedback.html

# 2. ANONYMOUS VOLUME: Protected node_modules
echo "=== Testing Anonymous Volume (node_modules) ==="
docker exec feedback-app ls /app/node_modules | wc -l
# Many packages present ✓

# Verify express specifically (the one that caused the original error)
docker exec feedback-app ls /app/node_modules/express
# Directory exists ✓

# 3. NAMED VOLUME: Persistent data
echo "=== Testing Named Volume (persistent data) ==="
# Create some feedback
curl -X POST -d "title=devtest&text=Development setup works!" \
  http://localhost:3000/submit

# Verify it exists
curl http://localhost:3000/feedback/devtest.txt
# Development setup works! ✓

# Stop container (--rm removes it)
docker stop feedback-app

# Named volume persists
docker volume ls | grep feedback-data
# feedback-data ✓

# Restart with same setup
docker run -d -p 3000:80 \
  -v "$(pwd):/app" \
  -v /app/node_modules \
  -v feedback-data:/app/feedback \
  --rm \
  --name feedback-app feedback-node

# Data survives restart
curl http://localhost:3000/feedback/devtest.txt
# Development setup works! ✓

docker stop feedback-app

# ============================================
# CLEANUP
# ============================================

docker volume rm feedback-data
```

## Question 6: After implementing the solution, verify that live code editing works. What changes are reflected immediately versus what requires a container restart?

### Answer

**Reflected Immediately (no restart needed):**
- Static files: HTML, CSS, images
- Client-side JavaScript
- Template files (if using server-side rendering)
- Configuration files (if application watches for changes)

**Requires Container Restart:**
- Server-side code changes (unless using a file watcher like nodemon)
- Changes to `package.json` dependencies
- Changes to environment variables
- Changes to Dockerfile (requires rebuild + restart)

**For Node.js Specifically:**
Node.js loads server files once at startup. To get automatic server restarts on code changes, you need a tool like **nodemon** which watches for file changes and restarts the Node process.

### Practical Guide

```bash
docker build -t feedback-node .

docker run -d -p 3000:80 \
  -v "$(pwd):/app" \
  -v /app/node_modules \
  --rm \
  --name feedback-app feedback-node

# ============================================
# TEST 1: Static file changes (IMMEDIATE)
# ============================================

echo "=== Static File Changes ==="

# Check current HTML
curl -s http://localhost:3000 | grep -o "Your Feedback.*</h1>"
# Your Feedback</h1>

# Modify HTML on host
sed -i.bak 's/Your Feedback/Your Feedback Please/' feedback.html

# Reload browser / re-fetch - change is IMMEDIATE
curl -s http://localhost:3000 | grep -o "Your Feedback.*</h1>"
# Your Feedback Please</h1> ✓

# Restore
mv feedback.html.bak feedback.html

# ============================================
# TEST 2: Server-side code changes (NEEDS RESTART)
# ============================================

echo "=== Server Code Changes ==="

# Add a new endpoint to server.js
cat >> server.js << 'PATCH'

// Test endpoint added during development
app.get('/test-endpoint', (req, res) => {
  res.send('This is a test endpoint');
});
PATCH

# Try to access it - FAILS (server didn't restart)
curl http://localhost:3000/test-endpoint
# 404 or no response - server code not reloaded

# Restart the container to pick up server changes
docker stop feedback-app
docker run -d -p 3000:80 \
  -v "$(pwd):/app" \
  -v /app/node_modules \
  --rm \
  --name feedback-app feedback-node

# Now it works
curl http://localhost:3000/test-endpoint
# This is a test endpoint ✓

# Revert the change
git checkout server.js 2>/dev/null || head -n -5 server.js > temp && mv temp server.js

# ============================================
# SOLUTION: Use nodemon for auto-restart
# ============================================

# Modify package.json to use nodemon (development)
# Or run with: CMD ["npx", "nodemon", "server.js"]

# Example Dockerfile.dev for development:
cat > Dockerfile.dev << 'EOF'
FROM node:14
WORKDIR /app
COPY package.json .
RUN npm install
RUN npm install -g nodemon
COPY . .
EXPOSE 80
CMD ["nodemon", "server.js"]
EOF

docker build -t feedback-node:dev -f Dockerfile.dev .

docker stop feedback-app 2>/dev/null

docker run -d -p 3000:80 \
  -v "$(pwd):/app" \
  -v /app/node_modules \
  --rm \
  --name feedback-app feedback-node:dev

# Now server code changes trigger automatic restart
# (nodemon watches for changes)

# Clean up
docker stop feedback-app
rm Dockerfile.dev
```
