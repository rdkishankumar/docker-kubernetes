

# Docker Data Management — Interview Questions & Answers with Practical Guide

---

## Question 1: What are the three types of data in a Dockerized application, and how does each one behave?

### Answer

**1. Application Code & Environment (Read-Only)**
- Source code, dependencies, and runtime environment
- Copied into the image at build time via Dockerfile
- Fixed and immutable once the image is built
- Stored in the **image layer**

**2. Temporary Application Data (Read-Write, Ephemeral)**
- Data generated at runtime (e.g., form inputs, session data, intermediate calculations)
- Stored in the **container's writable layer**
- Lost when the container is removed — and that is acceptable
- Examples: user input being validated, in-memory caches, temporary files

**3. Permanent Application Data (Read-Write, Persistent)**
- Data that must survive container shutdowns and replacements (e.g., user accounts, uploaded files, database records)
- Stored using **Docker volumes**
- Persists independently of the container lifecycle

### Practical Guide

```dockerfile
# Dockerfile — Application code goes into the image (Type 1)
FROM node:18-alpine
WORKDIR /app
COPY package.json .
RUN npm install
COPY . .                  # Code is baked into the image here
EXPOSE 3000
CMD ["node", "server.js"]
```

```javascript
// server.js — demonstrates all three data types
const express = require('express');
const fs = require('fs');
const path = require('path');
const app = express();
app.use(express.json());

// TYPE 1: Application code — this file itself, read-only in the image

// TYPE 2: Temporary data — stored in memory, lost on container removal
let activeSessionCount = 0;

app.post('/login', (req, res) => {
  activeSessionCount++;  // Temporary; acceptable to lose
  res.json({ sessions: activeSessionCount });
});

// TYPE 3: Permanent data — written to a volume-backed path
const DATA_DIR = '/app/data';

app.post('/users', (req, res) => {
  const usersFile = path.join(DATA_DIR, 'users.json');
  let users = [];
  if (fs.existsSync(usersFile)) {
    users = JSON.parse(fs.readFileSync(usersFile, 'utf8'));
  }
  users.push({ id: Date.now(), name: req.body.name });
  fs.writeFileSync(usersFile, JSON.stringify(users));
  res.json({ message: 'User created', users });
});

app.listen(3000);
```

```bash
# Build and run with a volume for permanent data
docker build -t data-demo .
docker run -d -p 3000:3000 -v app-data:/app/data --name myapp data-demo

# Test permanent data
curl -X POST -H "Content-Type: application/json" -d '{"name":"Alice"}' http://localhost:3000/users

# Stop and remove container
docker stop myapp && docker rm myapp

# Restart with same volume — users.json is still there
docker run -d -p 3000:3000 -v app-data:/app/data --name myapp data-demo
curl http://localhost:3000/users   # Alice still exists
```

## Question 2: Why are Docker images read-only, and what happens if you need to change the application code?

### Answer

Docker images are **read-only by design**. Once every instruction in the Dockerfile finishes executing, the image is "locked in" and closed. You cannot go into an existing image and modify files.

This is intentional because:
- **Reproducibility**: Every container started from the same image behaves identically
- **Security**: Running applications should not modify their own source code
- **Caching efficiency**: Immutable layers can be safely shared across containers and builds

If you need to change application code, you must **rebuild the image**, creating a new image. The old containers continue running the old code until you replace them.

### Practical Guide

```bash
# Original build
docker build -t myapp:v1 .

# Make a code change in server.js, then rebuild
docker build -t myapp:v2 .

# Replace the running container
docker stop myapp
docker rm myapp
docker run -d -p 3000:3000 -v app-data:/app/data --name myapp myapp:v2
# Permanent data in the volume survives the transition
```

```bash
# Demonstrate that you CANNOT modify image contents
docker run -it myapp:v1 sh
# Inside container: you CAN write files in the container layer
echo "test" > /app/newfile.txt
exit

# But after removing and recreating the container, that file is gone
docker rm $(docker ps -aq --filter ancestor=myapp:v1)
docker run -it myapp:v1 sh
cat /app/newfile.txt   # File not found — the image is unchanged
```

## Question 3: Explain Docker's layered file system — specifically the difference between the image layer and the container's writable layer.

### Answer

Docker uses a **Union File System** architecture:

**Image Layers (Read-Only)**
- Each Dockerfile instruction creates a new layer
- Layers are stacked and cached
- Shared across all containers using that image

**Container Layer (Read-Write)**
- When a container starts, Docker adds a thin **writable layer** on top of the image layers
- This layer mirrors the image's file system without copying it (copy-on-write strategy)
- Any file modifications, new files, or deletions are tracked only in this layer
- Docker derives the final file system by combining the image layers + the changes in the writable layer
- This layer is **destroyed** when the container is removed

```
┌─────────────────────────────────┐
│  Container Writable Layer (R/W) │  ← Changes tracked here
├─────────────────────────────────┤
│  Image Layer: CMD               │  (Read-Only)
│  Image Layer: COPY . .          │  (Read-Only)
│  Image Layer: RUN npm install   │  (Read-Only)
│  Image Layer: COPY package.json │  (Read-Only)
│  Image Layer: WORKDIR /app      │  (Read-Only)
│  Image Layer: FROM node:18      │  (Read-Only)
└─────────────────────────────────┘
```

### Practical Guide — Observe the Layers

```bash
# Inspect image layers
docker history myapp:v1

# Check how much data the container's writable layer is using
docker ps -s
# The "SIZE" column shows the writable layer size
# The "virtual" size shows image + writable layer combined

# Demonstrate copy-on-write
docker run -d --name cow-demo myapp:v1

# Write a 10MB file inside the container
docker exec cow-demo sh -c "dd if=/dev/zero of=/app/bigfile bs=1M count=10"

# Check size again — writable layer grew by ~10MB
docker ps -s --filter name=cow-demo

# The image itself is unchanged
docker images myapp:v1   # Same size as before

# Clean up
docker rm -f cow-demo
```

## Question 4: What are Docker Volumes, and why are they necessary for permanent application data?

### Answer

**Volumes** are Docker-managed storage mechanisms that exist **outside the container's writable layer** and persist independently of the container lifecycle.

They are necessary because:
- The container's writable layer is destroyed when the container is removed
- You must be able to stop, remove, and replace containers (e.g., deploying updates) without losing critical data
- Without volumes, you could never update your application without losing all persistent data

**Types of Docker storage mounts:**

| Type | Managed By | Persistence | Use Case |
|------|-----------|-------------|----------|
| Named Volume | Docker | Survives container removal | Databases, user uploads |
| Anonymous Volume | Docker | Lost on `docker rm` (unless `--volumes-from`) | Temp optimization |
| Bind Mount | Host OS | Tied to host path | Development, config files |

### Practical Guide

```bash
# 1. Named Volume — best for production persistent data
docker volume create app-data
docker run -d -v app-data:/app/data --name prod myapp:v1

# Write data, remove container, verify data survives
docker exec prod sh -c 'echo "persistent" > /app/data/test.txt'
docker rm -f prod
docker run --rm -v app-data:/app/data alpine cat /app/data/test.txt
# Output: persistent

# 2. Anonymous Volume — container-scoped, typically for optimization
docker run -d -v /app/node_modules --name anon myapp:v1
# Useful to prevent bind mounts from overwriting node_modules

# 3. Bind Mount — for development (live code reload)
docker run -d \
  -v $(pwd):/app \
  -v /app/node_modules \
  -v app-data:/app/data \
  -p 3000:3000 \
  --name dev myapp:v1

# Inspect and manage volumes
docker volume ls
docker volume inspect app-data
docker volume rm app-data       # Only works if no container is using it
docker volume prune             # Remove all unused volumes
```

## Question 5: A developer says: "I'll just keep my container running forever so I never lose data." What's wrong with this approach?

### Answer

This approach has multiple critical flaws:

1. **Containers are ephemeral by design** — the Docker philosophy assumes containers can be stopped, replaced, and recreated at any time

2. **You cannot deploy updates** — changing application code requires building a new image and starting a new container. If your data lives only in the container layer, updating code means losing data.

3. **`docker stop` + `docker start`** preserves the writable layer, but **`docker rm`** destroys it. A server crash, host reboot, or OOM kill can remove the container entirely.

4. **Scaling is impossible** — running multiple replicas from the same image won't share the container-layer data

5. **No backup strategy** — container layer data is opaque and hard to back up

### Correct Approach

```bash
# Separate concerns: code in image, persistent data in volumes
docker run -d \
  -v user-data:/app/data \
  -v db-data:/var/lib/postgresql/data \
  --name myapp myapp:v1

# Now you can safely do this:
docker stop myapp
docker rm myapp
docker run -d \
  -v user-data:/app/data \
  -v db-data:/var/lib/postgresql/data \
  --name myapp myapp:v2    # New code, same data
```

## Question 6: Walk through a complete real-world example showing the problem volumes solve.

### Answer & Practical Guide

```javascript
// feedback-app/server.js
const express = require('express');
const fs = require('fs');
const path = require('path');
const app = express();
app.use(express.json());

const FEEDBACK_DIR = '/app/feedback';

// Ensure directory exists
if (!fs.existsSync(FEEDBACK_DIR)) {
  fs.mkdirSync(FEEDBACK_DIR, { recursive: true });
}

app.post('/feedback', (req, res) => {
  const { title, text } = req.body;
  const filename = `${title.toLowerCase()}.txt`;
  fs.writeFileSync(path.join(FEEDBACK_DIR, filename), text);
  res.json({ message: 'Feedback saved' });
});

app.get('/feedback', (req, res) => {
  const files = fs.readdirSync(FEEDBACK_DIR);
  const feedback = files.map(f => ({
    title: f.replace('.txt', ''),
    text: fs.readFileSync(path.join(FEEDBACK_DIR, f), 'utf8')
  }));
  res.json(feedback);
});

app.listen(3000, () => console.log('Listening on 3000'));
```

```dockerfile
FROM node:18-alpine
WORKDIR /app
COPY package.json .
RUN npm install
COPY . .
EXPOSE 3000
CMD ["node", "server.js"]
```

```bash
# --- WITHOUT VOLUME: Data is lost ---
docker build -t feedback-app .
docker run -d -p 3000:3000 --name fb feedback-app

curl -X POST -H "Content-Type: application/json" \
  -d '{"title":"great","text":"Awesome course!"}' \
  http://localhost:3000/feedback

curl http://localhost:3000/feedback
# [{"title":"great","text":"Awesome course!"}]

docker rm -f fb
docker run -d -p 3000:3000 --name fb feedback-app

curl http://localhost:3000/feedback
# [] ← DATA IS GONE!

docker rm -f fb

# --- WITH VOLUME: Data persists ---
docker run -d -p 3000:3000 \
  -v feedback-data:/app/feedback \
  --name fb feedback-app

curl -X POST -H "Content-Type: application/json" \
  -d '{"title":"great","text":"Awesome course!"}' \
  http://localhost:3000/feedback

docker rm -f fb
docker run -d -p 3000:3000 \
  -v feedback-data:/app/feedback \
  --name fb feedback-app

curl http://localhost:3000/feedback
# [{"title":"great","text":"Awesome course!"}] ← DATA SURVIVED!
```

## Quick Reference Cheat Sheet

```
┌──────────────────────────────────────────────────────────────┐
│              DOCKER DATA MANAGEMENT SUMMARY                  │
├────────────────┬──────────┬────────────┬─────────────────────┤
│ Data Type      │ Access   │ Stored In  │ Lifecycle           │
├────────────────┼──────────┼────────────┼─────────────────────┤
│ App Code/Env   │ Read     │ Image      │ Fixed at build time │
│ Temp App Data  │ Read/Write│ Container │ Dies with container │
│ Permanent Data │ Read/Write│ Volume    │ Survives container  │
└────────────────┴──────────┴────────────┴─────────────────────┘

Key Commands:
  docker volume create <name>
  docker volume ls
  docker volume inspect <name>
  docker volume rm <name>
  docker volume prune
  docker run -v <name>:<container-path>     # Named volume
  docker run -v <host-path>:<container-path> # Bind mount
  docker run -v <container-path>             # Anonymous volume
```
