

# Docker Build-Time Arguments (ARG) — Complete Study Guide

---

## 📘 Detailed Notes

### 1. What Are Build-Time Arguments (ARG)?

Build-time arguments allow you to inject variable values into your Dockerfile **at image build time** without modifying the Dockerfile itself. This enables building multiple different images from the same Dockerfile by passing different argument values.

### 2. ARG vs ENV — The Complete Picture

```
┌─────────────────────────────────────────────────────────────────┐
│                        DOCKERFILE                                │
│                                                                  │
│   ARG DEFAULT_PORT=80          ← Build-time variable             │
│   ENV PORT $DEFAULT_PORT       ← Runtime variable, seeded by ARG │
│   EXPOSE $PORT                 ← Uses ENV                        │
│                                                                  │
├──────────────────────┬──────────────────────────────────────────┤
│    docker build      │           docker run                      │
│    --build-arg       │           --env / -e                      │
│    DEFAULT_PORT=8000 │           PORT=9000                       │
│                      │                                           │
│  Locks value INTO    │  Overrides value AT                       │
│  the image           │  container startup                        │
└──────────────────────┴──────────────────────────────────────────┘
```

| Aspect | **ARG** | **ENV** |
|---|---|---|
| **Available when** | Image build only | Build + Runtime |
| **Set via** | `--build-arg` on `docker build` | `--env` / `-e` on `docker run` |
| **Accessible in app code** | ❌ No | ✅ Yes |
| **Accessible in Dockerfile** | ✅ Yes (most instructions) | ✅ Yes |
| **Can use in CMD** | ❌ No (runtime instruction) | ✅ Yes |
| **Persists in image** | ❌ No (not in final image metadata) | ✅ Yes |
| **Purpose** | Customize image at build time | Customize container at runtime |

### 3. ARG Syntax in Dockerfile

```dockerfile
# With default value
ARG DEFAULT_PORT=80

# Without default value (MUST be provided at build time)
ARG DEFAULT_PORT

# Using ARG in other instructions ($ prefix required)
ENV PORT $DEFAULT_PORT
```

### 4. The "Inception" Pattern — ARG Feeding ENV

This is a powerful and common pattern:

```dockerfile
ARG DEFAULT_PORT=80        # Flexible at BUILD time
ENV PORT $DEFAULT_PORT     # Flexible at RUN time, seeded by ARG
EXPOSE $PORT               # Uses the ENV value
```

**What this achieves:**
- `ARG` sets a **build-time configurable default**
- `ENV` takes that default but remains **overridable at runtime**
- You get flexibility at **both** stages without changing the Dockerfile

### 5. Setting ARG at Build Time

```bash
# Using the default value (ARG DEFAULT_PORT=80)
docker build -t feedback-node:web-app .

# Overriding with a custom value
docker build -t feedback-node:dev --build-arg DEFAULT_PORT=8000 .
```

After building, the ARG value is **locked into that specific image**. The two images above have different default ports baked in.

### 6. Critical: ARG Placement and Layer Caching

**Problem:** ARG instructions add layers. When an ARG value changes, **all subsequent layers are invalidated and rebuilt**.

```dockerfile
# ❌ BAD PLACEMENT — npm install reruns every time ARG changes
FROM node:18-alpine
WORKDIR /app
ARG DEFAULT_PORT=80          # ← If this changes...
COPY package.json .
RUN npm install              # ← ...this reruns unnecessarily!
COPY . .
ENV PORT $DEFAULT_PORT
EXPOSE $PORT
CMD ["node", "server.js"]
```

```dockerfile
# ✅ GOOD PLACEMENT — npm install is cached regardless of ARG changes
FROM node:18-alpine
WORKDIR /app
COPY package.json .
RUN npm install              # ← Cached! Not affected by ARG below
COPY . .
ARG DEFAULT_PORT=80          # ← Placed AFTER npm install
ENV PORT $DEFAULT_PORT
EXPOSE $PORT
CMD ["node", "server.js"]
```

**Rule:** Place `ARG` (and `ENV`) as late as possible — right before the first instruction that actually needs them.

### 7. Where ARG Can and Cannot Be Used

| Instruction | ARG Usable? | Notes |
|---|---|---|
| `FROM` | ✅ Yes | Only if ARG is declared before FROM |
| `RUN` | ✅ Yes | |
| `COPY` | ✅ Yes | |
| `ADD` | ✅ Yes | |
| `ENV` | ✅ Yes | Common pattern to seed ENV with ARG |
| `EXPOSE` | ✅ Yes | |
| `WORKDIR` | ✅ Yes | |
| `LABEL` | ✅ Yes | |
| `USER` | ✅ Yes | |
| **`CMD`** | **❌ No** | Runtime instruction — ARG is not available |
| **`ENTRYPOINT`** | **❌ No** | Runtime instruction — ARG is not available |

### 8. Complete Flow Summary

```
┌─────────────────────────────────────────────────────────────┐
│  STEP 1: Dockerfile defines ARG with default                 │
│          ARG DEFAULT_PORT=80                                  │
│                                                              │
│  STEP 2: Build image A (uses default)                        │
│          docker build -t app:web .                           │
│          → DEFAULT_PORT = 80 (locked in image)               │
│                                                              │
│  STEP 3: Build image B (overrides ARG)                       │
│          docker build -t app:dev --build-arg DEFAULT_PORT=8000│
│          → DEFAULT_PORT = 8000 (locked in image)             │
│                                                              │
│  STEP 4: Run container from image B                          │
│          docker run -p 3000:8000 app:dev                     │
│          → PORT = 8000 (from baked-in default)               │
│                                                              │
│  STEP 5: Run container from image B with ENV override        │
│          docker run -p 3000:9000 -e PORT=9000 app:dev        │
│          → PORT = 9000 (runtime override wins)               │
└─────────────────────────────────────────────────────────────┘
```

## 🎯 Interview Questions & Answers

### Q1: What are Docker build-time arguments and how do they differ from environment variables?

**Answer:**
Build-time arguments (`ARG`) are variables available **only during the image build process**. They allow you to pass values into the Dockerfile at `docker build` time using `--build-arg`. Once the image is built, ARG values are no longer accessible.

Environment variables (`ENV`), by contrast, persist into the running container and are accessible by the application code. ARG is for **build-time customization** (e.g., which version of a dependency to install, which default port to set), while ENV is for **runtime configuration** (e.g., database connection strings, feature flags).

A common and powerful pattern combines both: ARG seeds a default value for ENV, giving flexibility at both build time and runtime:
```dockerfile
ARG DEFAULT_PORT=80
ENV PORT $DEFAULT_PORT
```

---

### Q2: Why can't you use ARG in CMD or ENTRYPOINT instructions?

**Answer:**
`CMD` and `ENTRYPOINT` are **runtime instructions** — they define what executes when the container starts, not during the build. ARG values exist only during the build process and are not embedded in the final image's runtime environment. By the time the container starts and CMD executes, ARG values no longer exist.

If you need a configurable value at runtime, use `ENV` instead:
```dockerfile
# ❌ Won't work
ARG MY_CMD=server.js
CMD ["node", "$MY_CMD"]

# ✅ Works — ENV is available at runtime
ENV MY_CMD=server.js
CMD ["sh", "-c", "node $MY_CMD"]
```

---

### Q3: How does the placement of ARG in a Dockerfile affect build performance?

**Answer:**
Docker builds images in layers, and each instruction creates a layer. Docker caches layers and only rebuilds from the point where something changes. When an ARG value changes (via `--build-arg`), **all layers after the ARG instruction are invalidated** and must be rebuilt.

This means placing ARG early in the Dockerfile can cause expensive operations like `RUN npm install` to rerun unnecessarily:

```dockerfile
# Bad: npm install reruns when DEFAULT_PORT changes
ARG DEFAULT_PORT=80
COPY package.json .
RUN npm install        # ← invalidated by ARG change above

# Good: npm install stays cached
COPY package.json .
RUN npm install        # ← cached, unaffected
ARG DEFAULT_PORT=80    # ← placed after expensive operations
ENV PORT $DEFAULT_PORT
```

**Best practice:** Place ARG as late as possible — immediately before the first instruction that references it.

---

### Q4: Can you build multiple images from the same Dockerfile with different configurations? How?

**Answer:**
Yes, using `--build-arg`. This is one of the primary use cases for ARG:

```dockerfile
ARG DEFAULT_PORT=80
ARG NODE_ENV=production
ENV PORT $DEFAULT_PORT
ENV NODE_ENV $NODE_ENV
```

```bash
# Production image (port 80, production mode)
docker build -t myapp:prod .

# Development image (port 8000, development mode)
docker build -t myapp:dev \
  --build-arg DEFAULT_PORT=8000 \
  --build-arg NODE_ENV=development .

# Staging image (port 3000, staging mode)
docker build -t myapp:staging \
  --build-arg DEFAULT_PORT=3000 \
  --build-arg NODE_ENV=staging .
```

Each build produces a distinct image with different baked-in defaults, all from the same unchanged Dockerfile. The values are **locked in** after the build.

---

### Q5: What happens if you define an ARG without a default value and don't provide `--build-arg`?

**Answer:**
If an ARG is declared without a default value and no `--build-arg` is provided at build time, the ARG will be an **empty string**. Any Dockerfile instruction referencing it will receive an empty value, which may cause unexpected behavior:

```dockerfile
ARG DEFAULT_PORT         # No default
ENV PORT $DEFAULT_PORT   # PORT will be empty string
EXPOSE $PORT             # EXPOSE with empty value — may cause issues
```

```bash
# This will result in PORT="" in the image
docker build -t myapp .

# This will set PORT=8000
docker build -t myapp --build-arg DEFAULT_PORT=8000 .
```

**Best practice:** Always provide a sensible default value for ARG unless you explicitly want to force the user to provide one.

---

### Q6: Explain the "ARG feeding ENV" pattern and why it's useful.

**Answer:**
The pattern:
```dockerfile
ARG DEFAULT_PORT=80
ENV PORT $DEFAULT_PORT
```

This creates a **two-level configuration system**:

1. **At build time:** `--build-arg DEFAULT_PORT=8000` sets what default gets baked into the image
2. **At runtime:** `-e PORT=9000` can still override that baked-in default

Without this pattern, you'd either have:
- Only ARG: configurable at build time but not at runtime, not accessible in app code
- Only ENV with hardcoded default: configurable at runtime but the default is always the same across all image variants

The combined pattern gives maximum flexibility:
```bash
# Build with custom default
docker build -t app:dev --build-arg DEFAULT_PORT=8000 .

# Run with baked-in default (8000)
docker run -p 3000:8000 app:dev

# Run with runtime override (9000)
docker run -p 3000:9000 -e PORT=9000 app:dev
```

### Q7: Are ARG values visible in the final Docker image? What are the security implications?

**Answer:**
ARG values are **not persisted** in the final image's environment — they won't appear in `docker inspect` under the environment section. However, they **can be visible** in the image's build history:

```bash
docker history myapp:latest
# May show: --build-arg SECRET_KEY=mysecret
```

**Security implications:**
- **Never use ARG for secrets** (passwords, API keys, tokens)
- Anyone with access to the image can run `docker history` to see build arguments
- Multi-stage builds can help isolate ARG usage to intermediate stages
- For secrets during build, use `docker build --secret` (BuildKit feature)

```bash
# ❌ INSECURE — visible in image history
docker build --build-arg DB_PASSWORD=secret123 -t myapp .

# ✅ BETTER — use BuildKit secrets
DOCKER_BUILDKIT=1 docker build --secret id=db_pass,src=./db_password.txt -t myapp .
```

---

### Q8: Can you use ARG before the FROM instruction?

**Answer:**
Yes, but with important limitations. An ARG declared before `FROM` is only available in the `FROM` instruction itself. After `FROM`, the ARG goes out of scope:

```dockerfile
# ARG before FROM — used to parameterize the base image
ARG NODE_VERSION=18
FROM node:${NODE_VERSION}-alpine

# This ARG is out of scope now — need to redeclare if needed
ARG NODE_VERSION       # Must redeclare to use again
RUN echo "Node version: $NODE_VERSION"
```

```bash
docker build --build-arg NODE_VERSION=20 -t myapp .
```

This pattern is useful for building images with different base image versions from the same Dockerfile.

### Q9: How would you structure a Dockerfile that uses both ARG and ENV optimally for layer caching?

**Answer:**
The key principle is: **place ARG/ENV as late as possible** to maximize cache hits.

```dockerfile
FROM node:18-alpine

WORKDIR /app

# ── Layer 1: Dependencies (rarely changes) ──
COPY package.json package-lock.json ./
RUN npm ci --production

# ── Layer 2: Source code (changes frequently) ──
COPY . .

# ── Layer 3: Configuration (ARG + ENV placed LAST) ──
# Changing --build-arg only invalidates from here
ARG DEFAULT_PORT=80
ARG APP_VERSION=1.0.0
ENV PORT $DEFAULT_PORT
ENV APP_VERSION $APP_VERSION

EXPOSE $PORT

LABEL version=$APP_VERSION

CMD ["node", "server.js"]
```

With this structure:
- Changing `--build-arg DEFAULT_PORT` only rebuilds from the ARG instruction onward
- `npm ci` remains cached regardless of ARG changes
- Source code copy is also cached if unchanged

### Q10: Walk through a real-world scenario where you'd use both ARG and ENV together.

**Answer:**
**Scenario:** A Node.js API that needs to be deployed to three environments — development, staging, and production — each with different ports and log levels.

```dockerfile
FROM node:18-alpine
WORKDIR /app
COPY package.json .
RUN npm install
COPY . .

# Build-time configuration — baked into each image variant
ARG DEFAULT_PORT=80
ARG DEFAULT_LOG_LEVEL=info

# Runtime configuration — can be overridden per container
ENV PORT $DEFAULT_PORT
ENV LOG_LEVEL $DEFAULT_LOG_LEVEL
ENV NODE_ENV production

EXPOSE $PORT
CMD ["node", "server.js"]
```

```bash
# Build three image variants
docker build -t api:prod .
docker build -t api:staging --build-arg DEFAULT_PORT=3000 --build-arg DEFAULT_LOG_LEVEL=debug .
docker build -t api:dev --build-arg DEFAULT_PORT=8000 --build-arg DEFAULT_LOG_LEVEL=debug .

# Run production
docker run -d -p 80:80 api:prod

# Run staging with runtime override
docker run -d -p 3000:3000 -e NODE_ENV=staging api:staging

# Run dev with hot-reload bind mount
docker run -d -p 8000:8000 -e NODE_ENV=development -v $(pwd):/app:ro api:dev
```

Each image has different **baked-in defaults**, but any value can still be overridden at runtime with `-e`. This provides the maximum flexibility while maintaining sensible defaults per environment.

```dockerfile

# ── Dependencies layer (cached unless package.json changes) ──

# ── Source code layer ──
COPY . .

# ── Configuration layer (PLACED LAST for optimal caching) ──
# ARG: Build-time configurable — sets the default baked into the image
# ENV: Runtime configurable — can be overridden with docker run -e
ARG DEFAULT_PORT=80
ENV PORT $DEFAULT_PORT

# EXPOSE uses the ENV value (which was seeded by ARG)

# Anonymous volume for temp files
```

```dockerfile

# Changing --build-arg DEFAULT_PORT will invalidate ALL layers below

# ❌ This reruns every time DEFAULT_PORT changes — wasteful!
```

### server.js

```javascript
const express = require('express');
const bodyParser = require('body-parser');
const fs = require('fs');
const path = require('path');

const app = express();
app.use(bodyParser.urlencoded({ extended: true }));
app.use(express.static('public'));

// ─── Read environment variables ───
// process.env.PORT — set by Docker ENV (seeded by ARG at build time)
// Can be overridden at runtime with: docker run -e PORT=9000
const port = process.env.PORT || 80;
const appMode = process.env.APP_MODE || 'development';
const logLevel = process.env.LOG_LEVEL || 'info';

console.log('╔══════════════════════════════════════╗');
console.log('║       APPLICATION CONFIGURATION       ║');
console.log('╠══════════════════════════════════════╣');
console.log(`║  PORT:      ${String(port).padEnd(25)}║`);
console.log(`║  APP_MODE:  ${appMode.padEnd(25)}║`);
console.log(`║  LOG_LEVEL: ${logLevel.padEnd(25)}║`);
console.log('╚══════════════════════════════════════╝');

// Save feedback
app.post('/feedback', (req, res) => {
  const title = req.body.title;
  const content = req.body.content;
  const tempPath = path.join(__dirname, 'temp', title + '.txt');
  const finalPath = path.join(__dirname, 'feedback', title + '.txt');

  fs.writeFile(tempPath, content, (err) => {
    if (err) return res.status(500).send('Error saving');
    fs.copyFile(tempPath, finalPath, (err) => {
      if (err) return res.status(500).send('Error moving');
      fs.unlink(tempPath, () => {});
      res.send(`Feedback "${title}" saved! (Port: ${port}, Mode: ${appMode})`);
    });
  });
});

// Config endpoint — shows current configuration
app.get('/config', (req, res) => {
  res.json({ port, appMode, logLevel, nodeEnv: process.env.NODE_ENV || 'not set' });
});

// Feedback list
app.get('/feedback', (req, res) => {
  const dir = path.join(__dirname, 'feedback');
  fs.readdir(dir, (err, files) => {
    if (err) return res.json([]);
    res.json(files.filter(f => f.endsWith('.txt')));
  });
});

// Read feedback
app.get('/feedback/:file', (req, res) => {
  const filePath = path.join(__dirname, 'feedback', req.params.file);
  fs.readFile(filePath, 'utf8', (err, data) => {
    if (err) return res.status(404).send('Not found');
    res.send(data);
  });
});

// ─── Listen on the configured PORT ───
app.listen(port, () => {
  console.log(`Server running on port ${port}`);
});
```

```bash
#!/bin/bash

# ============================================================
# DOCKER ARG & ENV — COMPLETE PRACTICAL GUIDE
# ============================================================

# PART 1: BUILD WITH DEFAULT ARG VALUE
# ──────────────────────────────────────────────────────────

# feedback-node:web-app → PORT defaults to 80
# feedback-node:dev     → PORT defaults to 8000

# ──────────────────────────────────────────────────────────

  --name app-prod \
  --rm \
  -p 3000:80 \
  -v feedback:/app/feedback \
  feedback-node:web-app

# OUTPUT: { "port": 80, "appMode": "development", "logLevel": "info" }

docker stop app-prod

# ──────────────────────────────────────────────────────────
# PART 4: RUN DEV IMAGE (uses baked-in default of 8000)
# ──────────────────────────────────────────────────────────

docker run -d \
  --name app-dev \
  --rm \
  -p 3000:8000 \
  -v feedback:/app/feedback \
  feedback-node:dev

echo "✅ Dev container running — http://localhost:3000"
curl -s http://localhost:3000/config | python3 -m json.tool
# OUTPUT: { "port": 8000, "appMode": "development", "logLevel": "info" }

docker stop app-dev

# ──────────────────────────────────────────────────────────
# PART 5: RUNTIME ENV OVERRIDE (overrides baked-in ARG default)
# ──────────────────────────────────────────────────────────

# Production env file
```

```
│                    ARG IN DOCKERFILE                          │

│  EXPOSE $PORT              → Use in instructions              │
│                                                              │
│  ⚠️  Cannot use ARG in CMD or ENTRYPOINT                     │
│  ⚠️  ARG is NOT available in running application code         │

│                  SETTING ARG AT BUILD TIME                    │
├──────────────────────────────────────────────────────────────┤

│  docker build --build-arg A=1 --build-arg B=2 -t app .      │

│             THE FLEXIBILITY CHAIN                             │
├──────────────────────────────────────────────────────────────┤
```
