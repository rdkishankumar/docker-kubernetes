## Question 1: What happens to data stored inside a Docker container when the container is stopped versus when it is removed? Explain the difference.

### Answer

**Stopping a container (`docker stop`):**
- The container process halts but the container **still exists**
- The container's writable layer and all data within it are **fully preserved**
- You can restart the same container with `docker start` and all data will be intact
- Application code, generated files, and any runtime changes remain untouched

**Removing a container (`docker rm` or `--rm` flag):**
- The container and its entire writable layer are **permanently deleted**
- All data that was written inside the container is **lost forever**
- Starting a new container from the same image creates a **fresh writable layer** with no knowledge of the previous container's data
- The image itself is never modified, so only the base snapshot remains

The key insight: **stopping ≠ removing**. A stopped container is like a paused process — everything is preserved. A removed container is like deleting a virtual machine — everything is gone.

### Practical Guide

```bash
# Build the feedback application
docker build -t feedback-node .

# ============================================
# SCENARIO 1: Stop and Restart (data survives)
# ============================================

# Run WITHOUT --rm so the container persists after stopping
docker run -d -p 3000:80 --name feedback-app feedback-node

# Create some data inside the container
curl -X POST -d "title=awesome&text=This is awesome" http://localhost:3000/submit

# Verify data exists
curl http://localhost:3000/feedback/awesome.txt
# Output: This is awesome ✓

# Stop the container
docker stop feedback-app

# Verify container still exists (just stopped)
docker ps -a --filter name=feedback-app
# STATUS: Exited (0) ...  ← Container exists but is stopped

# Restart the SAME container
docker start feedback-app

# Data is still there!
curl http://localhost:3000/feedback/awesome.txt
# Output: This is awesome ✓ — DATA SURVIVED

# ============================================
# SCENARIO 2: Stop and Remove (data is lost)
# ============================================

# Stop and remove the container
docker stop feedback-app
docker rm feedback-app

# Verify container is gone
docker ps -a --filter name=feedback-app
# No results — container is deleted

# Start a NEW container from the same image
docker run -d -p 3000:80 --name feedback-app feedback-node

# Try to access the previously stored data
curl http://localhost:3000/feedback/awesome.txt
# 404 Not found — DATA IS GONE ✗

docker stop feedback-app && docker rm feedback-app

# ============================================
# SCENARIO 3: Using --rm flag (auto-removes)
# ============================================

# Run WITH --rm
docker run -d -p 3000:80 --rm --name feedback-app feedback-node

# Create data
curl -X POST -d "title=temporary&text=Will this survive?" http://localhost:3000/submit

# Stop the container (--rm means it's auto-removed)
docker stop feedback-app

# Container is gone
docker ps -a --filter name=feedback-app
# No results

# New container has no data
docker run -d -p 3000:80 --rm --name feedback-app feedback-node
curl http://localhost:3000/feedback/temporary.txt
# 404 Not found — DATA IS GONE ✗

docker stop feedback-app
```

## Question 2: Explain Docker's layered architecture and why data written by a container never modifies the underlying image.

### Answer

Docker uses a **Union File System** with two distinct zones:

**Image Layers (Read-Only):**
- Built from Dockerfile instructions
- Each instruction creates an immutable layer
- Contains the application code snapshot from build time
- Shared across all containers based on that image
- **Never modified** by any running container

**Container Layer (Read-Write):**
- A thin writable layer added on top of the image layers when a container starts
- Uses **copy-on-write (CoW)**: when a container needs to modify a file from the image, it copies that file into the writable layer and modifies the copy
- All new files, modifications, and deletions are tracked only in this layer
- This layer is **unique to each container** — multiple containers from the same image each get their own independent writable layer
- **Destroyed** when the container is removed

This is why:
- Removing a container loses data — the writable layer is deleted, and the image was never touched
- A new container from the same image starts fresh — it gets a new empty writable layer
- Multiple containers from the same image are completely isolated from each other

```
Container A                    Container B
┌──────────────────┐          ┌──────────────────┐
│ Writable Layer A │          │ Writable Layer B │
│ (awesome.txt)    │          │ (different data) │
├──────────────────┤          ├──────────────────┤
│                                                │
│          Shared Image Layers (Read-Only)       │
│  ┌─────────────────────────────────────────┐   │
│  │ CMD ["node", "server.js"]               │   │
│  │ EXPOSE 80                               │   │
│  │ COPY . .                                │   │
│  │ RUN npm install                         │   │
│  │ COPY package.json .                     │   │
│  │ WORKDIR /app                            │   │
│  │ FROM node:14                            │   │
│  └─────────────────────────────────────────┘   │
└────────────────────────────────────────────────┘
```

### Practical Guide

```bash
docker build -t feedback-node .

# Start two containers from the SAME image
docker run -d -p 3000:80 --name container-a feedback-node
docker run -d -p 3001:80 --name container-b feedback-node

# Write different data in each container
curl -X POST -d "title=fromA&text=Data from container A" http://localhost:3000/submit
curl -X POST -d "title=fromB&text=Data from container B" http://localhost:3001/submit

# Each container has ONLY its own data
docker exec container-a ls /app/feedback/
# fromA.txt

docker exec container-b ls /app/feedback/
# fromB.txt

# Container A cannot see Container B's data and vice versa
docker exec container-a cat /app/feedback/fromB.txt 2>&1
# cat: /app/feedback/fromB.txt: No such file or directory

# Remove container-a — its data is gone
docker stop container-a && docker rm container-a

# Container B is unaffected
docker exec container-b cat /app/feedback/fromB.txt
# Data from container B ✓

# Start a new container-a — it has no data
docker run -d -p 3000:80 --name container-a feedback-node
docker exec container-a ls /app/feedback/
# Empty — fresh writable layer

# Verify the IMAGE was never changed
docker image inspect feedback-node --format='{{.Created}}'
# Same timestamp as original build — image is untouched

# Clean up
docker stop container-a container-b
docker rm container-a container-b
```

## Question 3: Why is data loss on container removal a critical problem in real-world applications? Give concrete scenarios.

### Answer

In real-world applications, containers are removed **routinely and frequently**. Data loss on removal creates serious issues in these scenarios:

**1. Application Updates / Deployments:**
- You change source code → rebuild the image → must start a new container
- The old container must be removed
- All user-generated data from the old container is lost

**2. Scaling:**
- Multiple container instances don't share writable layers
- User data created in one container is invisible to others

**3. Container Crashes:**
- If a container crashes and the orchestrator restarts it as a new container, data is lost
- Even with `--restart` policies, certain failure modes result in container replacement

**4. Infrastructure Changes:**
- Moving containers between hosts
- Upgrading Docker itself
- OS-level maintenance requiring container recreation

**Types of data at risk:**
- User accounts and authentication data
- Uploaded files (images, documents)
- Application-generated reports
- Database records (if database runs in a container)
- User preferences and settings
- Transaction logs and audit trails

### Practical Guide — Demonstrating the Deployment Problem

```bash
# ---- Simulating a real deployment cycle ----

# Version 1 of the app
docker build -t feedback-node:v1 .

docker run -d -p 3000:80 --name feedback-app feedback-node:v1

# Users interact with the app over days/weeks
curl -X POST -d "title=review1&text=Great product!" http://localhost:3000/submit
curl -X POST -d "title=review2&text=Fast shipping!" http://localhost:3000/submit
curl -X POST -d "title=review3&text=Will buy again!" http://localhost:3000/submit

# Verify: 3 feedback files exist
docker exec feedback-app ls /app/feedback/
# review1.txt  review2.txt  review3.txt

# ---- Developer makes a code change and deploys v2 ----

# (Imagine editing server.js to add a new feature)
docker build -t feedback-node:v2 .

# Must remove old container to free the port and name
docker stop feedback-app
docker rm feedback-app

# Deploy new version
docker run -d -p 3000:80 --name feedback-app feedback-node:v2

# ALL USER DATA IS GONE
docker exec feedback-app ls /app/feedback/
# Empty! Three reviews lost forever.

curl http://localhost:3000/feedback/review1.txt
# 404 Not found

docker stop feedback-app && docker rm feedback-app
```

```bash
# ---- The solution preview: Volumes ----

# With a named volume, data survives container replacement
docker run -d -p 3000:80 \
  -v feedback-data:/app/feedback \
  --name feedback-app feedback-node:v1

curl -X POST -d "title=review1&text=Great product!" http://localhost:3000/submit
curl -X POST -d "title=review2&text=Fast shipping!" http://localhost:3000/submit

# Deploy v2 — remove old container
docker stop feedback-app && docker rm feedback-app

# Start v2 with the SAME volume
docker run -d -p 3000:80 \
  -v feedback-data:/app/feedback \
  --name feedback-app feedback-node:v2

# Data survived!
curl http://localhost:3000/feedback/review1.txt
# Great product! ✓

docker exec feedback-app ls /app/feedback/
# review1.txt  review2.txt ✓

docker stop feedback-app && docker rm feedback-app
```

## Question 4: A junior developer argues: "I'll just never use `--rm` and always use `docker start` instead of `docker run` to preserve my data." Why is this strategy flawed?

### Answer

While this approach technically preserves data in the short term, it fails for multiple reasons:

**1. You can never update your application:**
- `docker start` restarts the *same* container with the *same* image
- To deploy new code, you need a new image and therefore a new container
- The old container must eventually be removed, losing all data

**2. Container accumulation:**
- Without `--rm`, stopped containers pile up consuming disk space
- `docker ps -a` fills with dozens of dead containers
- Eventually you'll clean them up and lose data anyway

**3. Single point of failure:**
- All data exists in exactly one container's writable layer
- No backup, no redundancy
- A corrupted container means total data loss

**4. No scalability:**
- Can't run multiple replicas sharing the same data
- Tied to a single container instance

**5. No portability:**
- Can't move the container's data to another host easily
- Violates Docker's philosophy of disposable containers

### Practical Guide — Showing Why This Fails

```bash
docker build -t feedback-node .

# Junior developer's approach: never use --rm, always docker start
docker run -d -p 3000:80 --name feedback-app feedback-node

# Create data
curl -X POST -d "title=important&text=Critical data" http://localhost:3000/submit

# "Safe" restart — data preserved
docker stop feedback-app
docker start feedback-app
curl http://localhost:3000/feedback/important.txt
# Critical data ✓ — Junior developer says "See? It works!"

# ---- But then a code change is needed ----
# Edit server.js to fix a bug...
docker build -t feedback-node:v2 .

# Junior developer tries to use the new image
docker stop feedback-app
docker start feedback-app
# This STILL runs v1! docker start uses the original image.

# To use v2, they MUST create a new container
docker rm feedback-app
docker run -d -p 3000:80 --name feedback-app feedback-node:v2

# Data is gone!
curl http://localhost:3000/feedback/important.txt
# 404 Not found ✗

docker stop feedback-app && docker rm feedback-app

# ---- The correct approach: volumes ----
docker run -d -p 3000:80 \
  -v feedback-data:/app/feedback \
  --rm --name feedback-app feedback-node:v1

curl -X POST -d "title=important&text=Critical data" http://localhost:3000/submit

# Safe to stop (--rm removes container) and deploy new version
docker stop feedback-app
docker run -d -p 3000:80 \
  -v feedback-data:/app/feedback \
  --rm --name feedback-app feedback-node:v2

curl http://localhost:3000/feedback/important.txt
# Critical data ✓ — Data survived AND we're running new code
```

## Question 5: Explain the relationship between `docker stop`, `docker start`, `docker rm`, `docker run`, and `--rm` in the context of data persistence.

### Answer

| Command | What It Does | Container State After | Data in Writable Layer |
|---------|-------------|----------------------|----------------------|
| `docker run` | Creates and starts a **new** container | Running | Fresh/empty layer |
| `docker stop` | Stops a running container | Stopped (Exited) | **Preserved** |
| `docker start` | Restarts a **stopped** container | Running | **Preserved** (same layer) |
| `docker rm` | Deletes a stopped container | Deleted | **Destroyed** |
| `docker run --rm` | Creates container; auto-removes on stop | Deleted after stop | **Destroyed** on stop |

**The lifecycle:**
```
docker run → [Running] → docker stop → [Stopped] → docker start → [Running]
                                          ↓
                                       docker rm → [Deleted] → data lost
                                       
docker run --rm → [Running] → docker stop → [Deleted] → data lost
```

### Practical Guide

```bash
docker build -t feedback-node .

# ---- Full lifecycle demonstration ----

# 1. CREATE and START a new container
docker run -d -p 3000:80 --name lifecycle-demo feedback-node
echo "Step 1: Container created and running"
docker ps --filter name=lifecycle-demo --format "{{.Status}}"
# Up X seconds

# Add data
curl -X POST -d "title=lifecycle&text=Testing lifecycle" http://localhost:3000/submit

# 2. STOP the container
docker stop lifecycle-demo
echo "Step 2: Container stopped"
docker ps -a --filter name=lifecycle-demo --format "{{.Status}}"
# Exited (0) X seconds ago

# 3. START the same container again
docker start lifecycle-demo
echo "Step 3: Container restarted"
curl http://localhost:3000/feedback/lifecycle.txt
# Testing lifecycle ✓ — data preserved across stop/start

# 4. STOP again
docker stop lifecycle-demo

# 5. REMOVE the container
docker rm lifecycle-demo
echo "Step 5: Container removed"
docker ps -a --filter name=lifecycle-demo
# No results — container is gone

# 6. RUN a new container (same image)
docker run -d -p 3000:80 --name lifecycle-demo feedback-node
echo "Step 6: New container from same image"
curl http://localhost:3000/feedback/lifecycle.txt
# 404 — data is gone ✗

# Clean up
docker stop lifecycle-demo && docker rm lifecycle-demo

# ---- Demonstrate --rm behavior ----
docker run -d -p 3000:80 --rm --name rm-demo feedback-node

curl -X POST -d "title=rmtest&text=Will this survive?" http://localhost:3000/submit

# Cannot use docker rm on a --rm container while running
# docker rm rm-demo → Error: container is running

# Stop triggers automatic removal
docker stop rm-demo
docker ps -a --filter name=rm-demo
# No results — automatically removed

# Cannot docker start a removed container
docker start rm-demo 2>&1
# Error: No such container: rm-demo
```

## Question 6: What is Docker's solution to the data persistence problem, and what are the key concepts involved?

### Answer

Docker's solution is **Volumes** — a mechanism for persisting data outside the container's writable layer. Volumes are managed by Docker and exist on the host file system, but are designed to outlive any individual container.

**The core problem volumes solve:**
- Container writable layers are destroyed on `docker rm`
- Application data (user accounts, uploads, feedback) must survive container replacement
- Code updates require new containers, which means the old container's data would be lost

**How volumes work conceptually:**
- A volume is a directory on the host file system managed by Docker
- It is **mounted** into the container at a specific path
- When the container writes to that path, the data goes to the volume, not the writable layer
- When the container is removed, the volume remains untouched
- A new container can mount the same volume and immediately access the previous data

**Three types of external storage in Docker:**

| Type | Syntax | Managed By | Survives `docker rm` | Use Case |
|------|--------|-----------|---------------------|----------|
| **Named Volume** | `-v name:/path` | Docker | ✓ Yes | Production persistent data |
| **Anonymous Volume** | `-v /path` | Docker | ✗ No (unless explicitly kept) | Temp optimization |
| **Bind Mount** | `-v /host/path:/path` | User | ✓ Yes | Development, config |

### Practical Guide

```bash
docker build -t feedback-node .

# ---- WITHOUT volumes (the problem) ----
docker run -d -p 3000:80 --rm --name no-vol feedback-node
curl -X POST -d "title=lost&text=This will be lost" http://localhost:3000/submit
docker stop no-vol
# Container removed, data gone forever

# ---- WITH named volume (the solution) ----
docker run -d -p 3000:80 --rm \
  -v feedback-data:/app/feedback \
  --name with-vol feedback-node

# Create data
curl -X POST -d "title=saved&text=This will survive" http://localhost:3000/submit

# Verify data exists
curl http://localhost:3000/feedback/saved.txt
# This will survive ✓

# Stop container (--rm removes it)
docker stop with-vol

# Volume still exists!
docker volume ls
# DRIVER    VOLUME NAME
# local     feedback-data

# Inspect the volume
docker volume inspect feedback-data
# Shows mountpoint on host file system

# Start a completely new container with the same volume
docker run -d -p 3000:80 --rm \
  -v feedback-data:/app/feedback \
  --name with-vol feedback-node

# Data is still there!
curl http://localhost:3000/feedback/saved.txt
# This will survive ✓

# Even works across different image versions
docker stop with-vol
docker build -t feedback-node:v2 .
docker run -d -p 3000:80 --rm \
  -v feedback-data:/app/feedback \
  --name with-vol feedback-node:v2

curl http://localhost:3000/feedback/saved.txt
# This will survive ✓ — Data persists across image versions!

docker stop with-vol

# Volume management
docker volume ls                    # List all volumes
docker volume inspect feedback-data # Details about a volume
docker volume rm feedback-data      # Delete a volume
docker volume prune                 # Remove all unused volumes
```
