

# Docker ARG & ENV — Build-Time Arguments & Runtime Environment Variables

---

## 📘 Detailed Notes

### 1. Two Mechanisms for Flexible Configuration

Docker provides two mechanisms to avoid hard-coding values into images and containers:

| Feature | **ARG** (Build-time Argument) | **ENV** (Runtime Environment Variable) |
|---|---|---|
| **When available** | Only during image build (`docker build`) | During container runtime (`docker run`) AND in Dockerfile |
| **Set via** | `--build-arg` flag on `docker build` | `--env` / `-e` flag on `docker run` or `--env-file` |
| **Declared in Dockerfile** | `ARG` instruction | `ENV` instruction |
| **Accessible in app code** | ❌ No | ✅ Yes (e.g., `process.env.PORT` in Node.js) |
| **Accessible in Dockerfile** | ✅ Yes (in instructions after declaration) | ✅ Yes (with `$VARIABLE_NAME` syntax) |
| **Purpose** | Plug different values into Dockerfile instructions at build time | Configure running application behavior without rebuilding |

### 2. Environment Variables (ENV) — Deep Dive

#### Declaring in Dockerfile
```dockerfile
ENV PORT 80
```
- Announces the environment variable `PORT` with a default value of `80`
- Available in all subsequent Dockerfile instructions using `$PORT` syntax
- Available in the running application code

#### Using in Dockerfile Instructions
```dockerfile
EXPOSE $PORT
```
- The `$` prefix tells Docker to resolve the environment variable
- Docker substitutes the actual value stored in that variable

#### Using in Application Code (Node.js)
```javascript
const port = process.env.PORT;
app.listen(port);
```
- `process.env` is a globally available object in Node.js
- Most programming languages have equivalent mechanisms for reading environment variables

#### Overriding at Runtime
```bash
# Using --env flag
docker run --env PORT=8000 my-image

# Using shorthand -e flag
docker run -e PORT=8000 my-image

# Multiple environment variables
docker run -e PORT=8000 -e DB_HOST=localhost my-image

# Using an environment file
docker run --env-file ./.env my-image
```

#### Environment File (.env)
```
PORT=8000
DB_HOST=localhost
DB_USER=admin
```
- Conventionally named `.env` but any filename works
- Each line contains one `KEY=VALUE` pair
- Referenced with `--env-file ./path/to/.env`
- Advantage: change values in the file without modifying the `docker run` command

### 3. Key Behavioral Rules

- **No rebuild needed**: Changing an environment variable at runtime does NOT require rebuilding the image
- **Default values**: The `ENV` instruction in the Dockerfile sets a default; `--env` at runtime overrides it
- **Port mapping must match**: If you change the internal port via ENV, your `-p` flag must map to the new port
- **Convention**: Environment variable names are written in ALL UPPERCASE (e.g., `PORT`, `DB_HOST`)

### 4. The Workflow

```
┌──────────────────────────────────────────────────────────────┐
│                    BUILD TIME (docker build)                  │
│                                                              │
│   Dockerfile:  ENV PORT 80    ← declares with default        │
│                EXPOSE $PORT   ← uses the variable            │
│                                                              │
├──────────────────────────────────────────────────────────────┤
│                    RUN TIME (docker run)                      │
│                                                              │
│   Option A:  --env PORT=8000        ← overrides default      │
│   Option B:  -e PORT=8000           ← shorthand              │
│   Option C:  --env-file ./.env      ← reads from file        │
│   Option D:  (nothing)              ← uses default (80)      │
│                                                              │
├──────────────────────────────────────────────────────────────┤
│                    APPLICATION CODE                           │
│                                                              │
│   process.env.PORT  →  8000 (or 80 if no override)          │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

## 🎯 Interview Questions & Answers

### Q1: What is the difference between ARG and ENV in Docker?

**Answer:**
- **ARG** is a build-time variable. It is only available during the image build process (`docker build`). It's set using `--build-arg` and declared with the `ARG` instruction in the Dockerfile. It is **not** accessible in the running container or application code.
- **ENV** is a runtime environment variable. It is available both during the build (in Dockerfile instructions after its declaration) **and** at runtime inside the container's application code. It's declared with `ENV` in the Dockerfile and can be overridden using `--env` or `-e` on `docker run`.

The key distinction: ARG influences **how the image is built**; ENV influences **how the container runs**.

---

### Q2: How do you reference an environment variable inside a Dockerfile instruction?

**Answer:**
You use the dollar sign (`$`) prefix followed by the variable name. For example:

```dockerfile
ENV PORT 80
EXPOSE $PORT
```

Docker interprets `$PORT` by looking up the environment variable named `PORT` and substituting its value. Without the `$` prefix, Docker would treat it as a literal string.

---

### Q3: Do you need to rebuild an image to change an environment variable?

**Answer:**
**No.** That is one of the primary advantages of environment variables. The default value is baked into the image via the `ENV` instruction, but you can override it at runtime using `--env` or `--env-file` on the `docker run` command. This allows the same image to run in different configurations (development, staging, production) without rebuilding.

---

### Q4: What happens if you change the PORT environment variable but don't update the `-p` flag?

**Answer:**
The container will listen on the new port internally, but it won't be accessible from outside because the port mapping (`-p`) still points to the old port. For example:

```bash
# WRONG: Container listens on 8000 internally, but -p maps to 80
docker run -e PORT=8000 -p 3000:80 my-image
# Port 80 inside container has nothing → connection refused

# CORRECT: -p maps to the actual internal port
docker run -e PORT=8000 -p 3000:8000 my-image
```

The `EXPOSE` instruction in the Dockerfile is only documentation — it doesn't actually publish ports. The `-p` flag does the actual mapping and must match the real internal port.

---

### Q5: What are the different ways to pass environment variables to a Docker container?

**Answer:**
Four approaches:

1. **`--env KEY=VALUE`** — inline on docker run
   ```bash
   docker run --env PORT=8000 my-image
   ```

2. **`-e KEY=VALUE`** — shorthand for `--env`
   ```bash
   docker run -e PORT=8000 -e NODE_ENV=production my-image
   ```

3. **`--env-file`** — read from a file
   ```bash
   docker run --env-file ./.env my-image
   ```

4. **Default in Dockerfile** — if no override is provided
   ```dockerfile
   ENV PORT 80
   ```

Priority: Runtime flags (`--env`, `-e`) override Dockerfile defaults.

---

### Q6: Why would you use an `.env` file instead of inline `--env` flags?

**Answer:**
- **Convenience**: Avoid long `docker run` commands with many `-e` flags
- **Reusability**: Same file can be reused across multiple `docker run` invocations
- **Separation of concerns**: Change configuration by editing the file rather than modifying commands
- **Security**: Keep sensitive values (API keys, passwords) in a file that's `.gitignore`'d rather than in shell history
- **Consistency**: Team members share the same `.env.example` template

---

### Q7: How do most programming languages access Docker environment variables?

**Answer:**
Docker environment variables are standard OS-level environment variables. Most languages have built-in access:

| Language | Access Method |
|---|---|
| **Node.js** | `process.env.PORT` |
| **Python** | `os.environ['PORT']` or `os.getenv('PORT', '80')` |
| **Java** | `System.getenv("PORT")` |
| **Go** | `os.Getenv("PORT")` |
| **Ruby** | `ENV['PORT']` |
| **PHP** | `getenv('PORT')` or `$_ENV['PORT']` |
| **C#/.NET** | `Environment.GetEnvironmentVariable("PORT")` |

---

### Q8: Can you use ENV variables in every Dockerfile instruction?

**Answer:**
ENV variables can be used in most Dockerfile instructions that accept string values, including:
- `RUN`, `CMD`, `ENTRYPOINT`
- `EXPOSE`
- `WORKDIR`
- `COPY` (in some contexts)
- `ADD`
- `LABEL`
- `USER`

They are referenced with `$VARIABLE_NAME` or `${VARIABLE_NAME}` syntax. The variable must be declared with `ENV` (or `ARG`) **before** the instruction that references it.

---

### Q9: What is a common security concern with environment variables in Docker?

**Answer:**
Environment variables set via `ENV` in the Dockerfile are **baked into the image layers** and can be inspected by anyone with access to the image using `docker inspect` or `docker history`. This means:

- **Never put secrets** (passwords, API keys, tokens) in `ENV` instructions in the Dockerfile
- Use `--env` or `--env-file` at runtime instead for sensitive values
- The `.env` file should be added to `.gitignore` and `.dockerignore`
- For production, use Docker secrets (Swarm) or external secret management tools (Vault, AWS Secrets Manager)

---

### Q10: If you set `ENV PORT 80` in the Dockerfile and then run with `-e PORT=8000`, which value does the application receive?

**Answer:**
The application receives `8000`. Runtime `-e` / `--env` values **override** the default specified in the Dockerfile's `ENV` instruction. The Dockerfile default is only used when no runtime override is provided.

### Dockerfile

```dockerfile
FROM node:18-alpine

WORKDIR /app

COPY package.json .

RUN npm install

COPY . .

# ─── Environment Variable Declaration ───
# Declares PORT with a default value of 80
# Available in:
#   1. Subsequent Dockerfile instructions (via $PORT)
#   2. Running application code (via process.env.PORT)
ENV PORT 80

# Uses the environment variable — NOT hard-coded
EXPOSE $PORT

# Anonymous volume for temp files
VOLUME ["/app/temp"]

CMD ["node", "server.js"]
```

### server.js

```javascript
const express = require('express');
const bodyParser = require('body-parser');
const fs = require('fs');
const path = require('path');

const app = express();
app.use(bodyParser.urlencoded({ extended: true }));
app.use(express.static('public'));

// ─── ENVIRONMENT VARIABLE USAGE ───
// process.env.PORT reads the PORT environment variable
// If set via Docker: uses that value
// If not set: uses the default from Dockerfile's ENV instruction
const port = process.env.PORT || 80;

// Additional env var examples
const appMode = process.env.APP_MODE || 'development';
const logLevel = process.env.LOG_LEVEL || 'info';

console.log(`=== Configuration ===`);
console.log(`PORT: ${port}`);
console.log(`APP_MODE: ${appMode}`);
console.log(`LOG_LEVEL: ${logLevel}`);
console.log(`=====================`);

// Save feedback
app.post('/feedback', (req, res) => {
  const title = req.body.title;
  const content = req.body.content;
  const tempPath = path.join(__dirname, 'temp', title + '.txt');
  const finalPath = path.join(__dirname, 'feedback', title + '.txt');

  if (logLevel === 'debug') {
    console.log(`[DEBUG] Writing to temp: ${tempPath}`);
    console.log(`[DEBUG] Final destination: ${finalPath}`);
  }

  fs.writeFile(tempPath, content, (err) => {
    if (err) return res.status(500).send('Error saving feedback');

    fs.copyFile(tempPath, finalPath, (err) => {
      if (err) return res.status(500).send('Error moving feedback');
      fs.unlink(tempPath, () => {});

      if (logLevel === 'debug') {
        console.log(`[DEBUG] Feedback "${title}" saved successfully`);
      }

      res.send(`Feedback "${title}" saved! (Mode: ${appMode})`);
    });
  });
});

// Read feedback
app.get('/feedback/:filename', (req, res) => {
  const filePath = path.join(__dirname, 'feedback', req.params.filename);
  fs.readFile(filePath, 'utf8', (err, data) => {
    if (err) return res.status(404).send('Feedback not found');
    res.send(data);
  });
});

// Health check showing config
app.get('/config', (req, res) => {
  res.json({
    port,
    appMode,
    logLevel,
    nodeEnv: process.env.NODE_ENV || 'not set'
  });
});

// ─── Listen on the PORT from environment variable ───
app.listen(port, () => {
  console.log(`Server is running on port ${port}`);
});
```

### docker-commands.sh — Full Practical Walkthrough

```bash
#!/bin/bash

# ============================================================
# DOCKER ENV & ARG — PRACTICAL GUIDE
# ============================================================

# ──────────────────────────────────────────────────────────
# PART 1: BUILD THE IMAGE
# ──────────────────────────────────────────────────────────

docker build -t feedback-app:env .

# ──────────────────────────────────────────────────────────
# PART 2: RUN WITH DEFAULT ENV VALUES
# ──────────────────────────────────────────────────────────

# Uses PORT=80 (the default from Dockerfile's ENV instruction)
docker run -d \
  --name feedback-app \
  --rm \
  -p 3000:80 \
  -v feedback:/app/feedback \
  feedback-app:env

# Test it
curl http://localhost:3000/config
# OUTPUT: {"port":80,"appMode":"development","logLevel":"info","nodeEnv":"not set"}

# Stop before next run
docker stop feedback-app

# ──────────────────────────────────────────────────────────
# PART 3: OVERRIDE ENV WITH --env FLAG
# ──────────────────────────────────────────────────────────

# Override PORT to 8000 — NO IMAGE REBUILD NEEDED
docker run -d \
  --name feedback-app \
  --rm \
  -p 3000:8000 \
  -v feedback:/app/feedback \
  --env PORT=8000 \
  feedback-app:env

# Internal port is now 8000, mapped to external 3000
curl http://localhost:3000/config
# OUTPUT: {"port":8000,"appMode":"development","logLevel":"info","nodeEnv":"not set"}

docker stop feedback-app

# ──────────────────────────────────────────────────────────
# PART 4: USE SHORTHAND -e FLAG WITH MULTIPLE VARIABLES
# ──────────────────────────────────────────────────────────

docker run -d \
  --name feedback-app \
  --rm \
  -p 3000:8000 \
  -v feedback:/app/feedback \
  -e PORT=8000 \
  -e APP_MODE=staging \
  -e LOG_LEVEL=debug \
  -e NODE_ENV=staging \
  feedback-app:env

curl http://localhost:3000/config
# OUTPUT: {"port":8000,"appMode":"staging","logLevel":"debug","nodeEnv":"staging"}

docker stop feedback-app

# ──────────────────────────────────────────────────────────
# PART 5: USE --env-file TO LOAD FROM FILE
# ──────────────────────────────────────────────────────────

# Development mode (using .env file)
docker run -d \
  --name feedback-app \
  --rm \
  -p 3000:8000 \
  -v feedback:/app/feedback \
  --env-file ./.env \
  feedback-app:env

curl http://localhost:3000/config
# OUTPUT: {"port":8000,"appMode":"development","logLevel":"debug","nodeEnv":"not set"}

docker stop feedback-app

# Production mode (using .env.production file)
docker run -d \
  --name feedback-app \
  --rm \
  -p 3000:80 \
  -v feedback:/app/feedback \
  --env-file ./.env.production \
  feedback-app:env

curl http://localhost:3000/config
# OUTPUT: {"port":80,"appMode":"production","logLevel":"error","nodeEnv":"not set"}

docker stop feedback-app

# ──────────────────────────────────────────────────────────
# PART 6: COMBINE --env-file WITH INLINE OVERRIDES
# ──────────────────────────────────────────────────────────

# Load base config from file, override specific values inline
docker run -d \
  --name feedback-app \
  --rm \
  -p 3000:8000 \
  -v feedback:/app/feedback \
  --env-file ./.env \
  -e LOG_LEVEL=warn \
  feedback-app:env

# LOG_LEVEL will be "warn" (inline override wins)
curl http://localhost:3000/config

docker stop feedback-app

# ──────────────────────────────────────────────────────────
# PART 7: FULL COMMAND WITH VOLUMES + ENV
# ──────────────────────────────────────────────────────────

docker run -d \
  --name feedback-app \
  --rm \
  -p 3000:8000 \
  -v feedback:/app/feedback \
  -v "$(pwd):/app:ro" \
  -v /app/node_modules \
  -v /app/temp \
  --env-file ./.env \
  feedback-app:env

# Now we have:
# ✅ Named volume for persistent feedback data
# ✅ Bind mount for live code editing (read-only)
# ✅ Anonymous volumes protecting node_modules and temp
# ✅ Environment variables loaded from file
# ✅ No image rebuild needed to change configuration

docker stop feedback-app
```

### Docker Compose with ENV Variables (docker-compose.yml)

```yaml
version: "3.8"

services:
  feedback-app:
    build: .
    ports:
      - "3000:${PORT:-80}"
    volumes:
      - feedback:/app/feedback
      - ./:/app:ro
      - /app/node_modules
      - /app/temp
    environment:
      # Option A: Inline key-value pairs
      - PORT=8000
      - APP_MODE=development
      - LOG_LEVEL=debug
    # Option B: Use env_file instead of environment
    # env_file:
    #   - ./.env

volumes:
  feedback:
```

```bash
# Run with inline environment values
docker-compose up -d

# Or override with .env file by uncommenting env_file in compose
docker-compose up -d

# Pass variables from shell environment
PORT=9000 docker-compose up -d
```
