## Question 1: What are read-only volumes in Docker, and why would you use them?

### Answer

**What They Are:**

Read-only volumes are volumes mounted with restricted write permissions. By adding `:ro` after the container path in a volume mount, you prevent the container from modifying files in that volume.

**Syntax:**
```bash
-v "/host/path:/container/path:ro"
```

**Why Use Them:**

1. **Enforce Intent**: Your source code should be edited by developers on the host machine, not by the running application inside the container
2. **Security**: Prevents accidental or malicious modifications to important files
3. **Clarity**: Makes the purpose of each volume explicit — read-only volumes are for input, read-write volumes are for output
4. **Best Practice**: Follows the principle of least privilege — only grant write access where it's actually needed

**Default Behavior:**

By default, all volumes (bind mounts, named volumes, anonymous volumes) are **read-write**. The container can both read from and write to them. Adding `:ro` restricts this to read-only.

### Practical Guide

```bash
docker build -t feedback-node .

# ============================================
# DEFAULT: Read-Write Volume
# ============================================

docker run -d -p 3000:80 \
  -v "$(pwd):/app" \
  -v /app/node_modules \
  --rm \
  --name rw-demo feedback-node

# Container CAN write to the bind mount
docker exec rw-demo sh -c 'echo "Container wrote this" > /app/test-write.txt'

# File appears on host
cat test-write.txt
# Container wrote this ✓

# Clean up
rm test-write.txt
docker stop rw-demo

# ============================================
# READ-ONLY: Restricted Volume
# ============================================

docker run -d -p 3000:80 \
  -v "$(pwd):/app:ro" \
  -v /app/node_modules \
  --rm \
  --name ro-demo feedback-node

# Container CANNOT write to the bind mount
docker exec ro-demo sh -c 'echo "Attempt to write" > /app/test-write.txt'
# sh: can't create /app/test-write.txt: Read-only file system ✗

# Host can still write (restriction only affects container)
echo "Host wrote this" > host-file.txt

# Container can READ the host's file
docker exec ro-demo cat /app/host-file.txt
# Host wrote this ✓

# Clean up
rm host-file.txt
docker stop ro-demo
```

## Question 2: When using a read-only bind mount for your entire project folder, how do you handle subdirectories that need to be writable?

### Answer

**The Problem:**

If you make `/app` read-only, all subdirectories (`/app/feedback`, `/app/temp`, `/app/node_modules`) also become read-only. But your application needs to write to some of these directories.

**The Solution:**

Use Docker's **path specificity rule**: more specific (longer) paths override less specific paths. Add separate volumes for subdirectories that need write access.

```bash
-v "$(pwd):/app:ro"           # Entire app folder: read-only
-v feedback-data:/app/feedback # Feedback subfolder: read-write (overrides)
-v /app/temp                   # Temp subfolder: read-write (overrides)
-v /app/node_modules           # node_modules: read-write (overrides)
```

**How It Works:**

| Path | Volume Type | Access | Why |
|------|-------------|--------|-----|
| `/app` | Bind mount (ro) | Read-only | Source code shouldn't be modified |
| `/app/feedback` | Named volume | Read-write | Application needs to store user data |
| `/app/temp` | Anonymous volume | Read-write | Application needs temporary storage |
| `/app/node_modules` | Anonymous volume | Read-write | Needs to exist (and possibly be modified by npm) |

### Practical Guide

```bash
docker build -t feedback-node .

# ============================================
# PROBLEM: Read-only breaks writable subdirectories
# ============================================

# Try with just :ro - this will fail
docker run -d -p 3000:80 \
  -v "$(pwd):/app:ro" \
  -v /app/node_modules \
  --rm \
  --name broken-ro feedback-node

# Try to submit feedback
curl -X POST -d "title=test&text=Testing" http://localhost:3000/submit
# Error! Can't write to /app/temp or /app/feedback

# Check logs for the error
docker logs broken-ro
# Error: EROFS: read-only file system, open '/app/temp/test.txt'

docker stop broken-ro

# ============================================
# SOLUTION: Override specific paths with writable volumes
# ============================================

docker run -d -p 3000:80 \
  -v "$(pwd):/app:ro" \
  -v feedback-data:/app/feedback \
  -v /app/temp \
  -v /app/node_modules \
  --rm \
  --name working-ro feedback-node

# Now it works!
curl -X POST -d "title=rotest&text=Read-only test" http://localhost:3000/submit
# Saved! ✓

curl http://localhost:3000/feedback/rotest.txt
# Read-only test ✓

# ============================================
# VERIFY: Source code is protected
# ============================================

# Container cannot modify source files
docker exec working-ro sh -c 'echo "hack" >> /app/server.js'
# sh: can't create /app/server.js: Read-only file system ✗

# But can write to the allowed subdirectories
docker exec working-ro sh -c 'echo "ok" > /app/temp/test.txt'
# Success ✓

docker exec working-ro sh -c 'echo "ok" > /app/feedback/test.txt'
# Success ✓

# Clean up
docker stop working-ro
docker volume rm feedback-data
```

## Question 3: Why should the anonymous volume for `/app/temp` be specified in the `docker run` command rather than in the Dockerfile when using read-only bind mounts?

### Answer

**The Key Insight:**

When you have a read-only bind mount at `/app`, any volumes that need to override subdirectories must be specified at **runtime** (in `docker run`), not at **build time** (in Dockerfile).

**Why This Matters:**

1. **VOLUME in Dockerfile**: Creates a volume declaration in the image, but this doesn't interact with runtime bind mounts properly
2. **-v in docker run**: Creates the volume at container startup, allowing Docker to properly evaluate path specificity against the bind mount

**The Technical Reason:**

Docker evaluates volume mounts in the order they're processed at container creation. When you specify `-v /app/temp` at runtime:
- Docker sees the bind mount to `/app`
- Docker sees the anonymous volume to `/app/temp`
- Docker applies path specificity: `/app/temp` (more specific) overrides `/app`

When you use `VOLUME ["/app/temp"]` in Dockerfile with a runtime bind mount:
- The behavior is less predictable
- The bind mount may still take precedence
- The anonymous volume might not properly override the read-only restriction

### Practical Guide

```bash
# ============================================
# DOCKERFILE APPROACH (PROBLEMATIC)
# ============================================

cat > Dockerfile.vol-in-file << 'EOF'
FROM node:14
WORKDIR /app
COPY package.json .
RUN npm install
COPY . .
VOLUME ["/app/temp"]
VOLUME ["/app/feedback"]
EXPOSE 80
CMD ["npm", "start"]
EOF

docker build -t feedback-node:vol-in-file -f Dockerfile.vol-in-file .

# Try with read-only bind mount
docker run -d -p 3000:80 \
  -v "$(pwd):/app:ro" \
  -v /app/node_modules \
  --rm \
  --name vol-in-file feedback-node:vol-in-file

# This may still fail or behave unexpectedly
curl -X POST -d "title=test&text=Test" http://localhost:3000/submit
# Potentially: Error: EROFS: read-only file system

docker logs vol-in-file
docker stop vol-in-file 2>/dev/null

# ============================================
# RUNTIME APPROACH (CORRECT)
# ============================================

cat > Dockerfile << 'EOF'
FROM node:14
WORKDIR /app
COPY package.json .
RUN npm install
COPY . .
EXPOSE 80
CMD ["npm", "start"]
EOF

docker build -t feedback-node .

# Specify ALL volumes at runtime
docker run -d -p 3000:80 \
  -v "$(pwd):/app:ro" \
  -v feedback-data:/app/feedback \
  -v /app/temp \
  -v /app/node_modules \
  --rm \
  --name vol-runtime feedback-node

# This works reliably
curl -X POST -d "title=test&text=Test" http://localhost:3000/submit
# Saved! ✓

docker stop vol-runtime
docker volume rm feedback-data

# Clean up
rm Dockerfile.vol-in-file
```

## Question 4: Walk through the complete read-only development setup with all necessary volume overrides.

### Answer

A complete read-only development setup requires careful consideration of:

1. **What needs to be read-only**: Source code, configuration files
2. **What needs to be writable**: Data directories, temp files, dependencies
3. **Volume types**: Named volumes for persistent data, anonymous volumes for non-persistent but writable paths

**The Complete Command:**

```bash
docker run -d -p 3000:80 \
  -v "$(pwd):/app:ro" \              # Source code: read-only
  -v feedback-data:/app/feedback \   # User data: read-write, persistent
  -v /app/temp \                     # Temp files: read-write, ephemeral
  -v /app/node_modules \             # Dependencies: read-write, from image
  --rm \
  --name feedback-app feedback-node
```

## Question 5: What are the security and operational benefits of using read-only volumes in production?

### Answer

**Security Benefits:**

1. **Immutable Application Code**: Prevents runtime modification of application code, reducing attack surface
2. **Defense in Depth**: Even if an attacker gains container access, they cannot modify source files
3. **Prevents Accidental Corruption**: Application bugs cannot overwrite configuration or code
4. **Audit Trail**: Any code changes must happen through proper deployment channels, not runtime modification

**Operational Benefits:**

1. **Clear Separation of Concerns**: Read-only = code/config; Read-write = data
2. **Predictable Behavior**: Container always runs exactly the code from the image
3. **Easier Debugging**: You know source files haven't been modified during runtime
4. **Better Documentation**: Volume declarations explicitly show intent

**Production Considerations:**

In production, you often don't use bind mounts at all (code is in the image). But you can still use `:ro` on:
- Configuration volumes
- Secrets volumes
- Shared data that containers should only read

### Practical Guide

```bash
# ============================================
# SECURITY DEMONSTRATION
# ============================================

docker build -t feedback-node .

# Without :ro - container can modify files
docker run -d -p 3000:80 \
  -v "$(pwd):/app" \
  -v /app/node_modules \
  --rm \
  --name insecure feedback-node

# Simulate malicious modification
docker exec insecure sh -c 'echo "console.log(\"HACKED\");" >> /app/server.js'

# The "attack" succeeded
docker exec insecure grep "HACKED" /app/server.js
# console.log("HACKED"); ← File was modified!

# Worse: it's on your HOST machine too!
grep "HACKED" server.js
# console.log("HACKED"); ← Your source code is compromised!

# Revert
git checkout server.js 2>/dev/null || sed -i '' '/HACKED/d' server.js

docker stop insecure

# ============================================
# WITH :RO - ATTACK PREVENTED
# ============================================

docker run -d -p 3000:80 \
  -v "$(pwd):/app:ro" \
  -v feedback-data:/app/feedback \
  -v /app/temp \
  -v /app/node_modules \
  --rm \
  --name secure feedback-node

# Attempt malicious modification
docker exec secure sh -c 'echo "console.log(\"HACKED\");" >> /app/server.js' 2>&1
# sh: can't create /app/server.js: Read-only file system ✓

# Attempt to delete files
docker exec secure sh -c 'rm /app/package.json' 2>&1
# rm: can't remove '/app/package.json': Read-only file system ✓

# Attempt to create malicious file
docker exec secure sh -c 'echo "malware" > /app/backdoor.js' 2>&1
# sh: can't create /app/backdoor.js: Read-only file system ✓

# Source code is protected!
echo "Source code integrity verified ✓"

docker stop secure
docker volume rm feedback-data

# ============================================
# PRODUCTION PATTERN: Read-only config volume
# ============================================

# Create a config directory
mkdir -p config
echo '{"logLevel": "info", "maxConnections": 100}' > config/app-config.json

# Mount config as read-only
docker run -d \
  -v "$(pwd)/config:/app/config:ro" \
  --name config-demo alpine sleep 3600

# Container can READ config
docker exec config-demo cat /app/config/app-config.json
# {"logLevel": "info", "maxConnections": 100} ✓

# Container CANNOT modify config
docker exec config-demo sh -c 'echo "{}" > /app/config/app-config.json' 2>&1
# sh: can't create /app/config/app-config.json: Read-only file system ✓

docker stop config-demo && docker rm config-demo
rm -rf config
```

## Question 6: Summarize all the volume types, their access modes, and when to use each combination.

### Answer

| Volume Type | Syntax | Read/Write Default | Can Be :ro | Use Case |
|-------------|--------|-------------------|------------|----------|
| **Bind Mount** | `-v /host:/container` | Read-write | Yes | Development, config files |
| **Named Volume** | `-v name:/container` | Read-write | Yes | Persistent data |
| **Anonymous Volume** | `-v /container` | Read-write | No* | Protecting paths, temp data |

*Anonymous volumes don't typically need `:ro` as they're container-specific.

**Access Mode Combinations:**

| Configuration | Use Case |
|---------------|----------|
| Bind mount (rw) | Development with full bidirectional access |
| Bind mount (ro) | Source code in development, config in production |
| Named volume (rw) | User data, database storage |
| Named volume (ro) | Shared reference data across containers |
| Anonymous volume | Overriding bind mount paths, ephemeral storage |

### Practical Guide

```bash
docker build -t feedback-node .

# ============================================
# ALL VOLUME TYPES AND ACCESS MODES
# ============================================

# Create a named volume for shared config (will make it read-only)
docker volume create shared-config
docker run --rm -v shared-config:/data alpine sh -c 'echo "shared settings" > /data/config.txt'

# The comprehensive example
docker run -d -p 3000:80 \
  -v "$(pwd):/app:ro" \
  -v feedback-data:/app/feedback \
  -v shared-config:/app/shared-config:ro \
  -v /app/temp \
  -v /app/node_modules \
  --rm \
  --name complete-demo feedback-node

# ============================================
# VERIFY ALL COMBINATIONS
# ============================================

echo "=== 1. Bind Mount (Read-Only) ==="
docker exec complete-demo sh -c 'cat /app/server.js | head -1'
# First line of server.js (can read) ✓
docker exec complete-demo sh -c 'echo "x" >> /app/server.js' 2>&1
# Read-only file system (can't write) ✓

echo ""
echo "=== 2. Named Volume (Read-Write) ==="
docker exec complete-demo sh -c 'echo "data" > /app/feedback/test.txt'
# Success (can write) ✓
docker exec complete-demo cat /app/feedback/test.txt
# data (can read) ✓

echo ""
echo "=== 3. Named Volume (Read-Only) ==="
docker exec complete-demo cat /app/shared-config/config.txt
# shared settings (can read) ✓
docker exec complete-demo sh -c 'echo "x" > /app/shared-config/new.txt' 2>&1
# Read-only file system (can't write) ✓

echo ""
echo "=== 4. Anonymous Volume (Temp) ==="
docker exec complete-demo sh -c 'echo "temp" > /app/temp/file.txt'
# Success (can write) ✓
docker exec complete-demo cat /app/temp/file.txt
# temp (can read) ✓

echo ""
echo "=== 5. Anonymous Volume (node_modules) ==="
docker exec complete-demo ls /app/node_modules | head -1
# Package name (can read) ✓

# ============================================
# ACCESS SUMMARY TABLE
# ============================================

echo ""
echo "╔═══════════════════════════════════════════════════════════════╗"
echo "║  PATH              │ TYPE          │ ACCESS      │ PERSISTS  ║"
echo "╠═══════════════════════════════════════════════════════════════╣"
echo "║  /app              │ Bind mount    │ Read-only   │ N/A       ║"
echo "║  /app/feedback     │ Named volume  │ Read-write  │ Yes       ║"
echo "║  /app/shared-config│ Named volume  │ Read-only   │ Yes       ║"
echo "║  /app/temp         │ Anon volume   │ Read-write  │ No        ║"
echo "║  /app/node_modules │ Anon volume   │ Read-write  │ No        ║"
echo "╚═══════════════════════════════════════════════════════════════╝"

docker volume rm feedback-data shared-config
```

ACCESS MODES:
  (default)  → Read-write (container can read and write)
  :ro        → Read-only (container can only read)

PERSISTENCE:
  Bind mount        → Files on host (always persist)
  Named volume      → Docker-managed (persist until deleted)
  Anonymous volume  → Deleted with container (--rm)

DECISION TREE:

  Need container to write? ─── No ──→ Use :ro
           │
          Yes
           │
           ▼
  Need data to persist? ─── No ──→ Anonymous volume
           │
          Yes
           │
           ▼
  Need to edit from host? ─── Yes ──→ Bind mount (rw)
           │
           No
           │
           ▼
        Named volume

DEVELOPMENT PATTERN:
  docker run \
    -v "$(pwd):/app:ro" \           # Source code (protected)
    -v app-data:/app/data \         # User data (persistent)
    -v /app/temp \                  # Temp files (ephemeral)
    -v /app/node_modules \          # Deps (from image)
    image

PRODUCTION PATTERN:
  docker run \
    -v app-data:/app/data \         # User data (persistent)
    -v "$(pwd)/config:/app/config:ro" \ # Config (protected)
    image
    # No source code bind mount - code is in the image
```

┌──────────────────────────────────────────────────────────────────────────┐
│                    READ-ONLY VOLUMES — SUMMARY                           │
├──────────────────────────────────────────────────────────────────────────┤
│                                                                          │
│  SYNTAX:                                                                 │
│    -v "/host/path:/container/path:ro"                                    │
│                                    ^^                                    │
│                                    └── Read-only flag                   │
│                                                                          │
│  PURPOSE:                                                                │
│    • Prevent container from modifying source code                        │
│    • Security: reduce attack surface                                     │
│    • Clarity: explicit intent about write permissions                    │
│                                                                          │
│  THE CHALLENGE:                                                          │
│    :ro applies to ALL subdirectories of the mount                        │
│    Some subdirectories need to be writable                               │
│                                                                          │
│  THE SOLUTION:                                                           │
│    Add separate volumes for writable subdirectories                      │
│    Longer (more specific) paths override shorter paths                   │
│                                                                          │
│  COMPLETE COMMAND:                                                       │
│    docker run -d -p 3000:80 \                                            │
│      -v "$(pwd):/app:ro" \              # Source: read-only             │
│      -v feedback-data:/app/feedback \   # Data: read-write, persistent  │
│      -v /app/temp \                     # Temp: read-write, ephemeral   │
│      -v /app/node_modules \             # Deps: read-write              │
│      --rm --name app image                                               │
│                                                                          │
│  IMPORTANT:                                                              │
│    • Specify override volumes in docker run, not Dockerfile              │
│    • :ro only restricts container, not host                              │
│    • Use for source code, configs, shared reference data                 │
│                                                                          │
│  SECURITY BENEFIT:                                                       │
│    Without :ro → Attacker can modify source files                        │
│    With :ro    → "Read-only file system" error, attack prevented        │
│                                                                          │
└──────────────────────────────────────────────────────────────────────────┘
```
