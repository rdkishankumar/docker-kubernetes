## Question 1: Walk through the process of creating a Dockerfile for a Node.js application. Explain each instruction and why it's ordered that way.

### Answer

A Dockerfile for a Node.js application follows a specific sequence designed for **build efficiency** through layer caching:

1. **FROM** — Sets the base image with the Node.js runtime
2. **WORKDIR** — Establishes a working directory inside the container
3. **COPY package.json** — Copies only the dependency manifest first
4. **RUN npm install** — Installs dependencies (cached unless package.json changes)
5. **COPY . .** — Copies the remaining application code
6. **EXPOSE** — Documents the port the app listens on
7. **CMD** — Defines the default command to run when a container starts

The **critical ordering detail**: We copy `package.json` and run `npm install` *before* copying the rest of the code. This way, Docker caches the dependency installation layer. If only source code changes (not dependencies), Docker reuses the cached `npm install` layer, making rebuilds significantly faster.

### Practical Guide

```dockerfile
# Dockerfile
FROM node:14

# Set working directory — all subsequent commands run relative to this
WORKDIR /app

# Copy dependency manifest first (layer caching optimization)
COPY package.json .

# Install dependencies — this layer is cached until package.json changes
RUN npm install

# Copy remaining application source code
COPY . .

# Document the port the application uses internally
EXPOSE 80

# Command to execute when a container starts
CMD ["node", "server.js"]
```

```json
// package.json
{
  "name": "feedback-app",
  "version": "1.0.0",
  "dependencies": {
    "express": "^4.18.2",
    "body-parser": "^1.20.2"
  }
}
```

```javascript
// server.js
const express = require('express');
const fs = require('fs');
const path = require('path');
const bodyParser = require('body-parser');

const app = express();
app.use(bodyParser.urlencoded({ extended: true }));

const tempDir = path.join(__dirname, 'temp');
const feedbackDir = path.join(__dirname, 'feedback');

// Ensure directories exist
[tempDir, feedbackDir].forEach(dir => {
  if (!fs.existsSync(dir)) fs.mkdirSync(dir, { recursive: true });
});

app.get('/', (req, res) => {
  res.send(`
    <h1>Feedback App</h1>
    <form action="/submit" method="POST">
      <input name="title" placeholder="Title (one word, no special chars)" />
      <textarea name="text" placeholder="Your feedback"></textarea>
      <button type="submit">Save</button>
    </form>
  `);
});

app.post('/submit', (req, res) => {
  const { title, text } = req.body;
  const fileName = title.toLowerCase() + '.txt';
  const finalPath = path.join(feedbackDir, fileName);
  const tempPath = path.join(tempDir, fileName);

  if (fs.existsSync(finalPath)) {
    return res.send('<h1>Exists already</h1><a href="/">Go back</a>');
  }

  // Write to temp first, then move to final location
  fs.writeFileSync(tempPath, text);
  fs.copyFileSync(tempPath, finalPath);
  fs.unlinkSync(tempPath);

  res.send('<h1>Saved!</h1><a href="/">Go back</a>');
});

// Serve feedback files
app.get('/feedback/:file', (req, res) => {
  const filePath = path.join(feedbackDir, req.params.file);
  if (fs.existsSync(filePath)) {
    res.send(fs.readFileSync(filePath, 'utf8'));
  } else {
    res.status(404).send('Not found');
  }
});

app.listen(80, () => console.log('Listening on port 80'));
```

## Question 2: Explain the Docker build and run commands, including the flags used and what each one does.

### Answer

**Building the image:**
```bash
docker build -t feedback-node .
```
- `docker build` — Creates an image from a Dockerfile
- `-t feedback-node` — Tags the image with the name `feedback-node` and implicitly assigns the tag `latest`
- `.` — Build context; tells Docker where to find the Dockerfile and files to copy

**Running the container:**
```bash
docker run -d -p 3000:80 --rm --name feedback-app feedback-node
```
- `-d` — **Detached mode**; runs the container in the background so the terminal remains usable
- `-p 3000:80` — **Port publishing**; maps host port 3000 to container's internal port 80
- `--rm` — **Auto-remove**; automatically removes the container when it stops
- `--name feedback-app` — Assigns a human-readable name to the container
- `feedback-node` — The image to base the container on

### Practical Guide

```bash
# Step 1: Build the image
docker build -t feedback-node .

# Verify the image was created
docker images feedback-node
# REPOSITORY      TAG       IMAGE ID       CREATED          SIZE
# feedback-node   latest    a1b2c3d4e5f6   10 seconds ago   945MB

# Step 2: Run the container
docker run -d -p 3000:80 --rm --name feedback-app feedback-node

# Verify the container is running
docker ps
# CONTAINER ID   IMAGE           PORTS                  NAMES
# f1e2d3c4b5a6   feedback-node   0.0.0.0:3000->80/tcp   feedback-app

# Step 3: Test the application
# Open browser: http://localhost:3000
# Or test via curl:
curl http://localhost:3000

# Submit feedback
curl -X POST -d "title=awesome&text=This is awesome" http://localhost:3000/submit

# View stored feedback
curl http://localhost:3000/feedback/awesome.txt
# Output: This is awesome

# Step 4: Stop the container (--rm means it's automatically removed)
docker stop feedback-app

# Confirm it's gone
docker ps -a --filter name=feedback-app
# No results — container was auto-removed
```

## Question 3: Why can't you see files created inside a Docker container on your host machine? Explain Docker's isolated file system.

### Answer

Docker containers have a **completely isolated file system**. When you build an image:

1. The Dockerfile's `COPY` instruction takes a **snapshot** of your local files at that moment
2. This snapshot is stored inside the image's own file system
3. There is **no ongoing connection** between the host folder and the image/container file system

This means:
- Files created inside the container **do not appear** on the host machine
- Files changed on the host machine **are not reflected** in the running container
- The isolation is **intentional** — it would be a security risk if containers could arbitrarily write to your host file system

This is the same principle that explains why editing source code locally requires rebuilding the image — the container only has the snapshot that was copied in at build time.

### Practical Guide

```bash
# Build and run the app
docker build -t feedback-node .
docker run -d -p 3000:80 --name feedback-app feedback-node

# Create feedback inside the container
curl -X POST -d "title=dockertest&text=Hello from container" \
  http://localhost:3000/submit

# Try to find the file on your HOST machine
ls ./feedback/
# Empty or contains no dockertest.txt — file does NOT exist on host

# But it DOES exist inside the container
docker exec feedback-app ls /app/feedback/
# dockertest.txt

docker exec feedback-app cat /app/feedback/dockertest.txt
# Hello from container

# ---- Demonstrate the reverse: host changes not reflected in container ----

# Create a file on the host
echo "host file" > ./feedback/hostfile.txt

# Check inside the container — file is NOT there
docker exec feedback-app ls /app/feedback/
# Only dockertest.txt — no hostfile.txt

# ---- Prove the snapshot nature ----
# Modify server.js on the host
echo "// modified" >> ./server.js

# The running container still uses the OLD code
docker exec feedback-app head -1 /app/server.js
# Original first line — no modification visible

# To get the change into a container, you must rebuild
docker stop feedback-app && docker rm feedback-app
docker build -t feedback-node .
docker run -d -p 3000:80 --name feedback-app feedback-node

# Clean up host test file
rm ./feedback/hostfile.txt
```

## Question 4: What happens to data stored inside a container when the container is stopped and removed? Demonstrate the problem.

### Answer

Data stored inside a container's writable layer is **ephemeral**. When a container is removed (`docker rm` or via `--rm` flag), its writable layer is destroyed and all data within it is permanently lost.

This is a fundamental problem for any application that generates data that should persist, because:
- Deploying a new version requires replacing the container
- The `--rm` flag (common in production) auto-removes stopped containers
- Even without `--rm`, `docker stop` + `docker start` preserves data, but `docker rm` destroys it

### Practical Guide

```bash
# ---- Scenario 1: Container with --rm flag ----
docker build -t feedback-node .
docker run -d -p 3000:80 --rm --name feedback-app feedback-node

# Store feedback
curl -X POST -d "title=important&text=Critical data" http://localhost:3000/submit

# Verify it exists
curl http://localhost:3000/feedback/important.txt
# Output: Critical data

# Stop the container (--rm auto-removes it)
docker stop feedback-app

# Start a new container
docker run -d -p 3000:80 --rm --name feedback-app feedback-node

# Try to access the feedback
curl http://localhost:3000/feedback/important.txt
# 404 Not found — DATA IS GONE!

docker stop feedback-app

# ---- Scenario 2: Container without --rm (stop vs rm) ----
docker run -d -p 3000:80 --name feedback-app feedback-node

# Store feedback
curl -X POST -d "title=survive&text=Will this survive?" http://localhost:3000/submit

# Stop the container (NOT removed)
docker stop feedback-app

# Restart the SAME container
docker start feedback-app

# Data survives a stop/start cycle
curl http://localhost:3000/feedback/survive.txt
# Output: Will this survive? — DATA SURVIVES!

# But if we REMOVE the container...
docker stop feedback-app
docker rm feedback-app

# Start a fresh container
docker run -d -p 3000:80 --name feedback-app feedback-node

curl http://localhost:3000/feedback/survive.txt
# 404 Not found — DATA IS GONE after docker rm!

docker stop feedback-app && docker rm feedback-app
```

## Question 5: In the demo application, feedback is first written to a temp file and then copied to the final location. Why is this pattern used, and how does it relate to Docker's file system?

### Answer

The **temp-then-copy pattern** is a common data integrity practice:

1. Write data to a temporary location first
2. Validate or check conditions (e.g., does the file already exist in the final location?)
3. Only copy to the final destination if conditions are met
4. Clean up the temporary file

In the demo app, this prevents **overwriting existing feedback** — if a file with the same title already exists in the `/feedback` folder, the operation is rejected and the temp file is discarded.

From a Docker perspective, both the temp file and the final file exist in the **container's writable layer**. Neither the temp directory nor the feedback directory on the host machine is involved. All file operations happen within the container's isolated file system.

### Practical Guide

```javascript
// The pattern in the Node.js application
app.post('/submit', (req, res) => {
  const { title, text } = req.body;
  const fileName = title.toLowerCase() + '.txt';
  const tempPath = path.join('/app/temp', fileName);
  const finalPath = path.join('/app/feedback', fileName);

  // Step 1: Check if file already exists in final location
  if (fs.existsSync(finalPath)) {
    return res.send('<h1>Exists already</h1>');
  }

  // Step 2: Write to temp location first
  fs.writeFileSync(tempPath, text);

  // Step 3: Copy to final location
  fs.copyFileSync(tempPath, finalPath);

  // Step 4: Clean up temp file
  fs.unlinkSync(tempPath);

  res.send('<h1>Saved!</h1>');
});
```

```bash
# Demonstrate the duplicate prevention
docker build -t feedback-node .
docker run -d -p 3000:80 --rm --name feedback-app feedback-node

# First submission — succeeds
curl -X POST -d "title=awesome&text=This is awesome" http://localhost:3000/submit
# Response: Saved!

# Second submission with same title — rejected
curl -X POST -d "title=awesome&text=Different text" http://localhost:3000/submit
# Response: Exists already

# Original content is preserved
curl http://localhost:3000/feedback/awesome.txt
# Output: This is awesome (not "Different text")

# Verify temp directory is clean (no leftover files)
docker exec feedback-app ls /app/temp/
# Empty — temp files are properly cleaned up

docker stop feedback-app
```

## Question 6: What is the significance of the `--rm` flag, and when should you use or avoid it?

### Answer

The `--rm` flag tells Docker to **automatically remove the container when it stops**. This means the container's writable layer (and all data in it) is destroyed immediately upon stopping.

**Use `--rm` when:**
- Running temporary or stateless containers
- Data persistence is handled by volumes
- You want to avoid accumulating stopped containers
- CI/CD pipelines and one-off tasks

**Avoid `--rm` when:**
- You need to inspect logs or the file system of a stopped container for debugging
- You intend to restart the same container with `docker start`
- No volume is configured and you still need container data temporarily

### Practical Guide

```bash
# ---- With --rm: Container disappears on stop ----
docker run -d -p 3000:80 --rm --name app-rm feedback-node
docker stop app-rm
docker ps -a --filter name=app-rm
# No results — container is gone

# ---- Without --rm: Container persists after stop ----
docker run -d -p 3000:80 --name app-persist feedback-node
docker stop app-persist
docker ps -a --filter name=app-persist
# CONTAINER ID   IMAGE           STATUS                    NAMES
# abc123         feedback-node   Exited (0) 2 seconds ago  app-persist

# You can inspect it
docker logs app-persist
docker exec app-persist ls /app/feedback/  # Error: container not running

# Restart it — data inside the writable layer is preserved
docker start app-persist
docker ps --filter name=app-persist
# Container is running again with same data

# Clean up manually when done
docker stop app-persist
docker rm app-persist

# ---- Best practice: Use --rm WITH volumes ----
docker run -d -p 3000:80 --rm \
  -v feedback-data:/app/feedback \
  --name app-best feedback-node

# Data is in the volume, so --rm is safe
# Container cleanup is automatic, data persists in volume
docker stop app-best
docker volume ls  # feedback-data still exists
```
