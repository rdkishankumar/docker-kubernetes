

# Docker Compose File Setup — Writing Your First `docker-compose.yml`

---

## 📘 Detailed Notes

### 1. Getting Started with Docker Compose

The starting point is creating a `docker-compose.yml` file in your **project root folder** — the folder that contains all your service subdirectories (backend, frontend, etc.).

```
my-project/                    ← docker-compose.yml goes HERE
├── docker-compose.yml         ← The compose file
├── backend/
│   ├── Dockerfile             ← Still needed! Compose doesn't replace this
│   ├── package.json
│   └── app.js
├── frontend/
│   ├── Dockerfile             ← Still needed!
│   ├── package.json
│   └── src/
└── .env
```

### 2. File Extension

The compose file can use either extension:
- `docker-compose.yml` (3 characters — most common)
- `docker-compose.yaml` (4 characters — also valid)

Both are identical in functionality. Convention favors `.yml`.

### 3. YAML Format Fundamentals

YAML (YAML Ain't Markup Language) uses **indentation** to express hierarchy and dependencies between configuration options:

```yaml
# Parent-child relationship via indentation
parent:
  child1: value1        # 2-space indent = child of parent
  child2: value2        # Same level = sibling of child1
    grandchild: value3  # 4-space indent = child of child2
```

**Critical YAML rules:**
- Indentation must use **spaces** (NOT tabs)
- Consistent indentation depth matters (typically 2 spaces per level)
- Key names are **case-sensitive** (`version` ≠ `Version` ≠ `VERSION`)
- Colons separate keys from values
- Lists use dashes (`-`)

### 4. The `version` Key

```yaml
version: "3.8"
```

| Aspect | Detail |
|---|---|
| **What it is** | The Docker Compose specification version, NOT your app version |
| **Why it matters** | Determines which features/syntax are available in the file |
| **Where to find versions** | `docs.docker.com/compose/compose-file` |
| **Current recommendation** | Use the latest stable version (3.8+ at time of recording) |
| **Forward compatibility** | New versions add features; older syntax generally still works |

**Note:** In very recent versions of Docker Compose (V2+), the `version` key is actually **optional** and considered legacy. Compose auto-detects the format. But including it ensures compatibility and clarity.

### 5. The `services` Key — The Heart of Docker Compose

```yaml
version: "3.8"

services:              # REQUIRED — defines all containers
  mongodb:             # Service 1 = Container 1 (name of your choice)
    # ... configuration for mongodb container

  backend:             # Service 2 = Container 2
    # ... configuration for backend container

  frontend:            # Service 3 = Container 3
    # ... configuration for frontend container
```

**Key points:**
- `services` is the **most important** and **required** top-level key
- Each child under `services` defines one container (called a "service")
- **Service names are your choice** — they become DNS hostnames on the Docker network
- All services must be at the **same indentation level** (siblings)
- Configuration for each service is **nested below** its name (indented further)

### 6. Indentation Structure

```yaml
version: "3.8"           # Level 0 — top-level key
                          #
services:                 # Level 0 — top-level key
  mongodb:                # Level 1 (2 spaces) — service name
    image: mongo          # Level 2 (4 spaces) — service configuration
    volumes:              # Level 2 (4 spaces) — service configuration
      - data:/data/db     # Level 3 (6 spaces) — list item under volumes
                          #
  backend:                # Level 1 (2 spaces) — another service
    build: ./backend      # Level 2 (4 spaces) — its configuration
    ports:                # Level 2 (4 spaces)
      - "3000:3000"       # Level 3 (6 spaces)
    environment:          # Level 2 (4 spaces)
      - NODE_ENV=dev      # Level 3 (6 spaces)
                          #
  frontend:               # Level 1 (2 spaces) — another service
    build: ./frontend     # Level 2 (4 spaces)
    ports:                # Level 2 (4 spaces)
      - "3001:3000"       # Level 3 (6 spaces)
                          #
volumes:                  # Level 0 — top-level key
  data:                   # Level 1 (2 spaces) — volume declaration
```

### 7. VS Code Docker Extension

Install the **Docker extension** for Visual Studio Code to get:
- **Auto-completion** for compose file keys
- Syntax highlighting for YAML
- Validation of compose file structure
- IntelliSense for available options
- Hover documentation for keys

This significantly reduces typos and helps discover available configuration options.

### 8. Service Names = Container Identifiers

```yaml
services:
  mongodb:        # This name becomes:
                  #   1. DNS hostname on the Docker network
                  #   2. Prefix for container name (projectname_mongodb_1)
                  #   3. Reference in depends_on
                  #   4. Target for docker-compose logs mongodb
```

The service name you choose has real implications:
- Other services reference it as a hostname: `mongodb://mongodb:27017`
- Compose commands target it: `docker-compose logs backend`
- It appears in `docker-compose ps` output

### 9. Compose File Reference

The complete reference is at: `docs.docker.com/compose/compose-file`

**Reality check:** The reference lists hundreds of configuration options. For most applications, you only need a small subset:
- `image` or `build`
- `ports`
- `volumes`
- `environment` or `env_file`
- `depends_on`
- `networks` (often not needed — Compose auto-creates one)

## 🎯 Interview Questions & Answers

### Q1: Where do you place the `docker-compose.yml` file and why?

**Answer:**
The `docker-compose.yml` file is placed in the **project root directory** — the top-level folder that contains all your service subdirectories. This is because:

1. Compose uses the file's location as the **build context reference point** — relative paths like `./backend` in `build:` are resolved from the compose file's directory
2. The directory name becomes the **project name** by default, which prefixes container names, networks, and volumes
3. It provides a single entry point for the entire multi-container application
4. Running `docker-compose up` looks for the file in the current working directory

```
my-project/                     ← Run docker-compose commands HERE
├── docker-compose.yml          ← Compose file at project root
├── backend/
│   └── Dockerfile
├── frontend/
│   └── Dockerfile
└── .env
```

You can also specify a different file location with `-f`: `docker-compose -f path/to/compose.yml up`

---

### Q2: What does the `version` key in a Docker Compose file specify?

**Answer:**
The `version` key specifies the **Docker Compose file format version** (the specification version), NOT the version of your application. It determines which configuration features and syntax are available in the file.

```yaml
version: "3.8"    # Compose specification version
```

Different versions support different features. For example:
- Version 2.x introduced `depends_on`, `networks`
- Version 3.x added Swarm deployment configurations
- Version 3.8 added additional options

**Important note:** In Docker Compose V2 (the newer Go-based implementation), the `version` key is **optional** and treated as informational. The compose tool auto-detects the format. However, including it is still good practice for clarity and backward compatibility.

You can find all versions and their supported features at `docs.docker.com/compose/compose-file`.

### Q3: Why is indentation critical in a `docker-compose.yml` file?

**Answer:**
YAML uses **indentation to express hierarchy** — parent-child relationships between configuration keys. Incorrect indentation changes the meaning of the file or causes parsing errors.

```yaml
# CORRECT: ports belongs to backend service
services:
  backend:
    ports:
      - "3000:3000"

# WRONG: ports is at wrong level — parsed as a new service or top-level key
services:
  backend:
  ports:              # ← This is NOT under backend anymore!
    - "3000:3000"
```

Rules:
- Must use **spaces** (tabs cause errors)
- Typically **2 spaces** per indentation level
- **Consistent** indentation required throughout the file
- Children are indented **relative to their parent**
- Siblings must be at the **same indentation level**

### Q4: What are "services" in Docker Compose and how do they relate to containers?

**Answer:**
In Docker Compose, a "service" is a **container definition**. Each entry under the `services:` key describes one container — its image, ports, volumes, environment variables, and networking.

```yaml
services:
  mongodb:        # Service = 1 container running MongoDB
  backend:        # Service = 1 container running the Node.js API
  frontend:       # Service = 1 container running the React frontend
```

The service name:
- Acts as a **DNS hostname** on the Docker network (e.g., `mongodb://mongodb:27017`)
- Becomes part of the **container name** (e.g., `projectname-mongodb-1`)
- Is used to **target specific services** in commands (e.g., `docker-compose logs backend`)
- Is referenced in **`depends_on`** for startup ordering

Services can also be **scaled** to run multiple instances: `docker-compose up --scale backend=3` creates 3 backend containers.

### Q5: Do you still need Dockerfiles when using Docker Compose?

**Answer:**
**Yes, absolutely.** Docker Compose does NOT replace Dockerfiles. They serve different purposes:

| Concern | Dockerfile | Docker Compose |
|---|---|---|
| **Build instructions** | ✅ Defines how to build the image | References Dockerfile via `build:` |
| **Container orchestration** | ❌ Not its purpose | ✅ Manages multi-container setup |
| **Base image, dependencies** | ✅ `FROM`, `RUN`, `COPY` | ❌ Not its purpose |
| **Ports, volumes, env vars** | Partially (`EXPOSE`, `ENV`) | ✅ Full runtime configuration |
| **Networks, dependencies** | ❌ Not its purpose | ✅ `networks:`, `depends_on:` |

The compose file **references** Dockerfiles:
```yaml
services:
  backend:
    build: ./backend        # ← Points to directory containing Dockerfile
```

For official images (like MongoDB), no Dockerfile is needed — Compose pulls the pre-built image directly:
```yaml
services:
  mongodb:
    image: mongo            # ← Uses official image, no Dockerfile
```

### Q6: What happens if you misspell a key in the compose file (e.g., `Services` instead of `services`)?

**Answer:**
YAML keys in Docker Compose are **case-sensitive**. Misspelling or using wrong casing causes the key to be **ignored silently** or triggers an error when Compose tries to parse the file.

```yaml
# ❌ WRONG — "Services" with capital S is not recognized
Services:
  backend:
    build: .

# ❌ WRONG — "Version" not recognized
Version: "3.8"

# ✅ CORRECT — all lowercase
version: "3.8"
services:
  backend:
    build: .
```

This is why the **Docker extension for VS Code** is valuable — it provides auto-completion and validation, catching these errors before you run `docker-compose up`.

### Q7: How do service names in Docker Compose affect networking?

**Answer:**
Service names have a direct impact on networking because they become **DNS hostnames** on the automatically created Docker network. When Compose starts services, it creates a default network and registers each service name as a resolvable hostname.

```yaml
services:
  mongodb:                # Hostname: "mongodb"
    image: mongo

  backend:                # Hostname: "backend"
    build: ./backend
    environment:
      # "mongodb" resolves to the mongodb container's IP
      - MONGO_URL=mongodb://mongodb:27017/mydb

  frontend:               # Hostname: "frontend"
    build: ./frontend
    environment:
      # "backend" resolves to the backend container's IP
      - API_URL=http://backend:3000
```

This is identical to using `--name` with `docker run` on a custom Docker network, but Compose handles it automatically. You never need to look up IP addresses or create networks manually.

### Q8: Can you choose any name for services in Docker Compose?

**Answer:**
Yes, service names are **your choice**, but you should follow these guidelines:

**Valid names:**
- Must contain only lowercase letters, numbers, hyphens, and underscores
- Should be descriptive of the service's purpose
- Will be used as DNS hostnames, so keep them simple

```yaml
# ✅ Good naming
services:
  mongodb:
  backend:
  frontend:
  redis-cache:
  message_queue:

# ❌ Avoid
services:
  My Backend:        # Spaces not allowed
  MONGODB:           # Convention is lowercase
  a:                 # Not descriptive
```

**Important:** If you change a service name, you must update all references to it — `depends_on`, environment variables with hostnames, and any application code using the name for network connections.

### Q9: What is the relationship between the compose file version and Docker Engine version?

**Answer:**
The compose file version determines which features are available, and certain versions require a minimum Docker Engine version:

| Compose File Version | Minimum Docker Engine |
|---|---|
| 3.8 | 19.03.0+ |
| 3.7 | 18.06.0+ |
| 3.0 | 1.13.0+ |
| 2.4 | 17.12.0+ |

Specifying a version higher than what your Docker Engine supports will result in errors. Specifying a lower version means you can't use newer features.

**Modern approach:** Docker Compose V2 (the Go-based `docker compose` command, without the hyphen) treats the version as **optional and informational**. It supports all features regardless of the version specified. However, including the version is still recommended for documentation and compatibility with older Compose implementations.

### Q10: Walk through the minimal structure of a Docker Compose file for a three-service application.

**Answer:**

```yaml
# Step 1: Specify compose file version
version: "3.8"

# Step 2: Define services (containers)
services:
  # Service 1: Database (uses pre-built official image)
  mongodb:
    image: mongo
    volumes:
      - mongodata:/data/db

  # Service 2: Backend API (builds from Dockerfile)
  backend:
    build: ./backend
    ports:
      - "3000:3000"
    environment:
      - MONGO_URL=mongodb://mongodb:27017/mydb
    depends_on:
      - mongodb

  # Service 3: Frontend (builds from Dockerfile)
  frontend:
    build: ./frontend
    ports:
      - "3001:3000"
    depends_on:
      - backend

# Step 3: Declare named volumes
volumes:
  mongodata:
```

**What this defines:**
- 3 services (containers): `mongodb`, `backend`, `frontend`
- `mongodb` uses an official image — no Dockerfile
- `backend` and `frontend` build from Dockerfiles in their respective directories
- Named volume `mongodata` persists database data
- `depends_on` ensures startup order: mongodb → backend → frontend
- Default network is auto-created — all services can communicate by name
- Only `backend` and `frontend` publish ports (accessible from host)
- `mongodb` has no published ports (only accessed by `backend` within the network)

### docker-compose.yml (Fully Annotated)

```yaml
# ═══════════════════════════════════════════════════════════
# DOCKER COMPOSE FILE — Multi-Service Application
# ═══════════════════════════════════════════════════════════

# Compose specification version
# Determines available features and syntax
# Reference: docs.docker.com/compose/compose-file
version: "3.8"

# ─── SERVICES ───
# The HEART of the compose file
# Each entry = one container definition
# Service names become DNS hostnames on the auto-created network
services:

  # ════════════════════════════════════════
  # SERVICE 1: MongoDB Database
  # ════════════════════════════════════════
  # Equivalent to:
  #   docker run -d --name mongodb
  #     --network auto-created-net
  #     -v mongodata:/data/db
  #     -e MONGO_INITDB_ROOT_USERNAME=admin
  #     -e MONGO_INITDB_ROOT_PASSWORD=secret
  #     mongo
  mongodb:
    image: mongo                    # Official image — no Dockerfile needed
    volumes:
      - mongodata:/data/db          # Named volume for data persistence
    environment:                    # Environment variables for MongoDB
      MONGO_INITDB_ROOT_USERNAME: admin
      MONGO_INITDB_ROOT_PASSWORD: secret
    # NOTE: No ports published!
    # Only the backend service connects to MongoDB
    # Inter-container communication doesn't need -p

  # ════════════════════════════════════════
  # SERVICE 2: Node.js Backend API
  # ════════════════════════════════════════
  # Equivalent to:
  #   docker build -t backend ./backend
  #   docker run -d --name backend --rm
  #     --network auto-created-net
  #     -p 3000:3000
  #     -v logs:/app/logs
  #     -v ./backend:/app:ro
  #     -v /app/node_modules
  #     -e MONGO_URL=mongodb://admin:secret@mongodb:27017/mydb?authSource=admin
  #     backend
  backend:
    build: ./backend                # Build from ./backend/Dockerfile
    ports:
      - "3000:3000"                 # Published — accessed from browser/Postman
    volumes:
      - logs:/app/logs              # Named volume for log persistence
      - ./backend:/app:ro           # Bind mount for live code updates (read-only)
      - /app/node_modules           # Anonymous volume — protect node_modules
    environment:
      # "mongodb" = service name above = DNS hostname on the network
      - MONGO_URL=mongodb://admin:secret@mongodb:27017/mydb?authSource=admin
      - NODE_ENV=development
    depends_on:
      - mongodb                     # Start mongodb BEFORE backend

  # ════════════════════════════════════════
  # SERVICE 3: React Frontend
  # ════════════════════════════════════════
  # Equivalent to:
  #   docker build -t frontend ./frontend
  #   docker run -d --name frontend --rm
  #     --network auto-created-net
  #     -p 3001:3000
  #     -v ./frontend/src:/app/src:ro
  #     frontend
  frontend:
    build: ./frontend               # Build from ./frontend/Dockerfile
    ports:
      - "3001:3000"                 # Map host 3001 to container 3000
    volumes:
      - ./frontend/src:/app/src:ro  # Bind mount for live frontend code updates
    depends_on:
      - backend                     # Start backend BEFORE frontend
    stdin_open: true                # -i flag (needed for React dev server)
    tty: true                       # -t flag (needed for React dev server)

# ─── NAMED VOLUMES ───
# Must declare all named volumes used by services
# Anonymous volumes don't need declaration
volumes:
  mongodata:                        # MongoDB data persistence
  logs:                             # Backend application logs

# ─── NETWORKS ───
# OPTIONAL — Compose auto-creates a default network
# All services are on this default network and can reference each other by name
# Uncomment below only if you need custom network configuration:
# networks:
#   app-network:
#     driver: bridge
```

### backend/app.js

```javascript
const express = require('express');
const bodyParser = require('body-parser');
const mongoose = require('mongoose');
const fs = require('fs');
const path = require('path');

const app = express();
app.use(bodyParser.json());

// Enable CORS for frontend
app.use((req, res, next) => {
  res.setHeader('Access-Control-Allow-Origin', '*');
  res.setHeader('Access-Control-Allow-Methods', 'GET, POST, DELETE');
  res.setHeader('Access-Control-Allow-Headers', 'Content-Type');
  next();
});

// ─── Database Connection ───
// "mongodb" = the service name from docker-compose.yml
// Compose's auto-created network resolves it to the container's IP
const MONGO_URL = process.env.MONGO_URL || 'mongodb://mongodb:27017/mydb';

mongoose.connect(MONGO_URL)
  .then(() => {
    console.log('✅ Connected to MongoDB');
    logEvent('Connected to MongoDB');
  })
  .catch(err => {
    console.error('❌ Connection failed:', err.message);
    process.exit(1);
  });

// ─── Logging ───
function logEvent(msg) {
  const dir = path.join(__dirname, 'logs');
  if (!fs.existsSync(dir)) fs.mkdirSync(dir, { recursive: true });
  fs.appendFileSync(path.join(dir, 'app.log'),
    `[${new Date().toISOString()}] ${msg}\n`);
}

// ─── Model ───
const Goal = mongoose.model('Goal', {
  text: { type: String, required: true },
  createdAt: { type: Date, default: Date.now }
});

// ─── Routes ───
app.get('/goals', async (req, res) => {
  const goals = await Goal.find();
  logEvent(`GET /goals — ${goals.length} goals`);
  res.json({ goals });
});

app.post('/goals', async (req, res) => {
  const { text } = req.body;
  if (!text) return res.status(400).json({ error: 'Text required' });
  const goal = new Goal({ text });
  await goal.save();
  logEvent(`POST /goals — "${text}"`);
  res.status(201).json({ message: 'Goal saved', goal });
});

app.delete('/goals/:id', async (req, res) => {
  await Goal.findByIdAndDelete(req.params.id);
  logEvent(`DELETE /goals/${req.params.id}`);
  res.json({ message: 'Goal deleted' });
});

app.get('/health', (req, res) => {
  const states = { 0: 'disconnected', 1: 'connected', 2: 'connecting', 3: 'disconnecting' };
  res.json({
    status: 'ok',
    database: states[mongoose.connection.readyState],
    env: process.env.NODE_ENV || 'not set'
  });
});

const PORT = process.env.PORT || 3000;
app.listen(PORT, () => {
  console.log(`🚀 Backend running on port ${PORT}`);
  logEvent(`Server started on port ${PORT}`);
});
```

### frontend/src/App.js

```javascript
import React, { useState, useEffect } from 'react';

function App() {
  const [goals, setGoals] = useState([]);
  const [text, setText] = useState('');

  // Backend is accessed via published port from the HOST
  // (not via Docker network — frontend runs in the browser)
  const API_URL = process.env.REACT_APP_API_URL || 'http://localhost:3000';

  useEffect(() => {
    fetch(`${API_URL}/goals`)
      .then(res => res.json())
      .then(data => setGoals(data.goals))
      .catch(err => console.error(err));
  }, [API_URL]);

  const addGoal = async () => {
    if (!text.trim()) return;
    const res = await fetch(`${API_URL}/goals`, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ text })
    });
    const data = await res.json();
    setGoals(prev => [...prev, data.goal]);
    setText('');
  };

  const deleteGoal = async (id) => {
    await fetch(`${API_URL}/goals/${id}`, { method: 'DELETE' });
    setGoals(prev => prev.filter(g => g._id !== id));
  };

  return (
    <div style={{ maxWidth: 600, margin: '50px auto', fontFamily: 'Arial' }}>
      <h1>Docker Compose Demo</h1>
      <div>
        <input
          value={text}
          onChange={e => setText(e.target.value)}
          placeholder="Enter a goal..."
          style={{ padding: 8, width: '70%' }}
        />
        <button onClick={addGoal} style={{ padding: 8, marginLeft: 8 }}>
          Add Goal
        </button>
      </div>
      <ul style={{ marginTop: 20 }}>
        {goals.map(goal => (
          <li key={goal._id} style={{ margin: '10px 0' }}>
            {goal.text}
            <button onClick={() => deleteGoal(goal._id)} style={{ marginLeft: 10 }}>
              ✕
            </button>
          </li>
        ))}
      </ul>
    </div>
  );
}

export default App;
```

## 🧠 Quick Reference Cheat Sheet

```
┌──────────────────────────────────────────────────────────────┐
│              DOCKER COMPOSE FILE BASICS                       │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  FILE: docker-compose.yml (or .yaml)                         │
│  LOCATION: Project root directory                            │
│  FORMAT: YAML (indentation-based, space-sensitive)           │
│                                                              │
├──────────────────────────────────────────────────────────────┤
│              MINIMAL FILE STRUCTURE                           │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  version: "3.8"          ← Compose spec version              │
│                                                              │
│  services:               ← REQUIRED — container definitions  │
│    service-name:         ← Your chosen name (= container)    │
│      image: or build:    ← Image source                      │
│      ports:              ← Port mapping                      │
│      volumes:            ← Data persistence                  │
│      environment:        ← Env vars                          │
│      depends_on:         ← Startup order                     │
│                                                              │
│  volumes:                ← Named volume declarations         │
│    volume-name:                                              │
│                                                              │
├──────────────────────────────────────────────────────────────┤
│              YAML INDENTATION RULES                          │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  • Use SPACES only (never tabs)                              │
│  • 2 spaces per level (convention)                           │
│  • Children indented under parents                           │
│  • Siblings at same indentation level                        │
│  • Case-sensitive keys (services ≠ Services)                 │
│                                                              │
│  version: "3.8"       ← Level 0                              │
│  services:             ← Level 0                              │
│    mongodb:            ← Level 1 (child of services)         │
│      image: mongo      ← Level 2 (child of mongodb)         │
│      volumes:          ← Level 2                              │
│        - data:/data/db ← Level 3 (list item)                │
│                                                              │
├──────────────────────────────────────────────────────────────┤
│              KEY REMINDERS                                   │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  ✅ Compose works WITH Dockerfiles (doesn't replace them)    │
│  ✅ Service names = DNS hostnames on auto-created network    │
│  ✅ Compose auto-creates a default network for all services  │
│  ✅ Named volumes must be declared at top level              │
│  ✅ VS Code Docker extension gives auto-completion           │
│  ✅ Version key = compose spec version, not your app version │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```
