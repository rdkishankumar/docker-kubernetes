

# Docker Compose — Introduction & Fundamentals

---

## 📘 Detailed Notes

### 1. What Is Docker Compose?

Docker Compose is a tool that replaces multiple `docker build` and `docker run` commands with **one configuration file** and **simple orchestration commands**. Instead of copying and pasting long Docker commands, you define your entire multi-container application in a single YAML file and manage it with one-line commands.

```
┌─────────────────────────────────────────────────────────────────┐
│                     WITHOUT DOCKER COMPOSE                       │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  docker network create my-net                                    │
│  docker run -d --name mongodb --network my-net -v data:/data/db  │
│    mongo                                                         │
│  docker build -t my-app .                                        │
│  docker run -d --name app --network my-net -p 3000:3000          │
│    -e MONGO_URL=mongodb://mongodb:27017/db                       │
│    -v logs:/app/logs -v $(pwd):/app:ro -v /app/node_modules      │
│    my-app                                                        │
│                                                                  │
│  → Multiple commands, easy to forget flags, error-prone          │
│                                                                  │
├─────────────────────────────────────────────────────────────────┤
│                     WITH DOCKER COMPOSE                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  docker-compose up -d        → Start everything                  │
│  docker-compose down         → Stop everything                   │
│                                                                  │
│  → One file, one command, reproducible, shareable                │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 2. What Docker Compose IS

| Capability | Description |
|---|---|
| **Configuration file** | Single YAML file defining all containers, networks, volumes |
| **Orchestration commands** | `docker-compose up` / `docker-compose down` |
| **Multi-container management** | Start, stop, rebuild all services at once |
| **Reproducible setup** | Share the file → anyone can replicate the environment |
| **Single-host tool** | Manages containers on one machine |
| **Works with single containers too** | Just shines more with multiple containers |

### 3. What Docker Compose is NOT

| Common Misconception | Reality |
|---|---|
| "Replaces Dockerfiles" | ❌ No — Compose **works with** Dockerfiles, doesn't replace them |
| "Replaces images/containers" | ❌ No — Compose creates and manages them, but they're still Docker images and containers |
| "For multi-host deployments" | ❌ No — Compose is for **single-host** management. Use Docker Swarm or Kubernetes for multi-host |
| "Only for production" | ❌ No — It's used heavily in development AND can be used beyond development |
| "A completely different tool" | ❌ No — It's a wrapper around standard Docker commands |

### 4. The Docker Compose File Structure

```yaml
version: "3.8"                    # Compose file version

services:                         # The HEART of the compose file
  service-name-1:                 # = Container 1
    image: mongo                  # Which image to use
    volumes:                      # Volume configuration
      - data:/data/db
    environment:                  # Environment variables
      - MONGO_INITDB_ROOT_USERNAME=admin
    networks:                     # Network assignment
      - my-network
    ports:                        # Port publishing
      - "27017:27017"

  service-name-2:                 # = Container 2
    build: ./app                  # Build from Dockerfile
    ports:
      - "3000:3000"
    volumes:
      - ./app:/app:ro
    environment:
      - DB_HOST=service-name-1
    depends_on:
      - service-name-1
    networks:
      - my-network

volumes:                          # Named volume declarations
  data:

networks:                         # Network declarations
  my-network:
```

### 5. Core Concepts

#### Services = Containers
The term "service" in Docker Compose is essentially a **container definition**. Each service describes:
- What image to use (or how to build one)
- Ports to publish
- Environment variables
- Volumes to mount
- Networks to join
- Dependencies on other services

#### Configuration Replaces Commands
Everything you'd pass as flags to `docker run` goes into the service configuration:

| `docker run` Flag | Compose Equivalent |
|---|---|
| `--name` | Service name (key under `services:`) |
| `-p 3000:3000` | `ports: - "3000:3000"` |
| `-e KEY=VALUE` | `environment: - KEY=VALUE` |
| `-v name:/path` | `volumes: - name:/path` |
| `--network my-net` | `networks: - my-net` |
| `--rm` | Default behavior in Compose |
| `-d` | `docker-compose up -d` |
| `--build` flag | `build: ./path` |
| `--env-file .env` | `env_file: - ./.env` |

### 6. Key Docker Compose Commands

```bash
# Start all services (build images if needed)
docker-compose up

# Start in detached mode
docker-compose up -d

# Start and force rebuild images
docker-compose up -d --build

# Stop all services and remove containers
docker-compose down

# Stop and remove containers + volumes
docker-compose down -v

# Stop and remove containers + volumes + images
docker-compose down -v --rmi all

# View logs
docker-compose logs
docker-compose logs -f            # Follow (stream) logs
docker-compose logs service-name  # Specific service

# List running services
docker-compose ps

# Execute command in a running service
docker-compose exec service-name sh

# Build/rebuild images without starting
docker-compose build
```

## 🎯 Interview Questions & Answers

### Q1: What is Docker Compose and what problem does it solve?

**Answer:**
Docker Compose is a tool for defining and running multi-container Docker applications. It solves the problem of managing complex `docker build` and `docker run` commands for applications that require multiple containers (e.g., an API server, a database, a cache, a message queue).

Without Compose, you'd need to:
1. Create networks manually
2. Create volumes manually
3. Build images individually
4. Run each container with long command-line flags
5. Remember the correct startup order
6. Stop and clean up everything manually

With Compose, all of this is captured in a single `docker-compose.yml` file, and the entire application can be started with `docker-compose up` and stopped with `docker-compose down`. The file is declarative, shareable, and version-controllable.

---

### Q2: Does Docker Compose replace Dockerfiles?

**Answer:**
**No.** This is a common misconception. Docker Compose **works alongside** Dockerfiles — it does not replace them.

- **Dockerfile**: Defines how to build a single image (base image, dependencies, source code, configuration)
- **Docker Compose**: Defines how to orchestrate one or more containers (which images to use, networking, volumes, environment variables, port mappings)

A Compose file can reference a Dockerfile via the `build` key:

```yaml
services:
  app:
    build: ./app-directory    # Points to a directory containing a Dockerfile
    ports:
      - "3000:3000"
```

You still need Dockerfiles for custom images. Compose just automates the building and running process.

---

### Q3: What is a "service" in Docker Compose?

**Answer:**
A "service" in Docker Compose is essentially a **container definition**. Each service block under the `services:` key describes one container — what image it uses, what ports it publishes, what volumes it mounts, what environment variables it needs, and what networks it belongs to.

```yaml
services:
  mongodb:         # ← This is a "service" = one container
    image: mongo
    volumes:
      - data:/data/db

  backend:         # ← Another "service" = another container
    build: ./backend
    ports:
      - "3000:3000"
    depends_on:
      - mongodb
```

The service name also becomes the **DNS hostname** on the Docker network, so `backend` can connect to `mongodb` using `mongodb://mongodb:27017`.

---

### Q4: Can Docker Compose be used for single-container applications?

**Answer:**
**Yes.** While Compose shines most with multi-container setups, it's perfectly valid and common to use it for single-container applications. Benefits include:

- No need to remember long `docker run` commands
- Configuration is documented in a file
- Easy to add more services later
- Consistent workflow (`docker-compose up` / `down`) regardless of complexity
- Environment variables, volumes, and port mappings are clearly documented

```yaml
version: "3.8"
services:
  app:
    build: .
    ports:
      - "3000:3000"
    volumes:
      - ./:/app:ro
      - /app/node_modules
    environment:
      - NODE_ENV=development
```

Even for one container, this is more maintainable than remembering: `docker run -d --rm -p 3000:3000 -v $(pwd):/app:ro -v /app/node_modules -e NODE_ENV=development my-app`

---

### Q5: Is Docker Compose suitable for production deployments across multiple servers?

**Answer:**
**Not primarily.** Docker Compose is designed for **single-host** management — all containers run on one machine. It's excellent for:

- Local development environments
- CI/CD pipelines
- Testing
- Single-server deployments

For **multi-host** (multi-machine) deployments where containers need to run across a cluster of servers, you should use:
- **Docker Swarm** — Docker's built-in orchestration (uses Compose file format with `docker stack deploy`)
- **Kubernetes** — Industry-standard container orchestration for large-scale deployments

That said, Docker Compose can be used as part of a production workflow on a single server, especially for smaller applications.

### Q6: What happens when you run `docker-compose up`? Walk through the process.

**Answer:**
When you run `docker-compose up`, Docker Compose performs these steps in order:

1. **Reads** `docker-compose.yml` (or specified file)
2. **Creates a default network** for all services (named `<project>_default`)
3. **Creates declared volumes** if they don't exist
4. **Creates declared custom networks** if they don't exist
5. **Builds images** for services with `build:` (if not already built)
6. **Pulls images** for services with `image:` (if not already pulled)
7. **Creates containers** for each service
8. **Starts containers** respecting `depends_on` order
9. **Attaches to logs** (unless `-d` is used)

```bash
docker-compose up
# Creating network "myproject_default" with the default driver
# Creating volume "myproject_data" with default driver
# Building backend...
# Pulling mongodb (mongo:latest)...
# Creating myproject_mongodb_1 ... done
# Creating myproject_backend_1 ... done
# Attaching to myproject_mongodb_1, myproject_backend_1
```

### Q7: What happens when you run `docker-compose down`? What are the different options?

**Answer:**
`docker-compose down` stops and removes containers, networks, and optionally volumes and images:

```bash
# Stop containers + remove containers + remove default network
docker-compose down

# Also remove named volumes declared in the volumes: section
docker-compose down -v

# Also remove images built by Compose
docker-compose down --rmi local

# Remove ALL images used by services (including pulled ones)
docker-compose down --rmi all

# Nuclear option — remove everything
docker-compose down -v --rmi all
```

| Flag | Removes |
|---|---|
| (none) | Containers + default network |
| `-v` | + Named volumes |
| `--rmi local` | + Locally built images |
| `--rmi all` | + All images (including pulled) |

### Q8: How does Docker Compose handle networking compared to manual Docker commands?

**Answer:**
Docker Compose **automatically creates a default network** for all services defined in the file. You don't need to run `docker network create` manually.

**Manual approach:**
```bash
docker network create my-net
docker run --network my-net --name db mongo
docker run --network my-net --name app my-app
```

**Compose approach:**
```yaml
services:
  db:
    image: mongo
  app:
    build: .
```
No network configuration needed — Compose creates `projectname_default` and puts both services on it. Services reference each other by **service name** as hostname.

You can also define custom networks for segmentation:
```yaml
services:
  db:
    networks: [backend]
  api:
    networks: [backend, frontend]
  web:
    networks: [frontend]

networks:
  backend:
  frontend:
```

---

### Q9: How does `docker-compose up` relate to `docker build` and `docker run`?

**Answer:**
`docker-compose up` is essentially a **combined and orchestrated** version of multiple `docker build` and `docker run` commands:

| What Compose Does | Equivalent Manual Commands |
|---|---|
| Reads `build:` directives | `docker build -t <auto-name> ./path` |
| Reads `image:` directives | `docker pull <image>` |
| Creates networks | `docker network create <name>` |
| Creates volumes | `docker volume create <name>` |
| Starts containers | `docker run` with all configured flags |
| Manages dependencies | Starting services in `depends_on` order |

Adding `--build` forces image rebuilding:
```bash
docker-compose up -d --build
```

This is needed when source code changes, since Compose will reuse cached images by default.

### Q10: How would you map a `docker run` command to a Docker Compose service definition?

**Answer:**
Here's a direct translation:

```bash
docker run -d \
  --name backend \
  --rm \
  --network my-net \
  -p 3000:3000 \
  -v logs:/app/logs \
  -v $(pwd):/app:ro \
  -v /app/node_modules \
  -e NODE_ENV=production \
  -e MONGO_URL=mongodb://mongodb:27017/db \
  --env-file ./.env \
  my-backend-image
```

Equivalent Compose:

```yaml
services:
  backend:                                    # --name backend
    build: .                                  # or image: my-backend-image
    ports:
      - "3000:3000"                           # -p 3000:3000
    volumes:
      - logs:/app/logs                        # -v logs:/app/logs
      - ./:/app:ro                            # -v $(pwd):/app:ro
      - /app/node_modules                     # -v /app/node_modules
    environment:
      - NODE_ENV=production                   # -e NODE_ENV=production
      - MONGO_URL=mongodb://mongodb:27017/db  # -e MONGO_URL=...
    env_file:
      - ./.env                                # --env-file ./.env
    networks:
      - my-net                                # --network my-net
    # --rm is default behavior in Compose
    # -d is achieved with: docker-compose up -d

volumes:
  logs:

networks:
  my-net:
```

### docker-compose.yml

```yaml
version: "3.8"

# ─── SERVICES (= Containers) ───
# This is the HEART of the compose file
# Each service = one container definition

services:
  # ── Service 1: MongoDB Database ──
  mongodb:
    image: mongo                          # Use official image (no Dockerfile needed)
    volumes:
      - mongodata:/data/db                # Named volume for data persistence
    # No ports! Only backend connects to it (within the network)
    # Compose auto-creates a network — no manual docker network create needed
    environment:
      MONGO_INITDB_ROOT_USERNAME: admin
      MONGO_INITDB_ROOT_PASSWORD: secret

  # ── Service 2: Node.js Backend API ──
  backend:
    build: ./backend                      # Build image from ./backend/Dockerfile
    ports:
      - "3000:3000"                       # Publish port (accessed from host browser)
    volumes:
      - logs:/app/logs                    # Named volume for logs
      - ./backend:/app:ro                 # Bind mount for live code (read-only)
      - /app/node_modules                 # Anonymous volume (protect node_modules)
    environment:
      # "mongodb" = service name = hostname on the Docker network
      - MONGO_URL=mongodb://admin:secret@mongodb:27017/favorites?authSource=admin
      - NODE_ENV=development
    depends_on:
      - mongodb                           # Start mongodb BEFORE backend

# ─── NAMED VOLUMES ───
# Must declare named volumes at top level
volumes:
  mongodata:
  logs:

# Networks are optional — Compose creates a default network automatically
# Uncomment below for custom network configuration:
# networks:
#   app-network:
#     driver: bridge
```

### backend/app.js

```javascript
const express = require('express');
const bodyParser = require('body-parser');
const mongoose = require('mongoose');
const fs = require('fs');
const path = require('path');

const app = express();
app.use(bodyParser.json());

// ─── Connection URL from environment variable ───
// "mongodb" here is the SERVICE NAME from docker-compose.yml
// Docker Compose's auto-created network resolves it to the container's IP
const MONGO_URL = process.env.MONGO_URL || 'mongodb://mongodb:27017/favorites';

mongoose.connect(MONGO_URL)
  .then(() => {
    console.log('✅ Connected to MongoDB');
    logEvent('MongoDB connected successfully');
  })
  .catch((err) => {
    console.error('❌ MongoDB connection failed:', err.message);
    logEvent(`MongoDB connection failed: ${err.message}`);
    process.exit(1);
  });

// ─── Simple logging to volume ───
function logEvent(message) {
  const logsDir = path.join(__dirname, 'logs');
  if (!fs.existsSync(logsDir)) fs.mkdirSync(logsDir, { recursive: true });
  const logFile = path.join(logsDir, 'app.log');
  const entry = `[${new Date().toISOString()}] ${message}\n`;
  fs.appendFileSync(logFile, entry);
}

// ─── Schema & Model ───
const favoriteSchema = new mongoose.Schema({
  name: { type: String, required: true },
  type: { type: String, required: true },
  url: String,
  createdAt: { type: Date, default: Date.now }
});

const Favorite = mongoose.model('Favorite', favoriteSchema);

// ─── Routes ───
app.get('/favorites', async (req, res) => {
  try {
    const favorites = await Favorite.find();
    logEvent(`GET /favorites — returned ${favorites.length} items`);
    res.json({ favorites });
  } catch (err) {
    res.status(500).json({ error: err.message });
  }
});

app.post('/favorites', async (req, res) => {
  const { name, type, url } = req.body;
  if (!name || !type) {
    return res.status(400).json({ error: 'Name and type are required' });
  }
  try {
    const favorite = new Favorite({ name, type, url });
    await favorite.save();
    logEvent(`POST /favorites — saved "${name}"`);
    res.status(201).json({ message: 'Favorite saved!', favorite });
  } catch (err) {
    res.status(500).json({ error: err.message });
  }
});

app.delete('/favorites/:id', async (req, res) => {
  try {
    await Favorite.findByIdAndDelete(req.params.id);
    logEvent(`DELETE /favorites/${req.params.id}`);
    res.json({ message: 'Deleted' });
  } catch (err) {
    res.status(500).json({ error: err.message });
  }
});

app.get('/health', (req, res) => {
  const dbState = mongoose.connection.readyState;
  const states = { 0: 'disconnected', 1: 'connected', 2: 'connecting', 3: 'disconnecting' };
  res.json({
    status: 'ok',
    database: states[dbState],
    environment: process.env.NODE_ENV || 'not set'
  });
});

const PORT = process.env.PORT || 3000;
app.listen(PORT, () => {
  console.log(`🚀 Server running on port ${PORT}`);
  logEvent(`Server started on port ${PORT}`);
});
```

echo ""

# Scale a service (multiple instances)
