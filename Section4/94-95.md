

# Docker Compose — Configuring Services (MongoDB Example)

---

## 📘 Detailed Notes

### 1. Translating `docker run` to Docker Compose

Every flag and option from a `docker run` command maps to a key in the compose file:

```bash
# The docker run command we're translating:
docker run -d \
  --rm \
  --name mongodb \
  --network goals-net \
  -v data:/data/db \
  -e MONGO_INITDB_ROOT_USERNAME=max \
  -e MONGO_INITDB_ROOT_PASSWORD=secret \
  mongo
```

```yaml
# The equivalent docker-compose.yml configuration:
services:
  mongodb:                                    # --name mongodb
    image: mongo                              # mongo (the image)
    volumes:                                  # -v data:/data/db
      - data:/data/db
    environment:                              # -e KEY=VALUE
      MONGO_INITDB_ROOT_USERNAME: max
      MONGO_INITDB_ROOT_PASSWORD: secret
    # -d       → handled by: docker-compose up -d
    # --rm     → default behavior in Compose
    # --network → auto-created by Compose
```

### 2. The `image` Key

```yaml
services:
  mongodb:
    image: mongo          # Official Docker Hub image
```

Valid values for `image`:
| Example | Description |
|---|---|
| `mongo` | Official image name (looked up locally, then Docker Hub) |
| `mongo:6.0` | Specific version tag |
| `academind/hello-world` | User repository on Docker Hub |
| `registry.example.com/my-image:latest` | Full URL to private registry |
| `goals-node` | Custom locally-built image |

### 3. Detached Mode and Auto-Remove — Free in Compose

Two common `docker run` flags are **handled automatically** by Docker Compose:

| Flag | `docker run` | Docker Compose |
|---|---|---|
| `-d` (detached) | Must specify explicitly | Specify on command: `docker-compose up -d` |
| `--rm` (auto-remove) | Must specify explicitly | **Default behavior** — containers are removed on `docker-compose down` |

You do NOT add these to the service configuration in the compose file.

### 4. Volumes in Docker Compose

```yaml
services:
  mongodb:
    volumes:
      - data:/data/db           # Named volume
      - ./mongo-init:/docker-entrypoint-initdb.d:ro  # Bind mount
      - /data/configdb          # Anonymous volume
```

**Syntax is identical to `-v` flag:**
- `name:/container/path` → Named volume
- `./host/path:/container/path` → Bind mount
- `/container/path` → Anonymous volume
- Add `:ro` after for read-only

**Critical rule:** Named volumes must also be declared at the **top level** of the compose file:

```yaml
services:
  mongodb:
    volumes:
      - data:/data/db

volumes:              # ← TOP LEVEL — same level as services
  data:               # ← Just the name, colon, nothing after
```

Without this top-level declaration, Compose treats `data` as a relative path (bind mount) rather than a named volume.

### 5. Environment Variables — Three Approaches

#### Approach A: Key-Value Pairs (YAML object syntax)
```yaml
environment:
  MONGO_INITDB_ROOT_USERNAME: max
  MONGO_INITDB_ROOT_PASSWORD: secret
```
- Uses colon-space (`: `) between key and value
- No dashes needed
- Creates a YAML mapping/object

#### Approach B: List Syntax (with equals sign)
```yaml
environment:
  - MONGO_INITDB_ROOT_USERNAME=max
  - MONGO_INITDB_ROOT_PASSWORD=secret
```
- Uses dash (`-`) for each entry
- Uses equals sign (`=`) between key and value
- Single values in a list require dashes

#### Approach C: External File (`env_file`)
```yaml
env_file:
  - ./env/mongo.env
```

With `./env/mongo.env` containing:
```
MONGO_INITDB_ROOT_USERNAME=max
MONGO_INITDB_ROOT_PASSWORD=secret
```

**Why use `env_file`?**
- Keep secrets out of the compose file
- Add `.env` files to `.gitignore` to avoid committing secrets
- Separate configuration from orchestration
- Reuse the same env file across multiple services or environments

### 6. YAML Syntax: Dashes vs No Dashes

```yaml
# KEY-VALUE PAIRS (YAML mapping) → NO dashes
environment:
  KEY1: value1
  KEY2: value2

# SINGLE VALUES (YAML list) → YES dashes
environment:
  - KEY1=value1
  - KEY2=value2

# Lists always use dashes
volumes:
  - data:/data/db
  - ./src:/app:ro

ports:
  - "3000:3000"
  - "8080:80"

env_file:
  - ./env/mongo.env
  - ./env/common.env
```

**Rule:** 
- If each entry is a **single value** → use dashes (list)
- If entries are **key: value pairs** → no dashes needed (mapping)

### 7. Networks — Auto-Created by Compose

```yaml
# You DON'T need to specify networks in most cases!
services:
  mongodb:
    image: mongo
    # No networks: key needed

  backend:
    build: ./backend
    # No networks: key needed
```

**Docker Compose automatically:**
1. Creates a default network named `<project-directory>_default`
2. Adds ALL services defined in the compose file to this network
3. Makes service names resolvable as DNS hostnames

**When you WOULD specify networks:**
```yaml
services:
  mongodb:
    networks:
      - backend-net        # Custom network for segmentation

  backend:
    networks:
      - backend-net
      - frontend-net       # On both networks

  frontend:
    networks:
      - frontend-net

networks:                  # Must declare custom networks at top level
  backend-net:
  frontend-net:
```

### 8. Top-Level Named Volume Declaration

```yaml
services:
  mongodb:
    volumes:
      - data:/data/db        # References named volume "data"

  backend:
    volumes:
      - data:/shared-data    # SAME volume! Shared between containers
      - logs:/app/logs

volumes:                     # TOP LEVEL — required for named volumes
  data:                      # Colon with no value after it
  logs:                      # Each named volume listed here
```

**What needs top-level declaration:**
| Type | Top-level declaration needed? |
|---|---|
| Named volumes | ✅ Yes — must list under `volumes:` |
| Anonymous volumes | ❌ No |
| Bind mounts | ❌ No |
| Custom networks | ✅ Yes — must list under `networks:` |

### 9. Complete MongoDB Service Configuration

```yaml
version: "3.8"

services:
  mongodb:
    image: mongo                          # Official image
    volumes:
      - data:/data/db                     # Named volume for persistence
    environment:                          # Direct env vars
      MONGO_INITDB_ROOT_USERNAME: max
      MONGO_INITDB_ROOT_PASSWORD: secret
    # No -d: use docker-compose up -d
    # No --rm: default in Compose
    # No --network: auto-created by Compose

volumes:
  data:                                   # Named volume declaration
```

## 🎯 Interview Questions & Answers

### Q1: How do you specify which Docker image a service should use in Docker Compose?

**Answer:**
Use the `image` key under the service definition:

```yaml
services:
  mongodb:
    image: mongo              # Official Docker Hub image
```

The `image` value follows the same conventions as `docker run`:
- `mongo` — official image (looked up locally, then Docker Hub)
- `mongo:6.0` — specific tag/version
- `myuser/myimage:latest` — user repository on Docker Hub
- `registry.example.com/image:tag` — private registry with full URL
- `my-local-image` — locally built image

If the image doesn't exist locally, Docker Compose will pull it automatically. For custom images that need to be built from a Dockerfile, you use `build:` instead of (or alongside) `image:`.

---

### Q2: Do you need to specify `--rm` and `-d` flags in a Docker Compose service configuration?

**Answer:**
**No.** These are handled automatically:

- **`--rm` (auto-remove):** This is the **default behavior** in Docker Compose. When you run `docker-compose down`, all containers are stopped AND removed automatically. You never need to specify this in the compose file.

- **`-d` (detached mode):** This is specified on the **command**, not in the file. You run `docker-compose up -d` to start services in detached mode. The compose file itself doesn't contain this flag.

This is one of the conveniences of Compose — common operational flags are either defaults or command-level options, keeping the configuration file focused on service definition.

---

### Q3: How do you define volumes in Docker Compose and what is the top-level `volumes` key for?

**Answer:**
Volumes are defined under each service using the same syntax as the `-v` flag:

```yaml
services:
  mongodb:
    volumes:
      - data:/data/db          # Named volume
      - ./init:/docker-entrypoint-initdb.d:ro  # Bind mount
      - /data/configdb         # Anonymous volume
```

The **top-level `volumes` key** is required to **declare named volumes**:

```yaml
volumes:
  data:          # Must be listed here for Docker to recognize it as a named volume
```

Without the top-level declaration, Compose may misinterpret `data:/data/db` as a bind mount with a relative path called `data`. The top-level declaration tells Docker: "this is a named volume that Docker should manage."

Anonymous volumes and bind mounts do **not** need top-level declaration — only named volumes do.

If the same named volume appears in multiple services, those containers **share** the same volume (same folder on the host).

### Q4: What are the different ways to specify environment variables in Docker Compose?

**Answer:**
Three approaches:

**1. YAML mapping (key-value pairs):**
```yaml
environment:
  DB_USER: admin
  DB_PASS: secret
```
No dashes needed. Uses colon-space syntax.

**2. List syntax (equals sign):**
```yaml
environment:
  - DB_USER=admin
  - DB_PASS=secret
```
Uses dashes (YAML list). Uses equals sign for assignment.

**3. External file (`env_file`):**
```yaml
env_file:
  - ./env/mongo.env
```
File contains `KEY=VALUE` pairs, one per line. Advantages: keeps secrets out of the compose file, can be `.gitignore`'d, separates configuration from orchestration.

All three approaches are functionally identical. The choice depends on preference and whether you want to keep sensitive values separate from the compose file.

### Q5: Why don't you need to specify networks in Docker Compose for inter-service communication?

**Answer:**
Docker Compose **automatically creates a default network** for all services defined in the same compose file. All services are added to this network automatically.

This means:
- Services can reference each other by **service name** as hostname
- DNS resolution works out of the box
- No `docker network create` needed
- No `--network` flag needed on services

```yaml
services:
  mongodb:
    image: mongo
    # Automatically on the default network

  backend:
    build: ./backend
    environment:
      # "mongodb" resolves because both services are on the same auto-created network
      - MONGO_URL=mongodb://mongodb:27017/mydb
```

The auto-created network is named `<project-directory>_default`. You only need to specify custom networks if you want **network segmentation** (isolating groups of services from each other).

### Q6: Explain the YAML syntax difference between using dashes and not using dashes.

**Answer:**
In YAML, dashes indicate **list items** (sequences), while indented key-value pairs without dashes indicate **mappings** (objects/dictionaries):

**List (dashes required) — for single values:**
```yaml
volumes:
  - data:/data/db          # Each item is a single string value
  - logs:/app/logs

ports:
  - "3000:3000"
  - "8080:80"

environment:
  - DB_USER=admin          # Single string with = inside
  - DB_PASS=secret
```

**Mapping (no dashes) — for key-value pairs:**
```yaml
environment:
  DB_USER: admin           # Key: value pair
  DB_PASS: secret          # Key: value pair

labels:
  com.example.app: myapp
  com.example.env: prod
```

**Rule of thumb:**
- Single values that are complete items → dashes (list)
- Named properties with distinct keys and values → no dashes (mapping)
- Both formats are valid for `environment:` — choose one and be consistent

### Q7: How do you share a named volume between multiple services in Docker Compose?

**Answer:**
Simply reference the same volume name in multiple services. Both services will mount the same Docker-managed volume:

```yaml
services:
  writer-service:
    build: ./writer
    volumes:
      - shared-data:/app/output     # Writes to this volume

  reader-service:
    build: ./reader
    volumes:
      - shared-data:/app/input:ro   # Reads from the same volume (read-only)

volumes:
  shared-data:                      # Declared once at top level
```

Both containers access the same folder on the host machine. The `writer-service` can write files, and the `reader-service` can read them (mounted read-only with `:ro`). This is useful for:
- Sharing logs between a writer and a log processor
- Sharing uploaded files between an API and a static file server
- Data pipelines between processing stages

### Q8: What is the `env_file` key and when would you use it instead of `environment`?

**Answer:**
`env_file` reads environment variables from an external file instead of defining them inline:

```yaml
services:
  mongodb:
    image: mongo
    env_file:
      - ./env/mongo.env
```

`./env/mongo.env`:
```
MONGO_INITDB_ROOT_USERNAME=admin
MONGO_INITDB_ROOT_PASSWORD=supersecretpassword
```

**When to use `env_file` over `environment`:**

1. **Security**: Keep secrets (passwords, API keys) out of the compose file, which might be committed to Git
2. **Separation of concerns**: Configuration values in separate files, orchestration in compose file
3. **Environment-specific configs**: Different `.env` files for dev, staging, prod
4. **Reusability**: Same env file shared across services or projects
5. **Team collaboration**: Share `docker-compose.yml` freely while keeping `.env` files in `.gitignore`

```
.gitignore:
env/
.env
*.env
```

You can combine both — `env_file` for base values and `environment` for overrides (inline values take precedence).

### Q9: If you define a named volume `data` in a service but forget to declare it at the top-level `volumes` key, what happens?

**Answer:**
Docker Compose may misinterpret the volume definition. Without the top-level declaration, `data:/data/db` could be treated as a **relative path bind mount** rather than a named volume — Docker might look for a directory called `data` in the current directory.

In newer versions of Compose, you'll typically get a **warning or error** about an undeclared volume. In older versions, the behavior may be unpredictable.

```yaml
# ❌ MISSING top-level declaration
services:
  mongodb:
    volumes:
      - data:/data/db        # Is "data" a volume name or a directory path?

# ✅ CORRECT — with declaration
services:
  mongodb:
    volumes:
      - data:/data/db

volumes:
  data:                      # Now Docker knows "data" is a named volume
```

**Best practice:** Always declare named volumes at the top level. It's explicit, prevents ambiguity, and is required by the Compose specification.

### Q10: Walk through the complete translation of a `docker run` command for MongoDB into a Docker Compose service.

**Answer:**

**Original command:**
```bash
docker run -d \
  --rm \
  --name mongodb \
  --network goals-net \
  -v data:/data/db \
  -e MONGO_INITDB_ROOT_USERNAME=max \
  -e MONGO_INITDB_ROOT_PASSWORD=secret \
  mongo
```

**Translation:**

```yaml
version: "3.8"

services:
  mongodb:                                    # ← --name mongodb
    image: mongo                              # ← mongo (the image)
    volumes:
      - data:/data/db                         # ← -v data:/data/db
    environment:
      MONGO_INITDB_ROOT_USERNAME: max         # ← -e MONGO_INITDB_ROOT_USERNAME=max
      MONGO_INITDB_ROOT_PASSWORD: secret      # ← -e MONGO_INITDB_ROOT_PASSWORD=secret
    # -d         → docker-compose up -d (command-level, not in file)
    # --rm       → default behavior (containers removed on "down")
    # --network  → auto-created by Compose (all services share one network)

volumes:
  data:                                       # ← Named volume must be declared here
```

**What's NOT in the compose file:**
| Docker Run Flag | Why Not in Compose File |
|---|---|
| `-d` | Specified as `docker-compose up -d` |
| `--rm` | Default behavior in Compose |
| `--name` | Service name serves as the container identifier |
| `--network` | Compose auto-creates a shared network |

### docker-compose.yml (Step-by-Step Build)

```yaml
# ═══════════════════════════════════════════════════════════
# DOCKER COMPOSE — MongoDB Service Configuration
# Building the compose file step by step
# ═══════════════════════════════════════════════════════════

# Step 1: Specify compose specification version
version: "3.8"

# Step 2: Define services (containers)
services:

  # ════════════════════════════════════════
  # SERVICE: MongoDB
  # ════════════════════════════════════════
  # Translates from:
  #   docker run -d --rm --name mongodb --network goals-net
  #     -v data:/data/db
  #     -e MONGO_INITDB_ROOT_USERNAME=max
  #     -e MONGO_INITDB_ROOT_PASSWORD=secret
  #     mongo
  mongodb:
    # ── Image ──
    # Official MongoDB image from Docker Hub
    # Same as specifying "mongo" in docker run
    image: mongo

    # ── Volumes ──
    # Named volume for data persistence
    # Syntax: volumeName:containerPath
    # Same as -v data:/data/db
    volumes:
      - data:/data/db

    # ── Environment Variables ──
    # Option A: YAML mapping (key: value)
    environment:
      MONGO_INITDB_ROOT_USERNAME: max
      MONGO_INITDB_ROOT_PASSWORD: secret

    # # Option B: List syntax (- KEY=VALUE)
    # environment:
    #   - MONGO_INITDB_ROOT_USERNAME=max
    #   - MONGO_INITDB_ROOT_PASSWORD=secret

    # # Option C: External file
    # env_file:
    #   - ./env/mongo.env

    # ── NOT specified (handled automatically) ──
    # -d (detached): use docker-compose up -d
    # --rm (auto-remove): default in Compose
    # --network: Compose auto-creates a network for all services

  # ════════════════════════════════════════
  # SERVICE: Backend (configured in next lesson)
  # ════════════════════════════════════════
  # backend:
  #   build: ./backend
  #   ports:
  #     - "3000:3000"
  #   volumes:
  #     - logs:/app/logs
  #     - ./backend:/app
  #     - /app/node_modules
  #   environment:
  #     MONGO_URL: mongodb://max:secret@mongodb:27017/goals?authSource=admin
  #   depends_on:
  #     - mongodb

  # ════════════════════════════════════════
  # SERVICE: Frontend (configured in next lesson)
  # ════════════════════════════════════════
  # frontend:
  #   build: ./frontend
  #   ports:
  #     - "3001:3000"
  #   depends_on:
  #     - backend

# ── Named Volumes ──
# MUST be declared at top level (same indentation as services)
# Only named volumes need declaration here
# Anonymous volumes and bind mounts do NOT need this
volumes:
  data:             # Colon with no value — just the declaration
```
