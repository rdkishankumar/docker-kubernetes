

# Docker Networks — Container-to-Container Communication

---

## 📘 Detailed Notes

### 1. What Are Docker Networks?

Docker Networks are isolated virtual networks that allow containers to communicate with each other. When multiple containers are placed on the same network, Docker automatically handles IP resolution — you reference other containers **by name** instead of by IP address.

```
┌──────────────────────────────────────────────────────────────┐
│                    Docker Network: favorites-net              │
│                                                              │
│   ┌─────────────────┐          ┌─────────────────┐          │
│   │  Node.js App     │  ──────→ │  MongoDB         │          │
│   │  --name favorites│  uses    │  --name mongodb  │          │
│   │                  │ "mongodb"│                  │          │
│   │  Port: 3000      │ as host  │  Port: 27017     │          │
│   └─────────────────┘          └─────────────────┘          │
│                                                              │
│   Docker resolves "mongodb" → container's internal IP        │
│   No manual IP lookup needed                                 │
│   No -p flag needed for inter-container communication        │
└──────────────────────────────────────────────────────────────┘
```

### 2. Key Difference from Volumes

| Aspect | Volumes | Networks |
|---|---|---|
| **Auto-created on `docker run`** | ✅ Yes (named & anonymous) | ❌ No — must create manually first |
| **Create command** | `docker volume create <name>` | `docker network create <name>` |
| **List command** | `docker volume ls` | `docker network ls` |
| **Purpose** | Persist data | Enable container communication |

### 3. Network Setup Workflow

```
Step 1: Create the network
        docker network create favorites-net

Step 2: Start Container A on that network
        docker run -d --name mongodb --network favorites-net mongo

Step 3: Start Container B on the SAME network
        docker run -d --name favorites --network favorites-net -p 3000:3000 favorites-node

Step 4: In Container B's code, reference Container A by NAME
        mongoose.connect('mongodb://mongodb:27017/favorites')
                                     ↑
                          Container name = hostname
```

### 4. Docker Network Commands

```bash
# Create a network
docker network create <network-name>

# List all networks
docker network ls

# Inspect a network (see connected containers, config)
docker network inspect <network-name>

# Remove a network
docker network rm <network-name>

# Remove all unused networks
docker network prune

# Connect a running container to a network
docker network connect <network-name> <container-name>

# Disconnect a container from a network
docker network disconnect <network-name> <container-name>
```

### 5. DNS Resolution by Container Name

When two containers are on the **same custom Docker network**:

```javascript
// Container name "mongodb" is automatically resolved to its IP
mongoose.connect('mongodb://mongodb:27017/favorites');
```

Docker's embedded DNS server resolves the container name to its current IP address. This works because:
- Custom (user-defined) bridge networks provide **automatic DNS resolution**
- The default bridge network does **NOT** provide DNS resolution (only manual IP works)
- Container names act as hostnames within the network

### 6. Port Publishing Rules with Networks

| Scenario | `-p` Flag Needed? | Why |
|---|---|---|
| Access container from **host machine** (browser, Postman) | ✅ Yes | Host is outside the Docker network |
| Access container from **another container** on same network | ❌ No | Containers communicate internally on all ports |
| Access container from **the internet** | ✅ Yes | External traffic must be mapped to host |

```bash
# MongoDB — NO -p needed (only other containers connect to it)
docker run -d --name mongodb --network favorites-net mongo

# Node.js App — YES -p needed (we access it from our browser)
docker run -d --name favorites --network favorites-net -p 3000:3000 favorites-node
```

### 7. Default Networks vs Custom Networks

Docker comes with built-in networks visible via `docker network ls`:

| Network | Driver | Purpose |
|---|---|---|
| `bridge` | bridge | Default network — containers get IPs but **no DNS resolution by name** |
| `host` | host | Container shares host's network stack directly (Linux only) |
| `none` | null | No networking — container is completely isolated |
| **Your custom network** | bridge | DNS resolution by container name ✅ — **use this** |

### 8. Complete Address Reference

| Target | What to Use | Example |
|---|---|---|
| The container itself | `localhost` | `http://localhost:3000` |
| The host machine | `host.docker.internal` | `mongodb://host.docker.internal:27017` |
| Another container (same network) | **Container name** | `mongodb://mongodb:27017` |
| Another container (no network) | Container IP (manual) | `mongodb://172.17.0.2:27017` |
| External internet | Regular URL | `https://api.example.com` |

## 🎯 Interview Questions & Answers

### Q1: What are Docker Networks and why are they needed?

**Answer:**
Docker Networks are isolated virtual networks that enable container-to-container communication. By default, Docker containers are isolated and cannot communicate with each other. Networks solve this by:

1. Placing containers on a shared network where they can reach each other
2. Providing **automatic DNS resolution** — containers reference each other by name, not IP
3. Eliminating the need to manually look up container IP addresses
4. Ensuring communication survives container restarts (names stay the same even if IPs change)

```bash
docker network create my-network
docker run -d --name db --network my-network postgres
docker run -d --name api --network my-network -p 3000:3000 my-api
# In api's code: connect to "db:5432" — Docker resolves "db" automatically
```

This is essential for microservice architectures where multiple containers (API, database, cache, message queue) need to interact.

---

### Q2: Why doesn't Docker auto-create networks like it does for volumes?

**Answer:**
Unlike volumes (which Docker creates automatically when referenced in `docker run -v`), networks must be explicitly created with `docker network create` before use. If you try to use `--network my-net` without creating `my-net` first, Docker returns an error: `network my-net not found`.

The reasoning is that networks represent **infrastructure topology** — they define how containers can communicate. This is a deliberate design decision rather than something that should happen implicitly. Networks affect security boundaries (which containers can talk to which), so Docker requires explicit intent.

```bash
# This FAILS if network doesn't exist
docker run --network my-net my-image
# Error: network my-net not found

# Must create first
docker network create my-net
docker run --network my-net my-image  # Now works
```

### Q3: How does DNS resolution work in Docker networks? Why does the container name work as a hostname?

**Answer:**
Docker runs an **embedded DNS server** (at `127.0.0.11`) for user-defined (custom) networks. When containers are placed on a custom network:

1. Docker registers each container's name as a DNS entry pointing to its current IP
2. When Container A tries to connect to `mongodb:27017`, Docker's DNS server resolves `mongodb` to Container B's IP (e.g., `172.18.0.2`)
3. If Container B restarts and gets a new IP, Docker updates the DNS entry automatically

**Critical distinction:** This automatic DNS resolution only works on **custom (user-defined) networks**, NOT on the default `bridge` network. On the default bridge, you must use IP addresses.

```bash
# Default bridge — NO DNS resolution
docker run -d --name db mongo
docker run -d --name app my-app
# app cannot reach "db" by name, only by IP

# Custom network — DNS resolution works
docker network create my-net
docker run -d --name db --network my-net mongo
docker run -d --name app --network my-net my-app
# app CAN reach "db" by name
```

### Q4: When do you need the `-p` flag and when don't you?

**Answer:**
The `-p` (publish) flag maps a container's internal port to a port on the **host machine**. It's only needed when something **outside** the Docker network needs to access the container.

**Need `-p`:**
- Your browser accessing a web app container
- Postman or curl from your terminal hitting an API container
- External services connecting to your container

**Don't need `-p`:**
- Container-to-container communication within the same Docker network
- The MongoDB container that only your API container connects to

```bash
# MongoDB — NO -p (only app container connects to it)
docker run -d --name mongodb --network my-net mongo

# App — YES -p (users access it from browsers)
docker run -d --name app --network my-net -p 3000:3000 my-app
```

Within a Docker network, all ports are accessible between containers without publishing. Port publishing is the gateway between Docker's internal network and the outside world.

### Q5: What are the different Docker network drivers and when would you use each?

**Answer:**

| Driver | Use Case | Behavior |
|---|---|---|
| **bridge** (default for custom) | Standard container-to-container communication | Isolated network with DNS resolution; most common |
| **host** | Maximum network performance (Linux only) | Container shares host's network stack; no port mapping needed; no isolation |
| **overlay** | Multi-host networking (Docker Swarm) | Connects containers across different Docker hosts/machines |
| **macvlan** | Containers need their own MAC/IP on physical network | Container appears as a physical device on the network |
| **none** | Complete network isolation | Container has no network access at all |

```bash
# Default bridge driver (most common)
docker network create my-net

# Explicitly specify driver
docker network create --driver bridge my-net
docker network create --driver overlay my-swarm-net
```

For single-host development and most production scenarios, the **bridge** driver (which is the default) is what you'll use.

### Q6: Can a container belong to multiple networks simultaneously?

**Answer:**
**Yes.** A container can be connected to multiple networks at the same time. This is useful for creating network segmentation — for example, an API container that needs to talk to both a database network and a frontend network.

```bash
# Create two networks
docker network create backend-net
docker network create frontend-net

# Start containers
docker run -d --name db --network backend-net mongo
docker run -d --name web --network frontend-net nginx

# API connects to BOTH networks
docker run -d --name api --network backend-net my-api
docker network connect frontend-net api

# Now:
# - api can talk to db (both on backend-net)
# - api can talk to web (both on frontend-net)
# - web CANNOT talk to db (different networks, no shared network)
```

This provides **network-level security** — the web server cannot directly access the database.

### Q7: How do you troubleshoot networking issues between Docker containers?

**Answer:**
Step-by-step debugging approach:

```bash
# 1. Verify both containers are running
docker ps

# 2. Verify both containers are on the SAME network
docker network inspect my-net
# Look for both containers in the "Containers" section

# 3. Test DNS resolution from inside a container
docker exec -it app-container ping mongodb
# If ping works → network connectivity is fine

# 4. Test port connectivity
docker exec -it app-container wget -qO- http://mongodb:27017
# Or use: docker exec -it app-container nc -zv mongodb 27017

# 5. Check container logs for connection errors
docker logs app-container
docker logs mongodb

# 6. Verify the container name matches what's used in code
docker ps --format "{{.Names}}"
# The EXACT name must be used as hostname in connection strings

# 7. Check if using default bridge (no DNS) vs custom network (DNS works)
docker inspect app-container | grep -A 5 "Networks"
```

Common issues:
- Containers on different networks
- Using default bridge (no DNS resolution)
- Typo in container name
- Target container not running
- Application trying to connect before database is ready (race condition)

### Q8: What happens to a Docker network when you remove all containers connected to it?

**Answer:**
The network **persists** even when no containers are connected to it. Networks are independent resources that must be explicitly removed:

```bash
# Network exists even with no containers
docker network ls
# my-net still listed

# Remove a specific network
docker network rm my-net

# Remove ALL unused networks (not connected to any running container)
docker network prune
```

Unlike anonymous volumes (which can be auto-removed with `--rm`), networks always require manual cleanup. `docker network prune` is useful for cleaning up orphaned networks from previous development sessions.

### Q9: Compare the manual IP approach vs Docker Networks for inter-container communication.

**Answer:**

| Aspect | Manual IP Lookup | Docker Networks |
|---|---|---|
| **Setup effort** | Look up IP with `docker inspect` | Create network once with `docker network create` |
| **Connection string** | `mongodb://172.17.0.2:27017` | `mongodb://mongodb:27017` |
| **IP changes on restart** | ❌ Breaks connection | ✅ DNS auto-updates |
| **Code changes needed** | Yes (hard-code new IP) | No (name stays the same) |
| **Image rebuild needed** | Yes (if IP is in source code) | No |
| **Scalable** | ❌ Impractical with many containers | ✅ Works with any number |
| **Production ready** | ❌ No | ✅ Yes |
| **Security** | All containers on default bridge can see each other | Custom networks isolate groups of containers |

The Docker Network approach is **always preferred** for any non-trivial setup.

### Q10: In a Docker Compose context, do you need to manually create networks?

**Answer:**
**No.** Docker Compose **automatically creates a default network** for all services defined in the `docker-compose.yml` file. All services can reference each other by their **service name** (which acts as the hostname).

```yaml
version: "3.8"
services:
  mongodb:
    image: mongo
    # No network specified — Compose creates one automatically
    
  app:
    build: .
    ports:
      - "3000:3000"
    environment:
      # Use service name "mongodb" as hostname
      - MONGO_URL=mongodb://mongodb:27017/favorites
    depends_on:
      - mongodb
```

```bash
docker-compose up -d
# Creates network: projectfolder_default
# Both services are automatically on this network
# "mongodb" resolves to the mongodb container's IP
```

You can also define custom networks in Compose for network segmentation:

```yaml
services:
  db:
    networks:
      - backend
  api:
    networks:
      - backend
      - frontend
  web:
    networks:
      - frontend

networks:
  backend:
  frontend:
```

### app.js

```javascript
const express = require('express');
const bodyParser = require('body-parser');
const mongoose = require('mongoose');

const app = express();
app.use(bodyParser.json());

// ─── DATABASE CONNECTION ───
// Using container name as hostname — works on Docker Networks
// Docker's DNS resolves "mongodb" to the actual container IP
// Falls back to localhost for local development without Docker
const MONGO_URL = process.env.MONGO_URL || 'mongodb://mongodb:27017/favorites';

mongoose.connect(MONGO_URL)
  .then(() => console.log(`✅ Connected to MongoDB at: ${MONGO_URL}`))
  .catch((err) => {
    console.error('❌ MongoDB connection failed:', err.message);
    process.exit(1);
  });

// ─── Schema & Model ───
const favoriteSchema = new mongoose.Schema({
  name: { type: String, required: true },
  type: { type: String, required: true },
  url: String,
  createdAt: { type: Date, default: Date.now }
});

const Favorite = mongoose.model('Favorite', favoriteSchema);

// ─── Routes ───
app.get('/favorites', async (req, res) => {
  try {
    const favorites = await Favorite.find();
    res.json({ favorites });
  } catch (err) {
    res.status(500).json({ error: err.message });
  }
});

app.post('/favorites', async (req, res) => {
  const { name, type, url } = req.body;
  if (!name || !type) {
    return res.status(400).json({ error: 'Name and type are required' });
  }
  try {
    const favorite = new Favorite({ name, type, url });
    await favorite.save();
    res.status(201).json({ message: 'Favorite saved!', favorite });
  } catch (err) {
    res.status(500).json({ error: err.message });
  }
});

app.delete('/favorites/:id', async (req, res) => {
  try {
    await Favorite.findByIdAndDelete(req.params.id);
    res.json({ message: 'Favorite deleted' });
  } catch (err) {
    res.status(500).json({ error: err.message });
  }
});

app.get('/health', (req, res) => {
  const dbState = mongoose.connection.readyState;
  const states = { 0: 'disconnected', 1: 'connected', 2: 'connecting', 3: 'disconnecting' };
  res.json({ status: 'ok', database: states[dbState], mongoUrl: MONGO_URL });
});

const PORT = process.env.PORT || 3000;
app.listen(PORT, () => console.log(`🚀 Server running on port ${PORT}`));
```

┌──────────────────────────────────────────────────────────────┐
│                DOCKER NETWORK COMMANDS                        │
├──────────────────────────────────────────────────────────────┤
│  docker network create <name>        → Create a network      │
│  docker network ls                   → List all networks     │
│  docker network inspect <name>       → View network details  │
│  docker network rm <name>            → Remove a network      │
│  docker network prune                → Remove unused networks│
│  docker network connect <net> <ctr>  → Add container to net  │
│  docker network disconnect <n> <c>   → Remove from network   │
├──────────────────────────────────────────────────────────────┤
│             USING --network ON docker run                    │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  # Step 1: Create the network (required — not auto-created) │
│  docker network create my-net                                │
│                                                              │
│  # Step 2: Run containers on the same network                │
│  docker run -d --name db --network my-net mongo              │
│  docker run -d --name app --network my-net -p 3000:3000 img  │
│                                                              │
│  # Step 3: Use container name as hostname in code            │
│  mongodb://db:27017/mydb                                     │
│             ↑                                                │
│     Container name = DNS hostname on custom networks         │
│                                                              │
├──────────────────────────────────────────────────────────────┤
│             PORT PUBLISHING RULES                            │
├──────────────────────────────────────────────────────────────┤
│  Container → Container (same network):  NO -p needed         │
│  Host → Container:                      YES -p needed        │
│  Browser/Postman → Container:           YES -p needed        │
│  External internet → Container:         YES -p needed        │
├──────────────────────────────────────────────────────────────┤
│             KEY RULES                                        │
├──────────────────────────────────────────────────────────────┤
│  • Networks must be created manually before use              │
│  • Default bridge network: NO DNS resolution by name         │
│  • Custom networks: YES DNS resolution by container name     │
│  • Container name in --name = hostname on the network        │
│  • Containers can be on multiple networks simultaneously     │
│  • Networks persist until explicitly removed                 │
│  • Docker Compose auto-creates a default network             │
└──────────────────────────────────────────────────────────────┘
