## 📘 Detailed Notes

### 1. Image Building Behavior in Docker Compose

Docker Compose has specific rules about when it builds (or doesn't build) images:

```
┌─────────────────────────────────────────────────────────────┐
│              IMAGE BUILDING DECISION TREE                    │
│                                                              │
│  docker-compose up                                           │
│  ├── Service uses image: mongo                               │
│  │   └── Pull from Docker Hub (if not local)                 │
│  │                                                           │
│  └── Service uses build: ./backend                           │
│      ├── Image exists locally?                               │
│      │   ├── YES → Reuse it (NO rebuild)                     │
│      │   └── NO  → Build it from Dockerfile                  │
│      │                                                       │
│      └── docker-compose up --build                           │
│          └── ALWAYS rebuild (regardless of cache)            │
└─────────────────────────────────────────────────────────────┘
```

**Key insight:** `docker-compose up` does NOT automatically detect source code changes. If the image already exists locally, it reuses it — even if your code has changed. You must explicitly tell Compose to rebuild.

### 2. Three Build-Related Commands

```bash
# ── Command 1: docker-compose up ──
# Builds images ONLY if they don't exist yet
# If image exists → reuses it (fast, but won't pick up code changes)
docker-compose up -d

# ── Command 2: docker-compose up --build ──
# FORCES rebuild of all custom images before starting
# Use this when you've changed source code
docker-compose up -d --build

# ── Command 3: docker-compose build ──
# ONLY builds images — does NOT start containers
# Useful for pre-building or CI/CD pipelines
docker-compose build
```

| Command | Builds Images? | Starts Containers? | When to Use |
|---|---|---|---|
| `docker-compose up` | Only if missing | ✅ Yes | Normal startup (no code changes) |
| `docker-compose up --build` | ✅ Always (forced) | ✅ Yes | After code changes |
| `docker-compose build` | ✅ Always | ❌ No | Pre-build only, CI/CD |

### 3. What Gets Built vs What Gets Pulled

The `build` vs `image` distinction determines behavior:

```yaml
services:
  mongodb:
    image: mongo              # ← PULLED from Docker Hub (not built)
                              #    docker-compose build has NO effect on this

  backend:
    build: ./backend          # ← BUILT from local Dockerfile
                              #    docker-compose build DOES affect this

  frontend:
    build: ./frontend         # ← BUILT from local Dockerfile
                              #    docker-compose build DOES affect this
```

`docker-compose build` only affects services with `build:` — services using `image:` are already pre-built and are pulled, not built.

### 4. Container Naming Convention

Docker Compose generates container names automatically using this pattern:

```
<project-folder>_<service-name>_<instance-number>

Examples:
docker-complete_mongodb_1
docker-complete_backend_1
docker-complete_frontend_1
```

**Note:** In Docker Compose V2 (newer), the separator is a hyphen instead of underscore:
```
docker-complete-mongodb-1
docker-complete-backend-1
docker-complete-frontend-1
```

| Component | Source | Example |
|---|---|---|
| Project folder | Directory containing `docker-compose.yml` | `docker-complete` |
| Service name | Key under `services:` in compose file | `mongodb` |
| Instance number | Increments when scaling | `1` (or `2`, `3`...) |

### 5. Service Names vs Container Names

```yaml
services:
  mongodb:        # ← This is the SERVICE NAME
    image: mongo
```

| Concept | Value | Used For |
|---|---|---|
| **Service name** | `mongodb` | DNS hostname, `depends_on`, `docker-compose logs mongodb` |
| **Container name** (auto) | `docker-complete_mongodb_1` | `docker ps`, `docker stop`, `docker logs` |
| **Container name** (custom) | Whatever you set | Same as auto, but your chosen name |

**Service names are NOT container names** — service names are used within Docker Compose and for DNS resolution on the network. Container names are the actual names of the running Docker containers.

### 6. Custom Container Names with `container_name`

```yaml
services:
  mongodb:
    image: mongo
    container_name: mongodb    # ← Forces this exact container name
```

```bash
# Without container_name:
docker ps
# NAMES: docker-complete_mongodb_1

# With container_name: mongodb
docker ps
# NAMES: mongodb
```

**Considerations for using `container_name`:**

| Pro | Con |
|---|---|
| Predictable, clean names | Cannot scale the service (`--scale` won't work) |
| Easier to reference in scripts | Name conflicts if running multiple compose projects |
| Matches service name for consistency | Limits flexibility |

**When to use:** Small projects, single instances, when scripts reference containers by name.
**When to avoid:** Production, when scaling is needed, when running multiple compose projects.

### 7. Complete Command Reference Summary

```bash
# ── Starting ──
docker-compose up              # Attached mode, build if needed
docker-compose up -d           # Detached mode, build if needed
docker-compose up -d --build   # Detached, force rebuild
docker-compose up -d mongodb   # Start specific service only

# ── Building ──
docker-compose build           # Build all custom images (no start)
docker-compose build backend   # Build specific service image only

# ── Stopping ──
docker-compose down            # Stop + remove containers + network
docker-compose down -v         # + remove volumes
docker-compose down --rmi all  # + remove all images
docker-compose down -v --rmi all  # Remove everything
docker-compose stop            # Stop only (don't remove)

# ── Monitoring ──
docker-compose ps              # List running services
docker-compose logs            # View all logs
docker-compose logs -f         # Stream logs
docker-compose logs backend    # Logs for specific service
docker-compose top             # Processes in containers

# ── Interaction ──
docker-compose exec backend sh       # Shell into service
docker-compose exec mongodb mongosh  # Run command in service
docker-compose restart backend       # Restart one service
docker-compose start                 # Start stopped services
```

## 🎯 Interview Questions & Answers

### Q1: When does Docker Compose rebuild images and when does it reuse them?

**Answer:**
Docker Compose follows these rules for image management:

- **`docker-compose up`**: Checks if the image exists locally. If it does, it **reuses** it without rebuilding — even if source code has changed. If the image doesn't exist, it builds it.
- **`docker-compose up --build`**: **Forces a rebuild** of all images defined with `build:` before starting containers. Use this after modifying source code.
- **`docker-compose build`**: Builds images only, without starting containers.

This behavior is intentional for performance — rebuilding images on every `up` would be slow. But it means developers must explicitly trigger rebuilds when code changes:

```bash
# After changing backend source code:
docker-compose up -d --build    # ✅ Rebuilds with new code

# This would NOT pick up changes:
docker-compose up -d            # ❌ Reuses old cached image
```

Services using `image:` (pre-built images from registries) are never affected by the build commands — they're pulled, not built.

### Q2: What is the difference between `docker-compose build` and `docker-compose up --build`?

**Answer:**

| Command | Builds Images | Starts Containers | Use Case |
|---|---|---|---|
| `docker-compose build` | ✅ Yes | ❌ No | Pre-build images (CI/CD, validation) |
| `docker-compose up --build` | ✅ Yes | ✅ Yes | Build AND start in one step |

`docker-compose build` is useful when you want to verify that images build successfully without actually starting the application. This is common in CI/CD pipelines:

```bash
# CI/CD pipeline example
docker-compose build           # Step 1: Build images (fail fast if broken)
docker-compose up -d           # Step 2: Start containers (images already built)
docker-compose exec backend npm test  # Step 3: Run tests
docker-compose down            # Step 4: Cleanup
```

`docker-compose up --build` combines the build and start steps, which is more convenient during development when you want to quickly iterate.

### Q3: How does Docker Compose name containers and how can you customize the names?

**Answer:**
Docker Compose auto-generates container names using the pattern:
```
<project-name>_<service-name>_<instance-number>
```

For example, if your project folder is `my-app` and you have a service called `backend`:
- Container V1 naming: `my-app_backend_1`
- Container V2 naming: `my-app-backend-1` (hyphen separator)

The project name defaults to the directory name but can be overridden:
```bash
docker-compose -p custom-project up -d
# Container name: custom-project_backend_1
```

To set a **custom container name**, use `container_name`:
```yaml
services:
  mongodb:
    image: mongo
    container_name: my-mongodb    # Exact name used
```

**Caveat:** Using `container_name` prevents scaling (`docker-compose up --scale mongodb=3` would fail because multiple containers can't share the same name). For most cases, the auto-generated names are fine.

### Q4: Does `docker-compose build` affect services that use `image:` instead of `build:`?

**Answer:**
**No.** `docker-compose build` only builds images for services that have a `build:` directive. Services using `image:` reference pre-built images from registries (Docker Hub, private registries, etc.) and are not affected by the build command.

```yaml
services:
  mongodb:
    image: mongo          # ← NOT affected by docker-compose build
                          #    This is pulled, not built

  backend:
    build: ./backend      # ← AFFECTED by docker-compose build
                          #    Built from ./backend/Dockerfile

  frontend:
    build: ./frontend     # ← AFFECTED by docker-compose build
```

```bash
docker-compose build
# Only builds: backend, frontend
# Does NOT touch: mongodb (uses pre-built image)
```

To update a pulled image to its latest version, use:
```bash
docker-compose pull        # Pulls latest versions of image: services
```

### Q5: What is the relationship between service names in `docker-compose.yml` and actual container names?

**Answer:**
They are related but different:

- **Service name**: Defined as the key under `services:` in the compose file. Used for DNS resolution on the Docker network, in `depends_on`, and in compose commands (`docker-compose logs backend`).
- **Container name**: The actual name of the running Docker container. Auto-generated by Compose as `<project>_<service>_<n>` unless overridden with `container_name`.

```yaml
services:
  mongodb:              # Service name: "mongodb"
    image: mongo        # Container name: "myproject_mongodb_1" (auto)
```

The service name `mongodb` works as a DNS hostname regardless of the actual container name. Other services can always connect to `mongodb:27017` — Docker resolves it correctly.

```javascript
// This works regardless of actual container name
mongoose.connect('mongodb://mongodb:27017/mydb');
// "mongodb" = service name = DNS hostname
```

### Q6: When would you use `container_name` and when should you avoid it?

**Answer:**

**Use `container_name` when:**
- You have scripts or tools that reference containers by exact name
- You're running a single instance and want predictable naming
- Debugging and you want clean `docker ps` output
- External systems need to reference the container by a known name

**Avoid `container_name` when:**
- You need to **scale** the service (`--scale backend=3` fails if all instances would get the same name)
- You run **multiple instances** of the same compose project on one machine (name conflicts)
- You're following **best practices** for production (auto-generated names prevent conflicts)

```yaml
# ✅ OK for development
services:
  mongodb:
    container_name: mongodb

# ❌ Prevents scaling
docker-compose up --scale mongodb=3
# Error: container name "mongodb" already in use
```

In general, the auto-generated names work well and are the safer default.

### Q7: How would you handle a situation where you need to rebuild only one specific service's image?

**Answer:**
You can target a specific service with the build command:

```bash
# Build only the backend image
docker-compose build backend

# Build only the frontend image
docker-compose build frontend

# Build multiple specific services
docker-compose build backend frontend
```

After building, start the updated service:
```bash
# Restart only the rebuilt service
docker-compose up -d --no-deps backend
```

The `--no-deps` flag prevents Compose from also restarting services that `backend` depends on (like mongodb), since those don't need to change.

Alternatively, rebuild and restart in one step:
```bash
# Rebuild and restart everything
docker-compose up -d --build

# Rebuild and restart specific service (plus dependencies)
docker-compose up -d --build backend
```

### Q8: Summarize the complete Docker Compose workflow for a development cycle.

**Answer:**

```bash
# 1. INITIAL SETUP (first time)
docker-compose up -d                # Builds images, pulls dependencies, starts everything

# 2. DEVELOPMENT CYCLE
#    - Edit code (bind mounts sync changes for interpreted languages)
#    - For compiled languages or Dockerfile changes:
docker-compose up -d --build        # Rebuild and restart

# 3. DEBUGGING
docker-compose logs -f backend      # Stream backend logs
docker-compose exec backend sh      # Shell into container
docker-compose ps                   # Check service status

# 4. RESTART SPECIFIC SERVICE
docker-compose restart backend      # Quick restart (no rebuild)
docker-compose up -d --build backend # Rebuild + restart one service

# 5. STOP FOR THE DAY
docker-compose down                 # Stop + remove (volumes preserved)

# 6. RESUME NEXT DAY
docker-compose up -d                # Fast restart (images cached, data in volumes)

# 7. FULL RESET (fresh start)
docker-compose down -v --rmi all    # Remove everything
docker-compose up -d                # Complete rebuild from scratch
```

### Q9: What is the significance of `docker-compose --help` and how do you discover available options for subcommands?

**Answer:**
Docker Compose supports `--help` at multiple levels:

```bash
# Top-level help — shows all available commands
docker-compose --help

# Subcommand help — shows options for specific commands
docker-compose up --help       # Shows --build, -d, --scale, etc.
docker-compose down --help     # Shows -v, --rmi, --remove-orphans, etc.
docker-compose build --help    # Shows --no-cache, --pull, etc.
docker-compose logs --help     # Shows -f, --tail, --timestamps, etc.
```

This is the fastest way to discover available options. For example, `docker-compose up --help` reveals the `--build` flag, which is essential knowledge for development workflows.

Key discoverable options:
- `up --build` — force rebuild
- `up --scale service=N` — run N instances
- `up --no-deps` — don't start dependencies
- `down --rmi local` — remove locally built images
- `build --no-cache` — rebuild without Docker layer cache

### Q10: Compare the entire Docker Compose lifecycle to the equivalent manual Docker commands for a three-service application.

**Answer:**

**Manual Docker commands (setup):**
```bash
docker network create app-net
docker volume create app-data
docker volume create app-logs
docker pull mongo
docker build -t app-backend ./backend
docker build -t app-frontend ./frontend
docker run -d --name mongodb --network app-net -v app-data:/data/db \
  -e MONGO_INITDB_ROOT_USERNAME=admin -e MONGO_INITDB_ROOT_PASSWORD=secret mongo
docker run -d --name backend --network app-net -p 3000:3000 \
  -v app-logs:/app/logs -v $(pwd)/backend:/app -v /app/node_modules \
  -e MONGO_URL=mongodb://admin:secret@mongodb:27017/db?authSource=admin app-backend
docker run -d --name frontend --network app-net -p 3001:3000 \
  -v $(pwd)/frontend/src:/app/src -it app-frontend
```

**Manual Docker commands (teardown):**
```bash
docker stop frontend backend mongodb
docker rm frontend backend mongodb
docker network rm app-net
docker volume rm app-data app-logs
docker rmi app-backend app-frontend
```

**Total: ~15 commands**

**Docker Compose equivalent:**
```bash
# Setup
docker-compose up -d

# Teardown
docker-compose down -v --rmi all
```

**Total: 2 commands**

Same result. The `docker-compose.yml` file encapsulates all the configuration that would otherwise be scattered across 15 command-line invocations. It's reproducible, shareable, version-controlled, and dramatically reduces human error.

## 🛠️ Practical Guide

### docker-compose.yml (Final Complete Version)

```yaml
version: "3.8"

services:
  # ── Database ──
  mongodb:
    image: mongo
    # container_name: mongodb       # Optional: custom name
    volumes:
      - data:/data/db
    environment:
      MONGO_INITDB_ROOT_USERNAME: admin
      MONGO_INITDB_ROOT_PASSWORD: secret

  # ── Backend API ──
  backend:
    build: ./backend
    # container_name: backend       # Optional: custom name
    ports:
      - "3000:3000"
    volumes:
      - logs:/app/logs
      - ./backend:/app
      - /app/node_modules
    environment:
      MONGO_URL: mongodb://admin:secret@mongodb:27017/goals?authSource=admin
      NODE_ENV: development
    depends_on:
      - mongodb

  # ── Frontend ──
  frontend:
    build: ./frontend
    # container_name: frontend      # Optional: custom name
    ports:
      - "3001:3000"
    volumes:
      - ./frontend/src:/app/src
    stdin_open: true
    tty: true
    depends_on:
      - backend

volumes:
  data:
  logs:
```

### docker-commands.sh — Build & Naming Walkthrough

```bash
#!/bin/bash

# ============================================================
# DOCKER COMPOSE — BUILD COMMANDS & NAMING
# ============================================================

# ──────────────────────────────────────────────────────────
# PART 1: BUILD COMMANDS COMPARISON
# ──────────────────────────────────────────────────────────

echo "=== Build Commands ==="

# Just build images (don't start containers)

docker-compose build
echo "✅ Images built (containers NOT started)"
echo ""

# List built images
docker images | grep -E "REPOSITORY|docker-complete"

# Start using cached images (no rebuild)
echo ""
echo "--- docker-compose up -d (reuses cached images) ---"
docker-compose up -d
echo "✅ Started with cached images (fast)"

# Verify running
docker-compose ps

# Stop
docker-compose down

# Start with forced rebuild
echo ""
echo "--- docker-compose up -d --build (forces rebuild) ---"
docker-compose up -d --build
echo "✅ Started with freshly rebuilt images"

docker-compose down

# ──────────────────────────────────────────────────────────
# PART 2: SELECTIVE BUILDING
# ──────────────────────────────────────────────────────────

echo ""
echo "=== Selective Building ==="

# Build only backend
echo "--- Building only backend ---"
docker-compose build backend
echo "✅ Only backend image rebuilt"

# Build only frontend
echo "--- Building only frontend ---"
docker-compose build frontend
echo "✅ Only frontend image rebuilt"

# Build with no cache (complete fresh build)
echo "--- Building with no cache ---"
docker-compose build --no-cache backend
echo "✅ Backend rebuilt from scratch (no layer cache)"

# ──────────────────────────────────────────────────────────
# PART 3: CONTAINER NAMING
# ──────────────────────────────────────────────────────────

echo ""
echo "=== Container Naming ==="

docker-compose up -d

echo "--- Auto-generated container names ---"
docker ps --format "table {{.Names}}\t{{.Image}}\t{{.Status}}"
echo ""
echo "Pattern: <project-folder>_<service-name>_<instance-number>"
echo ""
echo "Service name 'mongodb' → Container: docker-complete_mongodb_1"
echo "Service name 'backend' → Container: docker-complete_backend_1"
echo "Service name 'frontend' → Container: docker-complete_frontend_1"
echo ""
echo "Note: Service names ≠ container names"
echo "Service names are for DNS resolution and compose commands"
echo "Container names are for docker CLI commands"

docker-compose down

# ──────────────────────────────────────────────────────────
# PART 4: CUSTOM PROJECT NAME
# ──────────────────────────────────────────────────────────

echo ""
echo "=== Custom Project Name ==="

docker-compose -p my-goals-app up -d

echo "--- With custom project name ---"
docker ps --format "table {{.Names}}"
echo ""
echo "Container names now prefixed with 'my-goals-app' instead of folder name"

docker-compose -p my-goals-app down

# ──────────────────────────────────────────────────────────
# PART 5: FULL WORKFLOW DEMONSTRATION
# ──────────────────────────────────────────────────────────

echo ""
echo "=== Complete Development Workflow ==="

# Initial setup
echo "1. First startup (builds everything)"
docker-compose up -d
sleep 5

# Verify
echo "2. Check status"
docker-compose ps

# Make a "code change" (simulated)
echo "3. After code change — rebuild and restart"
docker-compose up -d --build

# View logs
echo "4. Check logs"
docker-compose logs --tail=5 backend

# Restart specific service
echo "5. Restart backend only"
docker-compose restart backend

# Stop for the day
echo "6. Stop (preserve data)"
docker-compose down

# Resume next day
echo "7. Resume (fast — images cached)"
docker-compose up -d

# Full cleanup
echo "8. Full cleanup"
docker-compose down -v --rmi all

echo ""
echo "✅ Complete workflow demonstrated"
```
