

# Docker Container-to-Container Communication — Complete Study Guide

---

## 📘 Detailed Notes

### 1. The Principle: One Container, One Concern

Docker best practice dictates that each container should focus on **one main process or service**:

| Container | Responsibility |
|---|---|
| Container A | Node.js Web API |
| Container B | MongoDB Database |
| Container C | Redis Cache (if needed) |

**Why separate containers?**
- Independent scaling (scale the API without scaling the DB)
- Independent updates and deployments
- Isolation and security
- Reusability (swap MongoDB for PostgreSQL without touching the API container)
- Follows microservices principles

### 2. Using Official Docker Hub Images

You don't need to write a Dockerfile for every service. Docker Hub provides **official images** for common tools:

```bash
# Run MongoDB from the official image — no Dockerfile needed
docker run -d --name mongodb mongo
```

- **`mongo`** is the official MongoDB image on Docker Hub
- Docker automatically pulls the image if it's not available locally
- The image comes pre-configured with MongoDB ready to accept connections
- Default MongoDB port: **27017**
- Detailed documentation available on the Docker Hub page for each image

### 3. Three Types of Docker Network Communication

```
┌─────────────────────────────────────────────────────────────────┐
│                    COMMUNICATION TYPES                           │
├──────────────────────┬──────────────────────────────────────────┤
│ 1. Container → Web   │  Works out of the box                    │
│    (External APIs)   │  Containers can reach the internet        │
│                      │                                           │
│ 2. Container → Host  │  Use host.docker.internal                │
│    (Host machine)    │  Replaces localhost in connection strings │
│                      │                                           │
│ 3. Container →       │  Option A: Manual IP lookup (this lesson)│
│    Container         │  Option B: Docker Networks (next lesson) │
└──────────────────────┴──────────────────────────────────────────┘
```

### 4. The Manual IP Address Approach

#### Step 1: Start the target container
```bash
docker run -d --name mongodb mongo
```

#### Step 2: Inspect the container to find its IP address
```bash
docker container inspect mongodb
```

Look for the **NetworkSettings → IPAddress** field in the JSON output:
```json
"NetworkSettings": {
    "IPAddress": "172.17.0.2",
    ...
}
```

#### Step 3: Use the IP address in your application code
```javascript
// Replace host.docker.internal or localhost with the container IP
mongoose.connect('mongodb://172.17.0.2:27017/mydb');
```

#### Step 4: Rebuild the image (because the IP is hard-coded in source)
```bash
docker build -t my-app .
docker run -d --name my-app-container -p 3000:3000 my-app
```

### 5. Why the Manual IP Approach is Problematic

| Problem | Description |
|---|---|
| **Hard-coded IP** | The container IP is embedded in application code |
| **Rebuild required** | Any IP change requires code change → image rebuild |
| **Dynamic IPs** | Container IPs can change when containers restart |
| **Not portable** | IPs differ across machines and environments |
| **Manual lookup** | Must run `docker container inspect` every time |
| **Error-prone** | Easy to use wrong IP, especially with many containers |

### 6. Key Commands Learned

```bash
# Run a container from an official image
docker run -d --name mongodb mongo

# Inspect a container to find its IP address
docker container inspect mongodb

# Find just the IP address (using format flag)
docker container inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' mongodb

# List running containers
docker ps

# Stop a container
docker stop <container-name>
```

### 7. How Container IP Resolution Works

```
┌────────────────────────────────────────────────────────────────┐
│                    Docker Default Bridge Network                │
│                                                                │
│   ┌─────────────────┐          ┌─────────────────┐            │
│   │  Node.js App     │          │  MongoDB         │            │
│   │  Container       │ ──────→  │  Container       │            │
│   │                  │ IP:      │                  │            │
│   │  172.17.0.3      │ 172.17   │  172.17.0.2      │            │
│   │                  │ .0.2:    │                  │            │
│   │  Port: 3000      │ 27017   │  Port: 27017     │            │
│   └─────────────────┘          └─────────────────┘            │
│                                                                │
│   Both containers are on the default "bridge" network          │
│   They CAN communicate via IP, but IPs are dynamic             │
└────────────────────────────────────────────────────────────────┘
```

### 8. Important Distinction: `host.docker.internal` vs Container IP

| Target | Address to Use | When |
|---|---|---|
| Host machine | `host.docker.internal` | Container needs to reach a service on the host |
| Another container | Container's IP address (e.g., `172.17.0.2`) | Container-to-container (manual approach) |
| Another container | Container name (e.g., `mongodb`) | Container-to-container (Docker Networks — better approach) |
| External internet | Regular URL (e.g., `https://api.example.com`) | Works automatically |

## 🎯 Interview Questions & Answers

### Q1: Why should you run a database in a separate container from your application?

**Answer:**
This follows the **single-responsibility principle** for containers. Each container should focus on one main process:

1. **Independent lifecycle management**: Update the app without touching the database, and vice versa
2. **Independent scaling**: Scale API containers horizontally while keeping one database instance
3. **Isolation**: A crash in the application container doesn't bring down the database
4. **Reusability**: Swap databases (MongoDB → PostgreSQL) without rebuilding the app image
5. **Security**: Apply different security policies to each container
6. **Resource management**: Allocate different CPU/memory limits per service
7. **Follows Docker philosophy**: Containers are meant to be lightweight, focused units

---

### Q2: How can you run a MongoDB database in Docker without writing a Dockerfile?

**Answer:**
Docker Hub provides official pre-built images for common services. For MongoDB:

```bash
docker run -d --name mongodb mongo
```

This command:
- Pulls the official `mongo` image from Docker Hub (if not already local)
- Creates and starts a container named `mongodb`
- Runs it in detached mode (`-d`)
- MongoDB starts on its default port 27017 inside the container
- No Dockerfile, no build step — the image is ready to use

You can find official images for PostgreSQL (`postgres`), Redis (`redis`), MySQL (`mysql`), Nginx (`nginx`), and many more on Docker Hub.

### Q3: How do you find the IP address of a running Docker container?

**Answer:**
Use `docker container inspect`:

```bash
# Full inspection output (look for NetworkSettings.IPAddress)
docker container inspect mongodb

# Extract just the IP address
docker container inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' mongodb
```

The IP address is found in the `NetworkSettings` section of the JSON output. This IP is assigned by Docker's internal network and can be used by other containers to communicate with this container.

**Important caveat:** This IP address is dynamic — it can change when the container is restarted, making this approach unreliable for production use.

### Q4: What are the three types of network communication a Docker container can perform?

**Answer:**

1. **Container to External Web (Internet)**
   - Works out of the box with no special configuration
   - Example: `fetch('https://api.example.com')`

2. **Container to Host Machine**
   - Use the special DNS name `host.docker.internal`
   - Resolves to the host machine's IP address
   - Example: `mongoose.connect('mongodb://host.docker.internal:27017/mydb')`

3. **Container to Container**
   - **Manual approach**: Look up the target container's IP via `docker container inspect` and hard-code it
   - **Better approach**: Use Docker Networks with container names as hostnames (covered in next lesson)
   - Example (manual): `mongoose.connect('mongodb://172.17.0.2:27017/mydb')`

---

### Q5: Why is hard-coding a container's IP address in your application code a bad practice?

**Answer:**
Five critical reasons:

1. **Dynamic IPs**: Container IP addresses are assigned dynamically by Docker. They can change when containers are restarted, recreated, or when Docker restarts
2. **Rebuild required**: Since the IP is in the source code, any change requires modifying code → rebuilding the image → recreating the container
3. **Not portable**: The IP will be different on every machine, CI/CD environment, and deployment target
4. **Manual effort**: You must run `docker container inspect` every time and update accordingly
5. **Fragile**: If the target container is recreated (even with the same name), it may get a different IP, breaking the connection silently

The solution is to use **Docker Networks**, where you can reference containers by their **name** instead of IP.

---

### Q6: What is the default network mode in Docker and how does it relate to container-to-container communication?

**Answer:**
The default network mode is the **bridge** network. When you start containers without specifying a network, Docker places them on the default bridge network.

On the default bridge network:
- Containers **can** communicate with each other using IP addresses
- Containers **cannot** communicate using container names (DNS resolution doesn't work on the default bridge)
- Each container gets an IP in the `172.17.0.x` range (typically)

This is why the manual IP approach works but name-based resolution requires creating a **custom Docker network** (user-defined bridge network), which provides automatic DNS resolution by container name.

```bash
# Default bridge — IP only, no name resolution
docker run -d --name mongodb mongo
docker run -d --name app my-app
# app must use 172.17.0.2 to reach mongodb

# Custom network — name resolution works
docker network create my-net
docker run -d --name mongodb --network my-net mongo
docker run -d --name app --network my-net my-app
# app can use "mongodb" as hostname
```

### Q7: What is `docker container inspect` and what useful information does it provide?

**Answer:**
`docker container inspect` returns detailed low-level JSON information about a container:

| Section | Key Information |
|---|---|
| **NetworkSettings** | IP address, MAC address, ports, network name |
| **State** | Running/stopped, exit code, PID, start time |
| **Mounts** | Volumes and bind mounts attached |
| **Config** | Image, environment variables, CMD, entry point |
| **HostConfig** | Resource limits, port bindings, restart policy |

```bash
# Full output
docker container inspect mongodb

# Specific field extraction examples
docker container inspect -f '{{.NetworkSettings.IPAddress}}' mongodb
docker container inspect -f '{{.State.Status}}' mongodb
docker container inspect -f '{{json .Mounts}}' mongodb
```

This command is essential for debugging networking issues, verifying volume mounts, checking environment variables, and understanding container configuration.

### Q8: If you have a Node.js app connecting to MongoDB at `localhost:27017` and you move both into separate Docker containers, what changes do you need to make?

**Answer:**
You **cannot** use `localhost` because in a containerized environment, `localhost` refers to the container itself, not other containers or the host machine.

**Before (both on host):**
```javascript
mongoose.connect('mongodb://localhost:27017/mydb');
```

**After (separate containers — manual IP approach):**
```javascript
// Step 1: Find MongoDB container IP
// docker container inspect mongodb → "172.17.0.2"
mongoose.connect('mongodb://172.17.0.2:27017/mydb');
```

**After (separate containers — Docker Network approach, preferred):**
```javascript
// MongoDB container is named "mongodb" and on the same Docker network
mongoose.connect('mongodb://mongodb:27017/mydb');
```

Key changes:
- Replace `localhost` with the appropriate address
- Ensure both containers can reach each other (same network)
- No port publishing (`-p`) needed for inter-container communication on the same network
- Only the app container needs `-p 3000:3000` to be accessible from the host

---

### Q9: Do you need to publish ports (`-p`) for container-to-container communication?

**Answer:**
**No.** Port publishing (`-p` or `--publish`) maps a container's internal port to a port on the **host machine**. It's only needed when you want to access a container from outside Docker (e.g., from your browser or Postman).

For container-to-container communication:
- Containers on the same Docker network can communicate directly on their internal ports
- No `-p` flag is needed on the MongoDB container if only other containers need to access it
- The default MongoDB port 27017 is accessible to other containers without publishing

```bash
# MongoDB — no -p needed (only accessed by other containers)
docker run -d --name mongodb --network my-net mongo

# Node app — -p needed (accessed from host browser)
docker run -d --name app --network my-net -p 3000:3000 my-app
```

### Q10: How does data isolation work when you move from a local MongoDB to a containerized MongoDB?

**Answer:**
A containerized MongoDB is a **completely separate, isolated database instance**. It has:

- **No access** to data stored in a MongoDB installation on your host machine
- Its **own data directory** inside the container's filesystem
- An **empty database** when first started (unless volumes with existing data are mounted)

This is by design — isolation is a core Docker principle. If you need data to persist across container restarts, you must use a **named volume**:

```bash
# Without volume — data lost when container is removed
docker run -d --name mongodb mongo

# With named volume — data persists
docker run -d --name mongodb -v mongodata:/data/db mongo
```

The path `/data/db` is where MongoDB stores its data files inside the container (defined by the official mongo image).

### app.js (Node.js Application)

```javascript
const express = require('express');
const bodyParser = require('body-parser');
const mongoose = require('mongoose');

const app = express();
app.use(bodyParser.json());

// ─── DATABASE CONNECTION ───
// APPROACH 1: Hard-coded container IP (NOT recommended)
// Found via: docker container inspect mongodb
// const MONGO_URL = 'mongodb://172.17.0.2:27017/favorites';

// APPROACH 2: Using host.docker.internal (for host-installed MongoDB)
// const MONGO_URL = 'mongodb://host.docker.internal:27017/favorites';

// APPROACH 3: Using Docker Network with container name (BEST)
// const MONGO_URL = 'mongodb://mongodb:27017/favorites';

// Configurable via environment variable (most flexible)
const MONGO_URL = process.env.MONGO_URL || 'mongodb://localhost:27017/favorites';

mongoose.connect(MONGO_URL)
  .then(() => {
    console.log(`✅ Connected to MongoDB at: ${MONGO_URL}`);
  })
  .catch((err) => {
    console.error('❌ MongoDB connection failed:', err.message);
    process.exit(1);
  });

// ─── SCHEMA & MODEL ───
const favoriteSchema = new mongoose.Schema({
  name: { type: String, required: true },
  type: { type: String, required: true },
  url: String,
  createdAt: { type: Date, default: Date.now }
});

const Favorite = mongoose.model('Favorite', favoriteSchema);

// ─── ROUTES ───

// GET all favorites
app.get('/favorites', async (req, res) => {
  try {
    const favorites = await Favorite.find();
    res.json({ favorites });
  } catch (err) {
    res.status(500).json({ error: err.message });
  }
});

// POST a new favorite
app.post('/favorites', async (req, res) => {
  const { name, type, url } = req.body;

  if (!name || !type) {
    return res.status(400).json({ error: 'Name and type are required' });
  }

  try {
    const favorite = new Favorite({ name, type, url });
    await favorite.save();
    res.status(201).json({ message: 'Favorite saved!', favorite });
  } catch (err) {
    res.status(500).json({ error: err.message });
  }
});

// DELETE a favorite
app.delete('/favorites/:id', async (req, res) => {
  try {
    await Favorite.findByIdAndDelete(req.params.id);
    res.json({ message: 'Favorite deleted' });
  } catch (err) {
    res.status(500).json({ error: err.message });
  }
});

// Health check
app.get('/health', (req, res) => {
  const dbState = mongoose.connection.readyState;
  const states = { 0: 'disconnected', 1: 'connected', 2: 'connecting', 3: 'disconnecting' };
  res.json({
    status: 'ok',
    database: states[dbState] || 'unknown',
    mongoUrl: MONGO_URL.replace(/\/\/.*@/, '//***@') // hide credentials if any
  });
});

// ─── START SERVER ───
const PORT = process.env.PORT || 3000;
app.listen(PORT, () => {
  console.log(`🚀 Server running on port ${PORT}`);
});
```
