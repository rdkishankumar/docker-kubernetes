## 📘 Detailed Notes

### 1. Frontend Service Configuration

The frontend (React) service requires specific configuration that differs from backend/database services:

```yaml
frontend:
  build: ./frontend          # Build from Dockerfile in ./frontend/
  ports:
    - "3000:3000"            # Publish port for browser access
  volumes:
    - ./frontend/src:/app/src  # Bind mount for live code updates
  stdin_open: true           # -i flag (open standard input)
  tty: true                  # -t flag (allocate pseudo-terminal)
  depends_on:
    - backend                # Start backend before frontend
```

### 2. Interactive Mode (`-it` flag) in Docker Compose

Some applications (like React's development server) require interactive mode to run properly. The `-it` flag from `docker run` translates to **two separate options** in Docker Compose:

```bash
# docker run equivalent
docker run -it my-react-app
```

```yaml
# docker-compose.yml equivalent
services:
  frontend:
    stdin_open: true    # Equivalent of -i (keep STDIN open)
    tty: true           # Equivalent of -t (allocate pseudo-TTY)
```

| `docker run` Flag | Compose Key | Purpose |
|---|---|---|
| `-i` (interactive) | `stdin_open: true` | Keeps standard input open — container can receive input |
| `-t` (tty) | `tty: true` | Allocates a pseudo-terminal — proper output formatting |
| `-it` (combined) | Both keys set to `true` | Interactive terminal session |

**Important:** Even when running in detached mode (`docker-compose up -d`), these settings work internally. The container knows it should accept input and allocate a terminal, allowing applications like React's dev server to start correctly.

### 3. Bind Mounts with Relative Paths

One of Docker Compose's conveniences is that bind mounts use **relative paths** from the `docker-compose.yml` location, not absolute paths:

```bash
# docker run — requires absolute path or $(pwd)
docker run -v /Users/max/projects/my-app/frontend/src:/app/src my-image
docker run -v $(pwd)/frontend/src:/app/src my-image
```

```yaml
# docker-compose.yml — simple relative path
volumes:
  - ./frontend/src:/app/src    # Relative to docker-compose.yml location
```

### 4. Smart Image Rebuilding

Docker Compose is intelligent about when to rebuild images:

| Scenario | Compose Behavior |
|---|---|
| Image already exists, no code changes | ✅ Reuses existing image (fast) |
| Image doesn't exist yet | 🔨 Builds the image |
| Code changed since last build | 🔨 Detects change and rebuilds |
| Want to force rebuild | Use `docker-compose up --build` |
| Only want to build, not start | Use `docker-compose build` |

```bash
# First run — builds all images
docker-compose up -d
# ⏱ Takes time: building frontend, backend images

# Second run — reuses images
docker-compose down
docker-compose up -d
# ⚡ Super fast: images already exist

# Force rebuild after code changes
docker-compose up -d --build
```

### 6. `depends_on` — Service Startup Order

```yaml
services:
  mongodb:
    image: mongo
    # Starts first (no dependencies)

  backend:
    build: ./backend
    depends_on:
      - mongodb          # Starts AFTER mongodb

  frontend:
    build: ./frontend
    depends_on:
      - backend          # Starts AFTER backend
```

**Startup order:** `mongodb` → `backend` → `frontend`

**Important caveat:** `depends_on` only waits for the container to **start**, not for the service inside to be **ready**. MongoDB might be started but not yet accepting connections. For production, use health checks:

```yaml
services:
  mongodb:
    image: mongo
    healthcheck:
      test: mongosh --eval "db.runCommand('ping')"
      interval: 10s
      timeout: 5s
      retries: 5

  backend:
    depends_on:
      mongodb:
        condition: service_healthy    # Wait until HEALTHY, not just started
```

### 7. Volume Persistence Across Restarts

```bash
# Start everything
docker-compose up -d

# Add data via the app (e.g., add a goal)
# Data is stored in MongoDB → in the named volume 'data'

# Stop everything (volumes preserved!)
docker-compose down

# Restart — data is still there!
docker-compose up -d
# Reload browser → goals still visible
```

Without `-v`, `docker-compose down` preserves volumes. This is the expected behavior for persistent data like database records.

## 🎯 Interview Questions & Answers

### Q1: How do you enable interactive mode (`-it`) in Docker Compose?

**Answer:**
The `-it` flag from `docker run` is a combination of two flags: `-i` (interactive/stdin) and `-t` (tty/terminal). In Docker Compose, these are two separate configuration keys:

```yaml
services:
  frontend:
    build: ./frontend
    stdin_open: true    # Equivalent of -i
    tty: true           # Equivalent of -t
```

This is necessary for applications that require an interactive terminal to run properly, such as React's development server (create-react-app). Without these settings, the container may exit immediately or not function correctly.

Even when running in detached mode (`docker-compose up -d`), these settings ensure the container internally maintains an open input connection and terminal, allowing the application to start and run correctly.

### Q2: Does Docker Compose rebuild images every time you run `docker-compose up`?

**Answer:**
**No.** Docker Compose is smart about image management:

- If an image **already exists** and no changes are detected, it **reuses** the cached image (very fast)
- If an image **doesn't exist** (first run or after pruning), it **builds** it
- If code changes are detected (changes to files in the build context), it may **trigger a rebuild**

However, Compose's change detection isn't always perfect. To **force a rebuild**, use the `--build` flag:

```bash
# Reuse existing images (fast)
docker-compose up -d

# Force rebuild all images
docker-compose up -d --build

# Build specific service only
docker-compose build frontend

# Build without starting
docker-compose build
```

This is particularly important after modifying source code that gets `COPY`'d into the image (as opposed to code that's bind-mounted, which is synced live).

### Q3: Why can Docker Compose use relative paths for bind mounts while `docker run` typically needs absolute paths?

**Answer:**
`docker run -v` requires absolute paths (or `$(pwd)` to generate them) because the command runs in whatever directory you're currently in, and Docker needs to know the exact filesystem location.

Docker Compose resolves relative paths **from the location of the `docker-compose.yml` file**. Since Compose knows where its configuration file lives, it can resolve `./frontend/src` to the absolute path automatically.

```bash
# docker run — must use absolute path or $(pwd)
docker run -v $(pwd)/frontend/src:/app/src my-image
docker run -v /home/user/project/frontend/src:/app/src my-image

# docker-compose.yml — clean relative path
volumes:
  - ./frontend/src:/app/src
```

This is one of the many quality-of-life improvements that make Compose files cleaner and more portable than raw Docker commands.

### Q4: What does `depends_on` do and what are its limitations?

**Answer:**
`depends_on` controls **service startup order**. If Service B `depends_on` Service A, Compose ensures Service A's container is started before Service B's container.

```yaml
services:
  mongodb:
    image: mongo

  backend:
    depends_on:
      - mongodb      # mongodb starts first

  frontend:
    depends_on:
      - backend      # backend starts second, frontend starts third
```

**Limitation:** `depends_on` only waits for the container to **start** (the process to begin running), NOT for the service to be **ready** to accept connections. A MongoDB container might be started but still initializing its database, causing the backend to fail if it tries to connect immediately.

**Solutions for production:**
1. Application-level retry logic (reconnect on failure)
2. Health checks with `condition: service_healthy`:
```yaml
services:
  backend:
    depends_on:
      mongodb:
        condition: service_healthy
```

### Q5: Walk through the complete Docker Compose setup for a three-service application (database, backend, frontend).

**Answer:**

```yaml
version: "3.8"

services:
  # Layer 1: Database — no dependencies
  mongodb:
    image: mongo
    volumes:
      - data:/data/db
    environment:
      MONGO_INITDB_ROOT_USERNAME: admin
      MONGO_INITDB_ROOT_PASSWORD: secret
    # No ports published — only backend connects internally

  # Layer 2: API — depends on database
  backend:
    build: ./backend
    ports:
      - "3000:3000"
    volumes:
      - logs:/app/logs
      - ./backend:/app
      - /app/node_modules
    environment:
      MONGO_URL: mongodb://admin:secret@mongodb:27017/goals?authSource=admin
    depends_on:
      - mongodb

  # Layer 3: UI — depends on API
  frontend:
    build: ./frontend
    ports:
      - "3001:3000"
    volumes:
      - ./frontend/src:/app/src
    stdin_open: true
    tty: true
    depends_on:
      - backend

volumes:
  data:
  logs:
```

**What this achieves:**
- Three isolated containers with clear responsibilities
- Automatic network with DNS resolution (service names as hostnames)
- Data persistence via named volumes
- Live code updates via bind mounts
- Correct startup ordering via `depends_on`
- Interactive mode for React dev server
- One command to start (`up -d`) and one to stop (`down`)

### Q6: How does Docker Compose handle the difference between services that need published ports and those that don't?

**Answer:**
In the compose file, you only add `ports:` to services that need to be accessed from **outside** the Docker network (from the host machine, browser, etc.):

```yaml
services:
  mongodb:
    image: mongo
    # NO ports: — only accessed by backend within the network

  backend:
    ports:
      - "3000:3000"     # YES — accessed by frontend (in browser) and Postman

  frontend:
    ports:
      - "3001:3000"     # YES — accessed by user's browser
```

Within the Docker network, all services can communicate on **any port** without publishing. Port publishing (`ports:`) is only the bridge between the Docker network and the host machine. This is a security benefit — the database is not accessible from outside the network.

### Q7: If you run `docker-compose down` and then `docker-compose up -d`, is the startup fast or slow?

**Answer:**
It depends on what was preserved:

**Fast restart (typical — `docker-compose down` without `-v`):**
- Images are **cached** — no rebuild needed
- Volumes are **preserved** — data intact
- Only needs to create containers and network
- Takes seconds

**Slow restart (after `docker-compose down -v --rmi all`):**
- Images must be **rebuilt** or **pulled** again
- Volumes are **gone** — fresh data
- Full build process runs again
- Takes the same time as first startup

```bash
# Fast restart
docker-compose down        # Keeps images + volumes
docker-compose up -d       # ⚡ Seconds — reuses everything

# Slow restart
docker-compose down -v --rmi all   # Removes EVERYTHING
docker-compose up -d               # ⏱ Minutes — rebuilds all images
```

This is why `down` preserves volumes and images by default — for fast iteration during development.

### Q8: How would you set up a complete development environment with live code reloading for both frontend and backend?

**Answer:**

```yaml
version: "3.8"

services:
  mongodb:
    image: mongo
    volumes:
      - data:/data/db

  backend:
    build: ./backend
    ports:
      - "3000:3000"
    volumes:
      - ./backend:/app          # Bind mount — code changes sync live
      - /app/node_modules       # Anonymous volume — protects node_modules
    environment:
      - MONGO_URL=mongodb://mongodb:27017/mydb
    depends_on:
      - mongodb
    # Add nodemon for auto-restart on file changes
    command: ["npx", "nodemon", "app.js"]

  frontend:
    build: ./frontend
    ports:
      - "3001:3000"
    volumes:
      - ./frontend/src:/app/src   # Only mount src — React hot-reloads
    stdin_open: true
    tty: true
    depends_on:
      - backend

volumes:
  data:
```

**Dev workflow:**
1. `docker-compose up -d` — start everything
2. Edit `backend/app.js` → nodemon auto-restarts the server
3. Edit `frontend/src/App.js` → React hot-reloads in browser
4. No image rebuilds needed for code changes
5. `docker-compose down` when done

### Q9: What's the difference between `docker-compose stop` and `docker-compose down`?

**Answer:**

| Command | Stops Containers | Removes Containers | Removes Network | Removes Volumes |
|---|---|---|---|---|
| `docker-compose stop` | ✅ Yes | ❌ No | ❌ No | ❌ No |
| `docker-compose down` | ✅ Yes | ✅ Yes | ✅ Yes | ❌ No |
| `docker-compose down -v` | ✅ Yes | ✅ Yes | ✅ Yes | ✅ Yes |

```bash
# Stop — containers still exist (can restart with 'start')
docker-compose stop
docker-compose start     # ← Restart same containers

# Down — containers are removed (recreated on next 'up')
docker-compose down
docker-compose up -d     # ← Creates new containers
```

Use `stop`/`start` for quick pauses during development. Use `down`/`up` for clean restarts.

### Q10: Summarize why Docker Compose is essential for multi-container applications.

**Answer:**
Docker Compose solves five fundamental problems of multi-container management:

1. **Command complexity** — Replaces 10+ Docker commands with 2 (`up`/`down`)
2. **Configuration as code** — YAML file is readable, shareable, version-controlled
3. **Networking** — Auto-creates networks with DNS resolution by service name
4. **Dependency management** — `depends_on` ensures correct startup order
5. **Reproducibility** — Any developer can clone the repo and run `docker-compose up` to get an identical environment

Without Compose, setting up a three-service app requires manually creating networks, volumes, building images, and running containers with long flag-heavy commands — all in the correct order. One typo or forgotten flag breaks everything.

With Compose, the `docker-compose.yml` serves as living documentation of the entire application architecture, and the operational complexity is reduced to starting and stopping.

### backend/app.js

```javascript
const express = require('express');
const bodyParser = require('body-parser');
const mongoose = require('mongoose');
const cors = require('cors');
const fs = require('fs');
const path = require('path');

const app = express();
app.use(bodyParser.json());
app.use(cors());

// ─── Logging to volume ───
function log(msg) {
  const dir = path.join(__dirname, 'logs');
  if (!fs.existsSync(dir)) fs.mkdirSync(dir, { recursive: true });
  fs.appendFileSync(
    path.join(dir, 'access.log'),
    `[${new Date().toISOString()}] ${msg}\n`
  );
}

// ─── MongoDB Connection ───
const MONGO_URL = process.env.MONGO_URL || 'mongodb://mongodb:27017/goals';

mongoose.connect(MONGO_URL)
  .then(() => {
    console.log('✅ Connected to MongoDB');
    log('MongoDB connected');
  })
  .catch(err => {
    console.error('❌ Failed:', err.message);
    log(`MongoDB failed: ${err.message}`);
    process.exit(1);
  });

// ─── Model ───
const Goal = mongoose.model('Goal', {
  text: { type: String, required: true },
  createdAt: { type: Date, default: Date.now }
});

// ─── Routes ───
app.get('/goals', async (req, res) => {
  const goals = await Goal.find().sort({ createdAt: -1 });
  log(`GET /goals → ${goals.length} goals`);
  res.json({ goals });
});

app.post('/goals', async (req, res) => {
  const { text } = req.body;
  if (!text || !text.trim()) {
    return res.status(400).json({ error: 'Text is required' });
  }
  const goal = new Goal({ text: text.trim() });
  await goal.save();
  log(`POST /goals → "${text.trim()}"`);
  res.status(201).json({ message: 'Goal created', goal });
});

app.delete('/goals/:id', async (req, res) => {
  await Goal.findByIdAndDelete(req.params.id);
  log(`DELETE /goals/${req.params.id}`);
  res.json({ message: 'Goal deleted' });
});

const PORT = process.env.PORT || 3000;
app.listen(PORT, () => {
  console.log(`🚀 Backend on port ${PORT}`);
  log(`Server started on port ${PORT}`);
});
```
