

# Docker Compose — Starting & Stopping Services (`up` and `down`)

---

## 📘 Detailed Notes

### 1. The Two Essential Commands

Docker Compose boils down to two primary commands that replace dozens of manual Docker commands:

```
┌─────────────────────────────────────────────────────────────┐
│                                                              │
│  docker-compose up      → Build, pull, create, start         │
│  docker-compose down    → Stop, remove containers & network  │
│                                                              │
│  That's it. Two commands for your entire multi-container app.│
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

### 2. What `docker-compose up` Does (Step by Step)

When you run `docker-compose up`, Docker Compose performs these operations automatically and in order:

```
Step 1: Read docker-compose.yml
Step 2: Create a default network    → <project-folder>_default
Step 3: Create named volumes        → <project-folder>_<volume-name>
Step 4: Pull images (if not local)  → For services using image:
Step 5: Build images (if needed)    → For services using build:
Step 6: Create containers
Step 7: Start containers (respecting depends_on order)
Step 8: Attach to logs (unless -d is used)
```

**Example output:**
```
Creating network "docker-complete_default" with the default driver
Creating volume "docker-complete_data" with default driver
Pulling mongodb (mongo:)...
Building backend...
Creating docker-complete_mongodb_1 ... done
Creating docker-complete_backend_1 ... done
Attaching to docker-complete_mongodb_1, docker-complete_backend_1
```

### 3. Naming Convention

Docker Compose **prefixes** everything with your project folder name:

| Resource | Naming Pattern | Example |
|---|---|---|
| Network | `<project-folder>_default` | `docker-complete_default` |
| Named Volume | `<project-folder>_<volume-name>` | `docker-complete_data` |
| Container | `<project-folder>_<service-name>_<instance>` | `docker-complete_mongodb_1` |

The project folder name is the directory where `docker-compose.yml` lives. You can override this with `-p` flag:
```bash
docker-compose -p myproject up -d
```

### 4. Attached vs Detached Mode

```bash
# ATTACHED mode (default) — logs stream to terminal
# Ctrl+C stops all containers
docker-compose up

# DETACHED mode — runs in background, returns control to terminal
docker-compose up -d
```

| Mode | Behavior | Stop With |
|---|---|---|
| Attached (default) | Logs stream to terminal, terminal is blocked | `Ctrl+C` |
| Detached (`-d`) | Runs in background, terminal is free | `docker-compose down` |

### 5. What `docker-compose down` Does

```bash
# Standard — stops and removes containers + default network
docker-compose down

# With -v — ALSO removes named volumes
docker-compose down -v
```

| Command | Removes Containers | Removes Network | Removes Volumes |
|---|---|---|---|
| `docker-compose down` | ✅ Yes | ✅ Yes (default network) | ❌ No |
| `docker-compose down -v` | ✅ Yes | ✅ Yes | ✅ Yes |
| `docker-compose down --rmi all` | ✅ Yes | ✅ Yes | ❌ No, + removes images |
| `docker-compose down -v --rmi all` | ✅ Yes | ✅ Yes | ✅ Yes, + removes images |

**Why volumes are NOT removed by default:**
Volumes exist to **persist data**. Deleting them automatically would defeat their purpose. You must explicitly add `-v` to remove volume data.

### 6. Starting from a Clean Slate

To demonstrate a fresh start (as shown in the transcript):

```bash
# Remove all images
docker image prune -a

# Remove all stopped containers
docker container prune

# Verify nothing is running
docker ps

# Now docker-compose up will pull/build everything from scratch
docker-compose up -d
```

### 7. Lifecycle Flow

```
┌──────────────────────────────────────────────────────────────┐
│                    COMPOSE LIFECYCLE                          │
│                                                              │
│  docker-compose up -d                                        │
│  ┌──────────────────────────────────────────────────────┐   │
│  │ 1. Create network (docker-complete_default)           │   │
│  │ 2. Create volume  (docker-complete_data)              │   │
│  │ 3. Pull mongo image (if not local)                    │   │
│  │ 4. Build backend image (from Dockerfile)              │   │
│  │ 5. Create & start mongodb container                   │   │
│  │ 6. Create & start backend container                   │   │
│  └──────────────────────────────────────────────────────┘   │
│                          ↕                                   │
│              Application is running                          │
│                          ↕                                   │
│  docker-compose down                                         │
│  ┌──────────────────────────────────────────────────────┐   │
│  │ 1. Stop all containers                                │   │
│  │ 2. Remove all containers                              │   │
│  │ 3. Remove default network                             │   │
│  │ 4. Volumes PRESERVED (unless -v is used)              │   │
│  └──────────────────────────────────────────────────────┘   │
│                                                              │
│  docker-compose down -v                                      │
│  ┌──────────────────────────────────────────────────────┐   │
│  │ Same as above + removes named volumes                 │   │
│  │ ⚠️  ALL DATA IN VOLUMES IS PERMANENTLY LOST           │   │
│  └──────────────────────────────────────────────────────┘   │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 8. Terminal Requirement

You must be **navigated into the directory** where the `docker-compose.yml` file lives before running any compose commands. Compose looks for the file in the current working directory.

```bash
# Must be in the project directory
cd /path/to/my-project

# Now compose commands work
docker-compose up -d
docker-compose down
```

Alternatively, specify the file explicitly:
```bash
docker-compose -f /path/to/docker-compose.yml up -d
```

## 🎯 Interview Questions & Answers

### Q1: What does `docker-compose up` do and what resources does it create?

**Answer:**
`docker-compose up` reads the `docker-compose.yml` file and performs a complete setup:

1. **Creates a default network** — named `<project>_default`, connecting all services
2. **Creates named volumes** — as declared in the top-level `volumes:` section
3. **Pulls images** — for services using `image:` (if not available locally)
4. **Builds images** — for services using `build:` (from their Dockerfiles)
5. **Creates containers** — one per service
6. **Starts containers** — respecting `depends_on` ordering
7. **Attaches to logs** — streams output to terminal (unless `-d` is used)

All resources are prefixed with the project folder name (e.g., `myproject_default`, `myproject_data`, `myproject_mongodb_1`).

This single command replaces what would typically be 5-10+ separate Docker commands (network create, volume create, build, run for each service).

---

### Q2: What is the difference between `docker-compose up` and `docker-compose up -d`?

**Answer:**

| Aspect | `docker-compose up` | `docker-compose up -d` |
|---|---|---|
| **Mode** | Attached | Detached |
| **Terminal** | Blocked — logs stream in real-time | Free — returns control immediately |
| **Log visibility** | Logs visible directly | Use `docker-compose logs` to view |
| **How to stop** | `Ctrl+C` in the terminal | `docker-compose down` |
| **Use case** | Debugging, watching startup | Normal development, production |

Attached mode is useful when debugging startup issues because you can see all service logs interleaved in real-time. Detached mode is the standard for everyday use since it doesn't block your terminal.

---

### Q3: What does `docker-compose down` remove and what does it preserve?

**Answer:**
By default, `docker-compose down` removes:
- ✅ All containers created by `docker-compose up`
- ✅ The default network created by Compose

It **preserves**:
- ❌ Named volumes (data persists)
- ❌ Built images (cached for faster next startup)

To also remove volumes: `docker-compose down -v`
To also remove images: `docker-compose down --rmi all`

**Volumes are preserved by design** because their purpose is data persistence. If volumes were deleted automatically, databases would lose data every time you stopped the application — defeating the purpose of volumes entirely. The `-v` flag makes volume deletion an explicit, deliberate action.

---

### Q4: How does Docker Compose name the resources it creates?

**Answer:**
Compose prefixes all resources with the **project name**, which defaults to the directory name where `docker-compose.yml` is located:

```
Project directory: /home/user/my-app/

Resources created:
├── Network:    my-app_default
├── Volume:     my-app_data
├── Volume:     my-app_logs
├── Container:  my-app_mongodb_1     (or my-app-mongodb-1 in Compose V2)
├── Container:  my-app_backend_1
└── Container:  my-app_frontend_1
```

The `_1` suffix indicates instance number (relevant when scaling services).

You can override the project name:
```bash
# Using -p flag
docker-compose -p custom-name up -d

# Using COMPOSE_PROJECT_NAME environment variable
COMPOSE_PROJECT_NAME=custom-name docker-compose up -d
```

### Q5: What happens when you press `Ctrl+C` during attached mode? Does it just stop or also remove containers?

**Answer:**
Pressing `Ctrl+C` in attached mode **stops** the containers but does **not remove** them. The containers remain in a stopped state.

```bash
# Start in attached mode
docker-compose up
# ... logs streaming ...
# Press Ctrl+C

# Containers are STOPPED but NOT REMOVED
docker ps -a
# Shows stopped containers

# To remove them, run:
docker-compose down
```

This is different from `docker-compose down`, which both stops AND removes containers plus the default network. If you want the behavior of `Ctrl+C` to also remove containers, you can run `docker-compose down` afterward or use `docker-compose up --abort-on-container-exit` for specific scenarios.

### Q6: If you run `docker-compose up` and then modify your source code, do you need to rebuild?

**Answer:**
It depends on your setup:

**With bind mounts** — No rebuild needed for code changes:
```yaml
services:
  backend:
    build: ./backend
    volumes:
      - ./backend:/app    # Bind mount syncs code changes live
```

**Without bind mounts** — Yes, rebuild is needed:
```bash
# Force rebuild with --build flag
docker-compose up -d --build
```

`docker-compose up` by default **reuses existing images** if they're already built. It does NOT automatically detect source code changes. Adding `--build` forces Compose to rebuild images before starting containers.

```bash
# Just start (use cached images)
docker-compose up -d

# Rebuild and start
docker-compose up -d --build
```

### Q7: Does `docker-compose down -v` also remove anonymous volumes or only named volumes?

**Answer:**
`docker-compose down -v` removes:
- **Named volumes** declared in the top-level `volumes:` section
- **Anonymous volumes** associated with containers defined in the compose file

It effectively cleans up all volume data associated with the compose project.

```bash
# Standard down — keeps ALL volumes
docker-compose down

# With -v — removes named AND anonymous volumes
docker-compose down -v
```

**Important:** This is a destructive operation. All persisted data (database records, uploaded files, logs stored in volumes) is permanently deleted. Use `-v` only when you intentionally want a fresh start.

---

### Q8: Can you start only specific services from a compose file instead of all services?

**Answer:**
Yes. You can specify which services to start:

```bash
# Start only mongodb
docker-compose up -d mongodb

# Start mongodb and backend (not frontend)
docker-compose up -d mongodb backend

# If backend depends_on mongodb, starting backend also starts mongodb
docker-compose up -d backend
# This starts both mongodb (dependency) and backend
```

`depends_on` is respected — if you start a service that depends on another, the dependency is started automatically.

```bash
# Stop only one service
docker-compose stop backend

# Restart only one service
docker-compose restart backend

# View logs for one service
docker-compose logs -f backend
```

### Q9: What is the prerequisite for running `docker-compose` commands?

**Answer:**
You must be **navigated into the directory** that contains the `docker-compose.yml` file. Compose looks for the configuration file in the current working directory.

```bash
# Must be in the project directory
cd /path/to/my-project
docker-compose up -d     # ✅ Works

# From a different directory — fails
cd /home/user
docker-compose up -d     # ❌ Error: no docker-compose.yml found
```

Alternatively, you can specify the file path explicitly:
```bash
docker-compose -f /path/to/my-project/docker-compose.yml up -d
```

Or use a custom filename:
```bash
docker-compose -f docker-compose.prod.yml up -d
```

### Q10: Compare the full lifecycle using manual Docker commands vs Docker Compose.

**Answer:**

**Manual approach (10+ commands):**
```bash
# Setup
docker network create app-net
docker volume create app-data
docker pull mongo
docker build -t my-backend ./backend
docker run -d --name mongodb --network app-net -v app-data:/data/db mongo
docker run -d --name backend --network app-net -p 3000:3000 my-backend

# Teardown
docker stop backend mongodb
docker rm backend mongodb
docker network rm app-net
docker volume rm app-data
docker rmi my-backend
```

**Docker Compose (2 commands):**
```bash
# Setup — one command does everything
docker-compose up -d

# Teardown — one command cleans everything
docker-compose down -v
```

Same result. The compose file captures all the configuration that would otherwise be scattered across multiple terminal commands. It's reproducible, shareable, and version-controllable.

## 🛠️ Practical Guide

### Project Structure

```
docker-complete/
├── docker-compose.yml
├── env/
│   └── mongo.env
├── backend/
│   ├── Dockerfile
│   ├── package.json
│   └── app.js
└── docker-commands.sh
```

### docker-compose.yml

```yaml
version: "3.8"

services:
  mongodb:
    image: mongo
    volumes:
      - data:/data/db
    environment:
      MONGO_INITDB_ROOT_USERNAME: max
      MONGO_INITDB_ROOT_PASSWORD: secret

volumes:
  data:
```

### docker-commands.sh — Complete Practical Walkthrough

```bash
#!/bin/bash

# ============================================================
# DOCKER COMPOSE UP & DOWN — PRACTICAL GUIDE
# ============================================================

# ──────────────────────────────────────────────────────────
# PART 1: CLEAN SLATE — Start from scratch
# ──────────────────────────────────────────────────────────

echo "=== Cleaning Up Everything ==="

# Remove all images (start completely fresh)
docker image prune -a -f
echo "✅ All images removed"

# Remove all stopped containers
docker container prune -f
echo "✅ All stopped containers removed"

# Remove all unused volumes
docker volume prune -f
echo "✅ All unused volumes removed"

# Remove all unused networks
docker network prune -f
echo "✅ All unused networks removed"

# Verify nothing is running
echo ""
echo "--- Running Containers ---"
docker ps
echo "(should be empty)"

echo ""
echo "--- Images ---"
docker images
echo "(should be empty)"

# ──────────────────────────────────────────────────────────
# PART 2: docker-compose up (ATTACHED MODE)
# ──────────────────────────────────────────────────────────

echo ""
echo "=== Starting in Attached Mode ==="
echo "Running: docker-compose up"
echo "Press Ctrl+C to stop"
echo ""

# Attached mode — logs stream to terminal
# This will:
#   1. Create network: docker-complete_default
#   2. Create volume:  docker-complete_data
#   3. Pull mongo image (since we pruned all images)
#   4. Create and start mongodb container
#   5. Stream logs to terminal

# Uncomment to run:
# docker-compose up
# After Ctrl+C, container is STOPPED but NOT REMOVED

# Check stopped container
# docker ps -a
# Shows: docker-complete_mongodb_1 ... Exited

# ──────────────────────────────────────────────────────────
# PART 3: docker-compose up -d (DETACHED MODE)
# ──────────────────────────────────────────────────────────

echo ""
echo "=== Starting in Detached Mode ==="

docker-compose up -d

echo ""
echo "✅ Services started in background"
echo "Terminal is free for other commands"

# ──────────────────────────────────────────────────────────
# PART 4: INSPECT WHAT COMPOSE CREATED
# ──────────────────────────────────────────────────────────

echo ""
echo "=== What Docker Compose Created ==="

# Running services
echo "--- Running Services (docker-compose ps) ---"
docker-compose ps

# Network (auto-created)
echo ""
echo "--- Network ---"
docker network ls | grep -E "NAME|docker-complete"

# Volume (from volumes: section)
echo ""
echo "--- Volume ---"
docker volume ls | grep -E "VOLUME|docker-complete"

# Container (from services: section)
echo ""
echo "--- Container ---"
docker ps --format "table {{.Names}}\t{{.Image}}\t{{.Status}}"

echo ""
echo "Notice the naming convention:"
echo "  Network:   docker-complete_default"
echo "  Volume:    docker-complete_data"
echo "  Container: docker-complete-mongodb-1"
echo "  (all prefixed with project folder name)"

# ──────────────────────────────────────────────────────────
# PART 5: VIEW LOGS (since we're in detached mode)
# ──────────────────────────────────────────────────────────

echo ""
echo "=== Viewing Logs ==="

# View recent logs
docker-compose logs --tail=20

# Stream logs (like attached mode, but can Ctrl+C without stopping containers)
# docker-compose logs -f

# Logs for specific service
docker-compose logs --tail=10 mongodb

# ──────────────────────────────────────────────────────────
# PART 6: docker-compose down (WITHOUT -v)
# ──────────────────────────────────────────────────────────

echo ""
echo "=== Stopping with docker-compose down ==="

docker-compose down

echo ""
echo "What was REMOVED:"
echo "  ✅ Containers (docker-complete-mongodb-1)"
echo "  ✅ Default network (docker-complete_default)"
echo ""
echo "What was PRESERVED:"
echo "  ❌ Named volume (docker-complete_data) — still exists!"
echo "  ❌ Images (mongo) — still cached!"

# Verify volume still exists
echo ""
echo "--- Volumes after 'down' ---"
docker volume ls | grep -E "VOLUME|docker-complete"
echo "(Volume should still be listed)"

# Verify image still exists
echo ""
echo "--- Images after 'down' ---"
docker images | grep -E "REPOSITORY|mongo"
echo "(Image should still be cached)"

# ──────────────────────────────────────────────────────────
# PART 7: RESTART — Volume Data Persists
# ──────────────────────────────────────────────────────────

echo ""
echo "=== Restarting — Testing Volume Persistence ==="

# Start again
docker-compose up -d
sleep 3

# Insert test data
docker-compose exec mongodb mongosh \
  -u max -p secret --authenticationDatabase admin \
  --eval "use mydb; db.items.insertOne({name: 'test', value: 42}); print('Data inserted');"

# Stop (without -v)
docker-compose down

# Restart
docker-compose up -d
sleep 3

# Verify data survived
docker-compose exec mongodb mongosh \
  -u max -p secret --authenticationDatabase admin \
  --eval "use mydb; const doc = db.items.findOne(); print('Found: ' + JSON.stringify(doc));"

echo ""
echo "✅ Data persisted because 'down' preserves volumes!"

# ──────────────────────────────────────────────────────────
# PART 8: docker-compose down -v (WITH -v)
# ──────────────────────────────────────────────────────────

echo ""
echo "=== Stopping with docker-compose down -v ==="

docker-compose down -v

echo ""
echo "What was REMOVED:"
echo "  ✅ Containers"
echo "  ✅ Default network"
echo "  ✅ Named volumes (docker-complete_data) — DATA DELETED!"
echo ""

# Verify volume is gone
echo "--- Volumes after 'down -v' ---"
docker volume ls | grep -E "VOLUME|docker-complete"
echo "(Volume should be GONE)"

# Restart — data will be lost
docker-compose up -d
sleep 3

docker-compose exec mongodb mongosh \
  -u max -p secret --authenticationDatabase admin \
  --eval "use mydb; const count = db.items.countDocuments(); print('Documents: ' + count + ' (should be 0 — fresh start)');"

echo ""
echo "⚠️  Volume data was permanently deleted by 'down -v'"

docker-compose down -v

# ──────────────────────────────────────────────────────────
# PART 9: OTHER USEFUL COMMANDS
# ──────────────────────────────────────────────────────────

echo ""
echo "=== Other Useful Docker Compose Commands ==="

# Start services
docker-compose up -d

# Force rebuild images before starting
docker-compose up -d --build

# Start only specific service(s)
docker-compose up -d mongodb

# Stop without removing (can restart with 'start')
docker-compose stop

# Start previously stopped services
docker-compose start

# Restart specific service
docker-compose restart mongodb

# View running services
docker-compose ps

# Execute command in running service
docker-compose exec mongodb mongosh

# View logs (stream)
docker-compose logs -f

# View logs for specific service
docker-compose logs -f mongodb

# Build images without starting
docker-compose build

# Pull latest images
docker-compose pull

# List images used by services
docker-compose images

# View processes running in containers
docker-compose top

# Down variations
docker-compose down              # Remove containers + network
docker-compose down -v           # + remove volumes
docker-compose down --rmi local  # + remove built images
docker-compose down --rmi all    # + remove ALL images
docker-compose down -v --rmi all # Nuclear option

docker-compose down

# ──────────────────────────────────────────────────────────
# PART 10: COMPARISON TABLE
# ──────────────────────────────────────────────────────────

echo ""
echo "┌─────────────────────────────────────────────────────────────┐"
echo "│           docker-compose down OPTIONS                       │"
echo "├────────────────────────┬─────────┬─────────┬───────┬───────┤"
echo "│ Command                │Containers│Network │Volumes│Images │"
echo "├────────────────────────┼─────────┼─────────┼───────┼───────┤"
echo "│ down                   │  ✅ Rm  │  ✅ Rm  │  ❌   │  ❌   │"
echo "│ down -v                │  ✅ Rm  │  ✅ Rm  │ ✅ Rm │  ❌   │"
echo "│ down --rmi local       │  ✅ Rm  │  ✅ Rm  │  ❌   │ ✅ Rm │"
echo "│ down --rmi all         │  ✅ Rm  │  ✅ Rm  │  ❌   │ ✅ Rm │"
echo "│ down -v --rmi all      │  ✅ Rm  │  ✅ Rm  │ ✅ Rm │ ✅ Rm │"
echo "└────────────────────────┴─────────┴─────────┴───────┴───────┘"
```
